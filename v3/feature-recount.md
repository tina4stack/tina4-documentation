## D14 - CSS: every framework ships invalid declarations (found by checksum, 2026-07-23)

`tina4-css/src/scss/_grid.scss:7,8,24,25,30,31` and `_cards.scss:21,33` use bare SCSS variables
inside `calc()`. Whatever produced `tina4-css/dist/` did not resolve them, so the shipped artifact
literally contains `calc($grid-gutter / 2)` and `calc($border-radius-lg - 1px)`. Browsers treat
those as invalid and DROP the declaration:

- 6x `calc($grid-gutter / ±2)` - container padding, row negative margins, column padding
- 6x `calc($border-radius-lg - 1px)` - card first/last-child corner radii

All four frameworks vendored that broken artifact in **March 2026** (`tina4.min.css` md5
`7a522b86`, 28,558 bytes, byte-identical everywhere, all four leaking the same two variables).
`tina4-php/src/public/css/tina4.css` is the lone exception - regenerated by PHP's own compiler and
correctly compiled - so PHP is internally inconsistent: clean `.css`, broken `.min.css`.

**Not a compiler bug.** Tina4's own SCSS compiler resolves this correctly - verified: Python's
`compile_string` turns `calc($gutter / 2)` into `calc(1.5rem / 2)`, which is valid CSS. This is a
stale prebuilt artifact, and `tina4-css/package.json` has no CSS build script at all (only
`build:frond` for the JS), which is how it drifted unnoticed.

## D17 - all four SCSS compilers leak `!default` into output (NEW, major)

## D17 - RESOLVED (py `38279cc`, php `8902b2cc`, rb `626a43f`, node `d4d862f`)

**Both halves were broken in all four**, not just the leak. Proof against the pre-fix compilers:
`$primary: red;` followed by `$primary: blue !default;` emitted `color: blue !default` - wrong value
AND leaked flag. So every themeable variable a user overrode was being silently discarded.

Verified by me at `38279cc`: compiling `tina4-css/src/scss/tina4.scss` with Python now yields **0
`!default` lines, 0 tokens, 0 broken `rgba(#`** (was 317 / 432 / 41). Semantics correct: plain
assignment beats a later `!default`; an unset variable takes the `!default`; `content: "x !default
y"` is preserved. Per-framework end-to-end: Python 317->0, PHP 321->0, Ruby 203->0, Node 321->0.
Suites: Python 3576, PHP 3881/10025, Ruby 4002, Node 5589 - every delta exactly the +14 new tests.

**My brief was wrong about `!default` in a function argument.** I asked for it to be handled. Dart
Sass 1.101.6 *rejects* `rgba(#000 !default, 0.1)` with `Error: expected ")"`, and a grep over
tina4-css finds **zero** function-arg occurrences - all 53 are plain `$var: value !default;`
declarations. The 41 broken `rgba(#000 !default, ...)` were **the compiler's own corruption**: the
flag was stored inside the variable's value and then substituted into the call. Fixing the
declaration-site strip removed all 41 with no special-casing and **no source change**.

Two design calls I agree with:
- **No error path added.** These compilers have no exception surface at all (an unresolved import
  emits a `/* NOT FOUND */` comment), so raising in four languages for a construct that never occurs
  would be a new behaviour class. A stray `!default` is left verbatim, so invalid input stays
  visibly invalid instead of being converted into CSS Sass would never emit.
- **A blanket strip was rejected** because it would corrupt `content: "x !default y"`, which Dart
  Sass preserves. Both are locked in as negative tests. Flags match case-sensitively, since
  `!DEFAULT` is an error in Dart Sass.

**Ruby had a second, worse bug found on the way:** its declaration regex `(.+?);` lacked `/m`, so
multi-line `$var:` declarations were never extracted and **raw SCSS was dumped into the .css file**
(`$theme-colors: (`, `$font-sizes: (`, `$breakpoints: (`, `$container-max-widths: (`). Python /PHP
/Node's `[^;]+` already spans newlines, so this was a Ruby-only parity fix flowing master->mirror.

No CSS assets were touched - `tina4-css/dist/` and all four vendored `public/css/*` are unmodified
and already contain zero `!default` (they are built with real Dart Sass), so there is no conflict
with the D14 work and nothing needs regenerating.

## D19 - all four compilers still emit invalid CSS for `@each` / `@for` / maps (NEW)

Surfaced while fixing D17 and **unchanged by it**: compiling tina4-css's source leaves **905
unresolved `@each`/`@for` loop-variable lines and 211 map-literal leak lines** in all four
frameworks, because none of them implement `@each`, `@for` or map literals. Same family as D14 and
D17 - invalid CSS reaching output - but a missing feature rather than a leak.

Exposure is bounded: our own shipped assets are built with real Dart Sass, so they are clean. The
victim is a user project that writes idiomatic `@each`/`@for`/map SCSS and compiles it with Tina4's
own compiler - it silently gets garbage CSS.

Recommendation, in priority order: at minimum **fail loudly** ("`@each` is not supported by the
built-in compiler") instead of silently emitting broken output, per the loud-not-silent rule already
applied to `ORM.save()` and `Database.execute()`. Implementing `@each`/`@for`/maps in four
hand-rolled compilers is a much larger piece of work and a separate decision.

### Candidate 51 - RESOLVED, and my diagnosis was wrong in an important way

All four CLIs now reach `doctor`/`setup`/`deploy` by **allow-listed delegation** to the Rust client
(Python `8b2714d`, PHP `328a45e7`, Ruby `571c8a1`, Node `c8c4bc2`). Verified end-to-end against the
real installed client 3.8.56: all four print the genuine doctor report, and `<cli> deploy
bogus-target` propagates the client's exit 2.

**Correction 1 - Ruby was not the outlier, and hard-failing was never the bug.** Node also exits 1,
and rejecting unknown commands is what the self-describing-CLI design *mandates*
(`tina4/src/manifest.rs:9`: "the framework rejects unknowns"). The real defect was the opposite and
I had it backwards: **Python (master) and PHP exited 0** on an unknown command, so `tina4 <typo>`
reported SUCCESS. Fixed in Python first, then mirrored to PHP. The PHP test that asserted `exit 0`
was pinning the bug; it now asserts 1.

**Correction 2 - blind-forward would have been an infinite loop.** I proposed it as an option; it
is unsafe. The Rust client already forwards *its* unknowns to the framework CLI
(`Commands::External` -> `delegate_command`), so a framework forwarding its unknowns back would
ping-pong an unknown command between two processes forever. A closed `DELEGATED` set of commands
the client dispatches natively cannot loop by construction, and keeps "Unknown command" honest for
typos. Belt-and-braces guard: the child gets `TINA4_CLI_DELEGATED=<command>` and refuses to spawn
if it arrives already set.

Contract, identical in all four: client present -> propagate its exit code; client absent or guard
tripped -> actionable message + install one-liner, exit 127; unknown command -> help, exit 1.
The Rust client needed no change.

Not fixed, flagged for a decision:
- **Windows unverified.** PATH resolvers include `.exe`/`.cmd`/`.bat` and exit codes are OS-neutral,
  but nothing ran on Windows and the new test helpers are POSIX-only (`#!/bin/sh`).
- **Node monorepo `tina4` bin alias shadows the client.** `packages/cli/package.json` declares a
  `tina4` bin, so inside the monorepo `tina4nodejs doctor` resolves `tina4` to itself. Users are
  unaffected (the published root package only exposes `tina4nodejs`); removing the alias is a
  packaging change.
- **`packages/cli/dist/bin.js` silently no-ops when invoked via a symlink** (incl. a symlinked
  ancestor like macOS `/tmp`): its entrypoint guard compares realpath'd `import.meta.url` against
  the symlink `process.argv[1]`, so `main()` never runs and it exits 0. Pre-existing, not on the
  shipped path. One-line fix: `realpathSync(process.argv[1])`.
- `tina4-documentation/scripts/audit-truth.py` has a hardcoded `FORWARDED_SUBCOMMANDS` list for the
  client->framework direction; untouched, needs updating for the new delegated direction.
