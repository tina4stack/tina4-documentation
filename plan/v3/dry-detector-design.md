Thresholds\n\n**`MIN_DUPLICATE_NODES = 40` named AST nodes.** Source: Evans, Fraser and Ma, \"Clone Detection via Structural Abstraction\", verbatim: \"skimming suggests that a 40-node threshold gives many actionable clones and that a 20-node threshold is probably too low, just as 80 is too high.\" This is the only published calibration I could find expressed in AST nodes, which is the unit this design counts, and it brackets 40 from both sides.\n\nCross-checks, all in tools' own source: similarity-rs ships `min_tokens: Some(30)` where similarity-core/src/tsed.rs documents tokens as \"Minimum number of tokens (AST nodes)\". dupes-core ships `min_nodes: 10`. jscpd ships `minTokens: 50, minLines: 5` (packages/core/src/options.ts). SonarQube ships 100 tokens plus 10 lines for non-Java (`CpdSettings.getMinimumTokens().orElse(100)`, `DefaultSensorStorage.DEFAULT_CPD_MIN_LINES = 10`). PMD CPD has **no default at all** (`--minimum-tokens` is `required = true` in CpdCommand.java); the famous 100 belongs to apache/maven-pmd-plugin, a different project. Take the academic node-calibrated 40 over all of them.\n\n**COULD NOT VERIFY: there is no standards-body number here.** No ISO/IEEE/ECMA document specifies a duplication threshold. Baxter et al. ICSM 1998 names `MassThreshold`, `SimilarityThreshold` and `MinimumSequenceLengthThreshold` and publishes a value for none of them. Any brief citing \"Baxter's default mass threshold\" is inventing it.\n\n**`MIN_DISTINCT_FILES = 2`.** A clone class must span at least two distinct `file` values. Keep this. See section 8 for what it costs and why I kept it anyway.\n\n**Severity split: `error` when score >= 25.0, else `warn`.** Grounded in Baxter's measured clone-size distribution, verbatim from the paper: \"relatively small in size, on the order of 10 SLOC\" and \"sizes larger than 25 are rare and are therefore not shown.\" Score is removable code lines (section 6), so >= 25 puts a finding in the rare tail. It also mirrors the file's own escalation precedent (`cc > 10` warn / `cc > 20` error; `mi < 40` warn / `mi < 20` error). Measured, this yields 4 / 3 / 0 / 3 errors on tina4-python / tina4-php / tina4-ruby / tina4-nodejs.\n\n**No line floor.** jscpd, similarity-core (5) and SonarQube (10) all ship one; they slide a window over arbitrary lines, so a line floor is their only defence against a match spanning a formatting artefact. Our unit is a whole syntactic function, so a line floor does no independent work, and measured it only cost recall. The strongest evidence against a line floor is a real case in tina4-ruby: `crud.rb::inline_crud_javascript`, `template.rb::error_overlay_css` and `template.rb::error_overlay_head` are **6 nodes across 24 lines** and fingerprint identically. A line-based threshold reports all three as a 24-line clone; the node floor rejects them at 6. Do not add `MIN_CLONE_LINES` back. The in-tree implementation has one at metrics.rs:1292; delete it with the rest.\n\n**No project-level percentage gate.** SonarQube's built-in gate is `new_duplicated_lines_density > 3` on **new** code only, with a documented escape (`MAXIMUM_NEW_LINES_FOR_SMALL_CHANGESETS = 20` forces duplication conditions to OK on small changesets). tina4 has no new-code concept and no baseline store, so a 3% whole-project gate would be a strictly harsher thing than what Sonar ships. Report the percentage; do not gate on it. `--fail-on` stays driven by offender severity.\n\n**The number I am nervous about, stated openly.** A Python `__init__` assigning five fields is exactly 40 named nodes. Two model files with five differently-named fields each will be reported. No such case appeared in the corpus (the constructors that did fire were 115 and 199 nodes), and I judge a duplicated five-field constructor defensible rather than noise. If it proves noisy in the field the fix is one digit, but re-measure before changing it: nudging to 45 costs `frond/compiler.py::_tostr` (41 nodes) and `orm/adapters/firebird.ts::sqlDefault` (42).\n\n---\n\n## 3. Normalisation: what IS and is NOT normalised away\n\nEvery line in this section was measured with the probe at `.../scratchpad/normprobe`, not reasoned about.\n\n**IS normalised away:**\n\n- **Whitespace and layout.** Never enters the fingerprint because whitespace never becomes a tree-sitter node. Free, and it is Baxter's stated reason for choosing ASTs over text.\n- **Comments.** Dropped by `!n.is_named() || n.is_extra()`. Measured MATCH for PHP `/** */`, TypeScript jsdoc, Rust `///`, Ruby `#`, Python `#`. Python **docstrings** are handled by the explicit `is_docstring` skip described in section 1, because they are named nodes and would otherwise be the one cross-language asymmetry in the whole design. Exposure was structural, not theoretical: about a third of tina4-python's outermost function units open with a docstring.\n- **Punctuation and operator tokens.** Dropped by `!n.is_named()`.\n- **Identifiers.** Normalised by hashing `kind_id()` and never reading `utf8_text`. Measured: the two-way-renamed validator pair (every identifier and every string literal changed) MATCHES at `0599afe1963569a7`, 28 nodes. This is the core of the metric and it works.\n- **Ruby block delimiters.** `{ }` and `do/end` fold to the same synthetic id.\n\n**Is NOT normalised away, and the design does not pretend otherwise:**\n\n- **Literal values.** The proposed design claimed these were normalised. They are not. Measured Python MISSes: `'abc'` vs `''` (14 vs 13 nodes), `'abc'` vs `'a\\nb'` (14 vs 15 - `escape_sequence` is a named node), `42` vs `4.2` (same count, different hash), `'a'` vs `f'a{b}'`. String internals (`string_start`, `string_content`, `escape_sequence`, `string_end`, `interpolation`) are all named children.\n- **Type names.** Also claimed and also false. Measured MISSes: TypeScript `string` vs `Foo` (`predefined_type` vs `type_identifier`, same 13 nodes, different hash), `string` vs `string[]`, Rust `String` vs `&str`, PHP `int` vs `?int`.\n- **Statement order.** Swapping two statements changes the fingerprint. Baxter canonicalises commutative operators; we do not, because that needs a per-grammar commutativity table.\n- **Structure, arity, child positions.** Preserved by construction; the CLOSE sentinel makes the serialisation a balanced-parenthesis encoding, so two different shapes cannot collide by accident.\n\n**I considered fixing the literal and type gaps and rejected it on measurement.** Making literals and type annotations opaque leaves (mix the kind id, mix CLOSE, do not recurse) is about 12 lines and does close all of those MISSes. But it also shrinks node counts, which pushes units below the fixed 40-node floor, and Evans calibrated 40 against unnormalised AST node counts. Measured, at the same floor, full opacity took the corpus from 23 / 24 / 3 / 13 classes down to **19 / 22 / 1 / 10**, and literal-only opacity to **20 / 23 / 1 / 12**. Ruby, already the weakest language here, went from 3 findings to 1. Adopting opacity and then lowering the floor to compensate would mean inventing a number, which is the one thing this design refuses to do. So: no opacity, and the honest label follows.\n\n**The honest label.** In Roy/Cordy/Koschke terms this detects **Type-I plus consistent identifier renaming**. It is not full Type-II, because their Type II is verbatim \"Structurally/syntactically identical fragments except for variations in identifiers, literals, types, layout and comments\" and we tolerate identifiers, layout and comments but not literals or types. Write that in the changelog and the doc comment. Do not let the code say Type-2.\n\n**One accepted precision give-away.** `a + b` and `a - b` fingerprint identically (measured MATCH, `9352eb543a072a99`), because the operator token is anonymous while the `binary_expression` wrapper is named. PMD's `--ignore-identifiers` keeps operators distinct; we do not, because recovering it means reading `utf8_text` on anonymous children. Accepted.\n\n---\n\n## 4. Cross-file accumulation\n\n**The cross-file mechanism already exists; do not build one.** `analyze_targets` (metrics.rs:1969) already accumulates `all_functions: Vec<FunctionInfo>` across every file in the scan with no truncation, and already hands the whole vector to `build_offenders(files, functions)` (metrics.rs:1786). Adding two fields to `FunctionInfo` is the entire change.\n\nDo **not** copy the coupling subsystem's park-and-resolve pattern (`pending: Vec<(String, Lang, Vec<String>)>`). That exists because an import specifier only becomes an edge once every file is known. A fingerprint is complete the moment its file is parsed, so there is no second pass, no pending vector and no back-fill.\n\n**The grouping, inside `build_offenders`:**\n\n```rust\nlet mut classes: HashMap<(u64, u32), Vec<&FunctionInfo>> = HashMap::new();\nfor f in functions.iter().filter(|f| f.dup_fp != 0) {\n    classes.entry((f.dup_fp, f.dup_nodes)).or_default().push(f);\n}\nlet mut emitted: Vec<Offender> = Vec::new();\nfor (_, mut members) in classes {\n    if members.len() < 2 { continue; }\n    let distinct: HashSet<&str> = members.iter().map(|m| m.file.as_str()).collect();\n    if distinct.len() < 2 { continue; }\n    members.sort_by(|a, b| a.file.cmp(&b.file).then(a.line.cmp(&b.line)));\n    // ... emit one Offender anchored on members[0]\n}\n```\n\nBoth passes are linear. Iterate `classes` into a `Vec` and sort before emitting so the output does not depend on HashMap iteration order; the existing offender sort (severity_rank desc, then score desc, stable) then finishes the job.\n\nThe key is a **tuple**, not the hash alone. An accidental collision then needs agreement on a 64-bit hash *and* an exact node count, on top of the language seed folded into the FNV initial value. PMD hardens differently: it buckets by rolling hash and re-verifies token by token, which it can afford because it retains the whole token array. We retain no trees, so the tuple is the verification. At the measured ~15,000 eligible units the birthday probability of any collision is roughly 6e-12; at a million units roughly 2.7e-8. The failure mode is one spurious `warn`, not a crash or a wrong exit code. Stated, not hidden.\n\n**Memory on a 22,000-line project.** Two `u64`-sized fields on a struct that already exists. A 22,000-line repo in this corpus runs about 250 files and 1,500-2,000 function nodes, so roughly **32 KB** of new state. Measured across the whole five-repo corpus: 15,000 eligible units, about 240 KB. Even a million-function monorepo is 12 MB. Nothing new is retained:\n\n- **No source text.** The `source: String` is still dropped at the end of each pass-1 iteration. This is why offenders report `file:line` and never print a code snippet the way PMD's SimpleRenderer does. Retaining sources to print snippets would be the largest memory regression in the engine, and `file:line` is enough for a person or an editor to jump to.\n- **No trees, no nodes.** `Node<'tree>` borrows the local `tree` in `analyze_source` and cannot escape it; the existing return type proves the constraint. The fingerprint is an owned `u64` computed before the tree drops.\n- **No byte ranges.** Dropped along with subsumption.\n\n**No subsumption pass.** Baxter needs one because he hashes every subtree, so a 20-statement clone explodes into ~200 overlapping findings; the in-tree `group_clones` needs one for the same reason, and pays a quadratic for it. Our unit is a whole outermost function, so the only nesting possible is a function inside a function, and outermost-only removes that structurally. Measured: zero of the surviving clone classes across all four framework repos involved a nested function.\n\n**No per-file rollup.** No `FileMetrics.duplicate_lines`, no per-file percentage. It would mean touching `FileMetrics`, the `file_with` test helper and the dashboard bubble contract for a number nobody acts on. Project totals go on `Summary`; the actionable detail is the offender list, which carries every endpoint.\n\n---\n\n## 5. Exclusions\n\n**5.1 Test code.
