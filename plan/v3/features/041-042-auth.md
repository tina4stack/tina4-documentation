# Features 41 (JWT) + 42 (session handling)

Audited 2026-08-01. Part of `98-feature-audit.md`. Two features in one document
because they share a trust boundary: the JWT proves who you are, the session
remembers it, and both take their input from a header the client fully controls.

## Method

Every row in the tables below was read from source and then, where it is a
behaviour claim, executed. The two exploitable findings were reproduced against
a real filesystem before being reported, not inferred from reading. Platform for
every measured claim: **macOS 26.5.2 (arm64)**, PHP 8.5.7, Python 3.13.5 (uv
venv), Ruby 4.0.2, Node 24.9.0.

## Finding 1 (EXPLOITABLE): the session cookie steered a filesystem path

The file session backend is the default in all four. It builds a filename from
the session id, and the session id is the `tina4_session` cookie value.

| | id to filename | traversal outcome |
| --- | --- | --- |
| python | `sha256(id)` | safe |
| ruby | `id.gsub(/[^a-zA-Z0-9_-]/, "")` | safe, but silently COLLAPSES distinct ids |
| php | `storagePath . '/' . id . '.json'` | **arbitrary file create/write** |
| node | `join(storagePath, id + ".json")` | **arbitrary `.json` read + overwrite** |

Nothing sanitised the value in between. `Tina4/Router.php:669-671` passes
`$_COOKIE[$sessionCookieName]` straight into `Session::start()`, which assigns
it verbatim; `packages/core/src/dispatchPipeline.ts:192-203` does the same into
`sess.start()`.

**PHP, reproduced.** A cookie of `tina4_session=../../../OUTSIDE/pwned` created
`OUTSIDE/pwned.json` outside the session directory, containing the session data.
Path, filename (`.json` forced) and part of the content are attacker-chosen.

**Node, reproduced.** `start()` discards an id whose read returns null, so a new
file is not created - but when the traversed target already exists and parses as
JSON, the id IS adopted. A cookie of `tina4_session=../../../OUTSIDE/appconfig`
made `session.all()` return the contents of that file (arbitrary `.json`
disclosure into the request) and the following `save()` overwrote it.

Both are remote, unauthenticated, single-request, and need only a legal cookie:
RFC 6265 s4.1.1 permits `/` and `.` in a cookie-octet.

Ruby's sanitise is safe but lossy - `a/b` and `ab` map to the same file, so two
distinct ids collide into one session.

**Fixed** in all four per ADR-0021, with two gates. An incoming id is adopted
only when it is well-formed (`[A-Za-z0-9_-]{1,128}`) AND the store already holds
that session; failing either mints a fresh id. The file handlers also hash the
id into the filename. The alphabet gate is what closes the traversal; the
known-session gate (strict mode) is what closes the fixation described below.
The constraint is on the alphabet, not the length - see ADR-0021 for why an
entropy floor was tried and rejected.

Deploying this logs every existing session out once. That is expected.

## Finding 2 (EXPLOITABLE): Python returned a truthy auth result it never verified

`Auth.authenticate_request()` had a `Basic` branch that decoded the header and
returned `{"auth_type": "basic", "username": ..., "password": ...}`. Nothing
checked those credentials against anything.

| | `Authorization: Basic <anything>` |
| --- | --- |
| python | **truthy dict** |
| php | null |
| ruby | nil |
| node | null |

The documented Python idiom is
`auth = Auth.authenticate_request(request.headers)  # verified payload, or None`,
so an application following the documentation authenticated every caller that
sent a base64 string. Framework-internal callers happened to survive because
they read `user_id`/`sub`/`id`/`email`, which Basic never sets.

The existing suite ASSERTED this as correct: `test_basic_auth` checked that the
returned dict carried the submitted password. That is why it survived.

**Fixed**: the branch is deleted. Breaking, with a migration note.

## JWT (41) difference table

| Behaviour | python | php | ruby | node |
| --- | --- | --- | --- | --- |
| HMAC algorithms | HS256/384/512 | HS256/384/512 | HS256/384/512 | HS256/384/512 |
| RS256 | no | yes (ext-openssl) | only via the `jwt` GEM | yes (node:crypto) |
| `alg` pinned to the configured one | yes | yes | yes | yes |
| `alg: none` rejected | yes | yes | yes | yes |
| unsupported `alg` fails loudly | yes | yes | yes | yes |
| signature compare | `hmac.compare_digest` | `hash_equals` | `fixed_length_secure_compare` | `timingSafeEqual` |
| expiry clock | float | int | int | float |
| `exp` test (before) | `>` | `>` | `>=` | `>` |
| observable `exp` defect | sub-ms | **+1 full second** | none | sub-ms |
| malformed `exp` (before) | bool mis-read | **accepted, never expires** | **accepted, never expires** | **accepted, never expires** |
| malformed `nbf` (before) | bool mis-read | accepted | accepted | rejected |
| `nbf` honoured, 60s leeway | yes | yes | yes | yes |
| `expires_in=0` | non-expiring | non-expiring | **expires instantly** | non-expiring |
| `authenticate_request` order | JWT, key | JWT, key | **key, JWT** | JWT, key |
| API-key result key (before) | `auth_type` | `_auth` | `api_key` | `_auth` |
| `Basic` branch | **yes, unverified** | no | no | no |
| PBKDF2 | sha256 / 260000 / 32B | sha256 / 260000 / 32B | sha256 / 260000 / 32B | sha256 / 260000 / 32B |
| password compare timing-safe | yes | yes | yes | yes |
| `:` hash delimiter accepted | no | no | no | **yes (legacy)** |
| dev-secret bootstrap | yes | yes | yes | yes |
| blank secret in CI/prod warns, never mints | yes | yes | yes | yes |

Password hashes are byte-compatible across all four (`pbkdf2_sha256$260000$salt$hex`,
32-byte derived key), so a user row written by one framework verifies in the
other three. Verified rather than assumed: a Python-produced hash string was fed
to PHP's `hash_pbkdf2`, Ruby's `OpenSSL::KDF.pbkdf2_hmac` and Node's
`pbkdf2Sync`, and all three verified it while correctly rejecting a wrong
password. It is now pinned by a known-answer test with a fixed salt, so a change
to the algorithm, iteration count, key length or delimiter fails loudly instead
of silently locking every existing user out of the other three frameworks.

**RS256 is confirmed PHP/Node-only and should stay that way.** Python and Ruby
cannot sign RS256 without a third-party dependency, which the zero-dependency
core forbids. Ruby's situation is worse than "absent": `Auth.use_hmac?` returns
false whenever `.keys/private.pem` and `.keys/public.pem` exist on disk, at which
point `get_token` calls `require "jwt"` - a gem that is not a runtime dependency.
Calling `Auth.setup` once creates those files, so a single call silently flips
the whole application from HMAC to RS256 and makes every token operation depend
on an uninstalled gem. Recorded, not fixed here (see Not fixed, below).

## Session (42) difference table

The shared contract, not a per-backend sweep.

| Behaviour | python | php | ruby | node |
| --- | --- | --- | --- | --- |
| id entropy | 256 bit | 128 bit | 256 bit | 128 bit |
| adopts an unknown id (fixation, before) | yes | yes | yes | **no** |
| `set()` persists | lazy | **eager** | lazy | **eager** |
| `all()` hides internals | nothing | `_meta` + `_flash_` | nothing | every `_` key |
| `get(k, default)` with stored `false` | `false` | `false` | **`default`** | `false` |
| miss returns | `{}` | `[]` | `{}` | `null` |
| unreachable backend | log + degrade | log + degrade | log + degrade | log + degrade |
| `TINA4_SESSION_STRICT` re-raises | yes | yes | yes | yes |
| unknown backend name raises | yes | yes | yes | yes |
| backend aliases | identical | identical | identical | identical |
| `regenerate()` mints a new id | yes | yes | yes | yes |
| `regenerate()` destroys the old record | yes | yes | yes | yes |
| unrecognised `TINA4_SESSION_HTTPONLY` | **drops HttpOnly** | **drops HttpOnly** | keeps | keeps |
| `Secure` when SameSite=None | yes | yes | yes | yes |
| `Secure` proxy-aware (`x-forwarded-proto`) | yes | yes | yes | yes |

Six backends in all four (file, redis, valkey, mongodb, memcached, database),
with identical names, identical aliases, and an identical raise on an unknown
name. The backend-failure policy is genuinely uniform: read failure degrades to
an empty session, `save()` returns false with the dirty flag retained,
`TINA4_SESSION_STRICT` re-raises. That part of feature 42 is in good shape.

`get()` returning the default for a stored `false` is a real Ruby bug, confirmed
by execution on Ruby 4.0.2: `set("flag", false)` then `get("flag", true)`
returns `true`. `has?("flag")` correctly returns true, so the value is stored -
`@data[key.to_s] || default` is simply the wrong operator.

The `HttpOnly` divergence fails OPEN in Python and PHP: both treat any value
outside their truthy list as "off", so `TINA4_SESSION_HTTPONLY=enabled` silently
ships a session cookie readable from JavaScript. Ruby and Node treat only an
explicit false-ish value as opt-out, which is the safe reading.

## The auth gate

| | python | php | ruby | node |
| --- | --- | --- | --- | --- |
| token sources | header, body `formToken`, session | same | same | same |
| API-key bypass at the gate | yes | **no** | yes | **no** |
| API-key compare at the gate (before) | **`==`** | n/a | **`==`** | n/a |
| `FreshToken` header on a body token | yes | yes | yes | yes |

Both Python and Ruby already shipped a timing-safe `validate_api_key` and then
did not use it in the gate. A plain `==` on a secret returns as soon as two
bytes differ, so response timing leaks the key prefix and the key can be
recovered a character at a time. **Fixed** in both.

Whether the gate should honour an API key at all is two-two and is NOT resolved
here - see ADR-0021.

## Cross-audit: session identity never reaches a cache key

Reported because the caching audit needed the identity half. The response cache
keys on method plus URL with **no header input** in all four, and the session id
lives only in the `Cookie` header. The auth gates populate per-user state
(`request.user`, `req.user`, `env["tina4.auth_payload"]`) and none of it is
folded into the cache key, so on a `@secured()` GET one user's response can be
served to another. Confirmed independently by the caching branch. Verified key construction:
`response:GET:${req.url}` in Node, `cacheKey(method, url)` in PHP and Ruby.

The ruling is NOT to fold identity into the key. An authenticated response is
not stored at all (RFC 9111 s3.5), which needs no identity in the key and avoids
the per-user-key-on-a-shared-backend poisoning surface. That change is owned by
the caching audit (ADR-0020); this audit supplied the identity half and the
reproduction and does not touch the cache.

## Finding 3: strict mode nearly turned an outage into a mass logout

Recorded because it is the most instructive thing in this audit. Adding strict
mode to the Python master introduced a regression that neither Python's own
tests nor my own review caught: `Session._safe_read()` swallows a backend
exception and returns empty, so strict mode read "the store is unreachable" as
"the store does not know this id" and minted a fresh one. During a Redis blip
that rotates the session id on EVERY request - every user logged out, every
stored session orphaned. That is a worse outcome than the fixation strict mode
exists to prevent.

It was caught because the PHP and the Ruby ports BOTH refused to copy it and
said so independently. Neither was told about the other. A port that is allowed
to push back on the master is a real review, and this is what it bought.

The rule now, in all four: an unreachable backend keeps the supplied id and
degrades to an empty session; only a HEALTHY store answering "no such session"
discards the id.

Node turned out to carry the same bug and was fixed in the same pass - it was
found by reading all four side by side after the two ports flagged the fork,
not by a test. Verified by execution against a REAL unreachable Redis (a closed
port), not a double: three consecutive starts with the same supplied id.

| | outage keeps the id | how verified |
| --- | --- | --- |
| python | yes (it rotated; fixed) | real raising handler |
| php | yes | real closed port 59999 |
| ruby | yes | real closed port 59999 |
| node | yes (it rotated; fixed) | real throwing handler |

## Tests

`test_auth_session_contract` in all four, with identical case names:

- session id from cookie cannot escape the session directory
- session id with path separator is rejected and a fresh id minted
- valid generated session id is accepted unchanged
- jwt expired exactly at exp is rejected
- jwt one second before exp is accepted
- jwt non numeric exp is rejected not treated as no expiry
- jwt non numeric nbf is rejected not treated as unconstrained
- basic authorization header is not an authenticated request
- authenticate request api key payload shape is uniform
- route gate api key comparison is timing safe (python, ruby only)
- unknown session id is not adopted
- backend outage does not rotate the session id
- password hash is byte identical across the four frameworks

Every case carries a positive and a negative half. No doubles anywhere: real
`Auth`, real HMAC digests, real filesystem in a real temp directory.

Honest note on which of these were RED before the fix: the traversal, Basic,
API-key-shape and timing-safe cases were genuinely red. The `exp` boundary case
was **already green in Python and Node** - with a float clock, `>` and `>=`
differ only on an exactly integral instant - and **already green in Ruby**,
which had it right. It was red only in PHP, where the integer clock makes it a
full second. It is kept in all four as a conformance test so the boundary can
never drift again.

## Not fixed here

Recorded, with a recommendation, not changed:

1. **The API-key bypass at the route gate.** Two-two split. A capability
   question, not a defect. Escalated.
2. **Ruby's RS256 auto-switch.** A stray `.keys/` directory flips the app to
   RS256 and a `require "jwt"` that is not a declared dependency. Recommend
   deleting the RSA path from Ruby entirely - RS256 is documented as PHP/Node
   only, so Ruby's half-implementation is a trap rather than a feature.
3. **Ruby `Session#get` returns the default for a stored `false`.** One-operator
   fix (`||` to a key check). Small, but a behaviour change.
4. **`all()` hides four different things.** Python hides nothing, Ruby hides
   nothing, PHP hides `_meta` and `_flash_`, Node hides every `_`-prefixed key.
   Python's own CLAUDE.md documents "excludes internals", which is not what the
   code does - doc drift. Recommend Node's rule.
5. **`set()` is lazy in Python/Ruby and eager in PHP/Node.** A write per `set()`
   is a real per-request cost difference, and it changes what `save()` means.
   Recommend lazy.
6. **Session id entropy is 128 bit in PHP/Node and 256 bit in Python/Ruby.**
   Both exceed the OWASP 64-bit floor, so this is parity tidiness, not a defect.
7. **`expires_in=0` means "never expires" in three frameworks and "already
   expired" in Ruby**, which always stamps `exp`.
8. **Redis and Valkey session handler tests in Python were MOCK-BASED**
   (`MagicMock` clients), so those session paths had never been proven against a
   live server - exactly the shape of the MongoDB-queue lesson. FIXED in this
   pass: both now drive a real Redis (6379) and Valkey (6380) through
   mint -> save -> resume -> destroy, and skip loudly naming host and port when
   the service is unreachable. The equivalent mocks in the other three
   frameworks were NOT audited and may still exist.
