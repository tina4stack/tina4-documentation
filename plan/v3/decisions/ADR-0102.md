# ADR-0102: a user-facing raw TCP service runs in-process, with a callback handler model and a connection registry for server→device push

- Status: Accepted
- Date: 2026-11-03
- Context: feature 142 (`plan/v3/features/142-raw-tcp-service.md`), the driving
  consumer (IoT device gateways — GT06/TK103/Concox/Teltonika GPS-GPRS car
  trackers), the zero-dependency mandate, ADR-0004 (best implementation
  prevails), ADR-0019 (write-secure-by-default routing), the WebSocket subsystem
  (the only user-facing realtime surface today). New cross-framework contract.
- Fixture (owed): `plan/v3/fixtures/raw_tcp_service_contract.json`

## Context

All four frameworks speak raw TCP internally — the HTTP server, the HTTP client,
the queue brokers, the cache/session backends, MQTT and the WebSocket upgrade are
all hand-rolled over sockets (tina4-php most of all, because it cannot add a
composer dependency). None of the four exposes a raw TCP LISTENER to application
code. The only user-facing realtime surface an app can open is a WebSocket, which
rides the HTTP upgrade and speaks the WebSocket framing — useless to a device that
speaks a bare binary protocol over a long-lived socket.

The concrete consumer is an IoT device gateway, specifically a GPS/GPRS car-tracker
fleet. That workload has a fixed shape, and the shape is what forces the design:

- **Long-lived** — a tracker opens ONE TCP socket and holds it for hours or days,
  streaming location packets. The opposite of HTTP's short request/response.
- **Login-then-stream** — the first packet is a login carrying the device IMEI;
  every later packet belongs to that device. Per-connection identity is mandatory,
  not a nicety.
- **Binary, length-framed, often CRC'd** — NOT newline-delimited. A line reader
  does not cover it; the app must see raw bytes and frame them itself.
- **ACK-per-packet** — the server typically writes a reply to each inbound packet.
- **Server→device commands** — "set report interval", "locate now", "cut fuel" are
  pushed DOWN to a specific device, addressed by IMEI, from somewhere else in the
  app (an HTTP route an operator clicked). Without a way to reach a specific live
  socket by app-id, the feature can only ingest, which is half a gateway.

The value is that the tracker gateway and its operator dashboard/API run as ONE
Tina4 app: devices ingest on the TCP port, the same ORM/Queue persist and fan out,
the operator UI is ordinary routes — no second stack, no glue process. This is a
niche primitive in the abstract; the car-tracker consumer is what makes it concrete
and justified rather than speculative.

Because this is a new forever-maintained public contract across four languages, it
needs a decision before any code (T4DD, ADR-0099): the handler model, the framing
baseline, identity/push, the connection object, and TLS all have to be ONE shape in
all four or the primitive is not portable.

## Decision

Expose a user-facing raw TCP service. One contract, four implementations, Python the
reference (ADR-0004).

**D1 — It runs IN-PROCESS, folded into each runtime's EXISTING accept/event loop.**
Not a second blocking loop beside the HTTP server, and not a separate daemon by
default:
- **Node** — a `net.createServer` on the same event loop.
- **Python** — an `asyncio.start_server` registered as another task on the server's
  existing event loop.
- **Ruby** — a dedicated acceptor thread, thread-per-connection (the `http_server.rb`
  model).
- **PHP** — the TCP listener fd is folded into `Server.php`'s existing `stream_select`
  read set, so ONE loop serves HTTP and raw TCP in a single process.

**D2 — Handler model: callbacks, not per-connection coroutines.** The app registers
`on_connect(conn)`, `on_data(conn, bytes)`, `on_close(conn)`, and an optional
`on_line(conn, line)` convenience. Per-connection generator/coroutine handlers are
rejected: they are natural only in Python/asyncio and Ruby fibers and do not port to
Node's callback loop or PHP's single `stream_select` process. Callbacks are the
shape all four already use internally and the only one that ports cleanly.

**D3 — Framing: raw `on_data` + an app-owned per-connection buffer is the baseline.**
Tracker frames are binary/length/CRC — the app owns the parser (and may reuse the
ORM/Queue to persist and fan out). `on_line` is a newline convenience for text
line protocols only. v1 ships NO CRC/length-framing helper — that is the app's,
because every device family frames differently and a generic helper would fit none.

**D4 — A connection registry + server→device push is v1 scope, not a follow-up.**
`conn.identify(app_id)` registers the live connection under an app-assigned id (the
IMEI). From anywhere in the app: `tcp(name).send_to(app_id, bytes)` writes to that
device's socket, `tcp(name).connection(app_id)` returns the handle, and
`tcp(name).broadcast(bytes)` writes to all. Without this the feature can only
ingest; tracker command-and-control is the reason it earns its place.

**D5 — A uniform connection object in all four:** `send(bytes)`, `close()`,
`remote_addr` (the raw socket peer, never a forwarded header), `id` (the registry
id once identified), `identify(app_id)`, and `context` — a per-connection state bag
the app uses to hold the IMEI, auth state, and parse buffer.

**D6 — TLS is OUT of scope for v1.** Trackers are mostly plaintext GPRS; an app that
needs TLS fronts the service with a terminator. Revisit in a later feature.

**Non-goals v1:** UDP (many trackers ALSO do UDP — a fast-follow feature, not this
one), framing helpers beyond `on_line`, and replacing WebSocket (the HTTP-adjacent
realtime surface stays what it is).

**Security posture (ADR-0019 alignment):** a raw TCP service is opened explicitly by
the app for a specific protocol — it is not an ambient route surface, so the
write-secure-by-default rule does not transfer mechanically. Identity and
authorization live in the app's own login-packet handling (`on_data` →
`conn.identify`), because only the app can read its device protocol's login frame.
The framework's duty is the socket hard-parts: lifecycle, `max_connections` refusal,
an idle reaper (default OFF, because these connections are deliberately long-lived),
graceful-shutdown drain, and backpressure (a slow/stalled reader must never grow
server memory without bound).

## Consequences

- **Scaling ceiling is per-runtime and is stated, not hidden.** In-process suits the
  common gateway — hundreds to low-thousands of devices. Node and Python/asyncio
  carry many thousands of idle long-lived sockets cheaply; Ruby's thread-per-connection
  is fine to low-thousands but a fleet of 10k idle trackers is a lot of threads; PHP's
  single `stream_select` process is one core. The documented escape hatch at fleet
  scale is to run the SAME `tcp_service` as a dedicated process (identical API) — the
  framework will not pretend one in-process listener serves unlimited trackers on every
  runtime.
- **Multi-worker bind caveat (Python/PHP).** When the HTTP side runs N workers, N
  processes must NOT each bind the TCP port. v1 answer: the listener binds in ONE
  owner (the primary worker); `SO_REUSEPORT` is off by default. This is pinned in the
  fixture and documented, because it is the first thing that breaks under a process
  manager.
- **PHP cost is real.** Folding the fd into `Server.php`'s `stream_select` set is
  genuine surgery on the hottest path in the PHP framework, single-process. It is the
  clean answer (no second blocking loop) but it is the highest-risk of the four and
  will carry the most careful no-mock coverage.
- **New public contract, forever maintained**, in four languages, with a fixture
  (`raw_tcp_service_contract.json`) driving all four runners: listen+accept in-process;
  the three callbacks (+`on_line`); the connection object; `identify` + registry
  (`send_to`/`connection`/`broadcast`); `max_connections` refusal; idle reaper
  (default off); graceful-shutdown drain; backpressure; `remote_addr` is the raw peer.
- **No-mock proof.** Every case exercises a REAL client socket against a REAL listener:
  a binary frame round-trips and is ACK'd; a login registers via `identify` and a later
  `send_to(imei, cmd)` is received by that same client socket and NOT by another; the
  (N+1)th connection past `max_connections` is refused; `idle_timeout=0` keeps a silent
  connection open while `>0` reaps it; SIGTERM drains live connections while HTTP keeps
  serving until the deadline; a stalled reader does not grow server memory without
  bound. Each proven able to FAIL by mutation before it counts.
- **Reversibility.** D6 (TLS) and the UDP non-goal are explicitly deferred, not
  foreclosed — each is a later feature that extends this contract rather than changing
  it. D1 (in-process) is the one hard-to-reverse choice; the dedicated-process escape
  hatch is the pressure valve that keeps it from being a dead end.
