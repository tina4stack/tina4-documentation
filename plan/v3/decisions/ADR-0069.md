# ADR-0069: Identifiers that reach SQL come from the model, never the request

- **Date:** 2026-09-24
- **Status:** Accepted
- **Scope:** AutoCrud list filter and sort (PHP, Ruby, Node), ORM `find()` with a
  filter map (all four), AutoCrud and ORM write keys and the database write
  helpers (all four), the DocStore SQLite fallback's field paths (all four), Ruby's
  HTML CRUD component, and the `TINA4_REQUIRE_SERVICES` test gate (all four).
- **Relates to:** [ADR-0025](ADR-0025.md) (the fallback imitates the driver, and may
  raise where the driver would not), [ADR-0043](ADR-0043.md) (the list envelope),
  [ADR-0004](ADR-0004.md) (parity flows both ways).
- **Fixture:** `fixtures/identifier_allowlist_contract.json`

## Context

A value from a request is always bound as a parameter, and every framework already
does that. A column name can't be bound, so it lands in the SQL text as-is. Three
paths took that column name, or a JSON path, straight from the request:

- **AutoCrud list.** A `?filter[KEY]=value` key and every part of `?sort=` were
  written into the WHERE and ORDER BY clauses. PHP took any key; Ruby and Node
  limited the key to word characters but still took any column of the table,
  declared or not, and quietly dropped a key they couldn't read. Node wrapped the
  sort part in double quotes without escaping it.
- **ORM `find(filter)`.** A filter-map key the model didn't declare fell through
  its field mapping unchanged and was written into `key = ?`.
- **DocStore fallback.** A filter or sort key was written into a single-quoted
  JSON path literal (`json_extract(doc, '$.KEY')`). Operators were already on an
  allow-list, keys were not.

The same shape, three times: the request was choosing an identifier.

## Decision

> **An identifier the framework writes into SQL is chosen by the model's own
> declaration. The request only ever names it, and a name the model doesn't know
> is refused before any SQL is built.**

### AutoCrud list (PHP, Ruby, Node)

A request will first have each `filter[KEY]` key (and Node's `filter[KEY][OP]`)
looked up against the model. The key may be a declared field or that field's
database column, and it will be resolved to the column through the model's own
mapping. Any key between the brackets will be looked up, not only word characters,
so an unknown one is refused rather than dropped. The `sort` value will then be
split on commas, empty parts skipped, a leading `-` read as DESC, anything else as
ASC, and the rest of each part resolved the same way. The ORDER BY will be built
from resolved columns and the literal words ASC and DESC, nothing else.

If a filter or sort name doesn't resolve, the request will be answered with the
framework's standard error envelope, before any query runs:

```
HTTP 400
{"error": true, "code": "UNKNOWN_FIELD", "message": "Unknown filter field 'KEY'", "status": 400}
{"error": true, "code": "UNKNOWN_FIELD", "message": "Unknown sort field 'KEY'", "status": 400}
```

A value of the wrong shape gets the same envelope with its own code, never a 500 and
never an array bound into the driver. If `sort` arrives as anything but one string
(`?sort[]=x`), or a filter value arrives as a list or a nested map (`filter[name][]=1`),
the request will be refused:

```
HTTP 400
{"error": true, "code": "INVALID_QUERY_PARAMETER", "message": "Query parameter 'sort' must be a single comma-separated string", "status": 400}
{"error": true, "code": "INVALID_QUERY_PARAMETER", "message": "Filter value for 'KEY' must be a single value", "status": 400}
```

Node's operator filters (`filter[age][gt]=25`) stay, as long as the operator is one
Node knows. An operator it doesn't know used to be dropped without a word, and it now
gets the same 400.

For a filter, KEY is the key exactly as it arrived between the brackets. For a sort,
KEY is the part with its surrounding space and its leading `-` taken off, so
`?sort=-colour` is reported as `'colour'`.

The resolved column is written the way that framework's ORM already writes column
names for its own INSERT and UPDATE: through the adapter's own identifier quoting in
Python (`quote_identifier()`) and Node (`quoteIdentifier()`), bare in PHP and Ruby.
The adapter knows its engine, so MySQL gets backticks and Firebird gets the
upper-cased name it actually stored. A new quoting style in PHP or Ruby would change
case folding on Firebird and PostgreSQL and would trip PHP's MongoDB SQL translator,
and it buys nothing once the allow-list decides which names can arrive.

Node's ORM used to write every identifier in double quotes whatever the engine. On
MySQL that's a string literal, and on Firebird it's a lower-case name the table
never had, so BaseModel queries failed on both engines before this change. Node now
takes its identifier quoting from the adapter, the way Python already did. Raw SQL
a developer writes is never rewritten.

Two PHP-only details:

- A PHP model can declare no fields at all and take every column dynamically. That
  model's allow-list is the table's real columns, read once through
  `getColumns()` and compared without regard to case.
- PHP ignored `?sort=` when no filter was given. It now sorts either way, as Ruby
  and Node already did.

Ruby's HTML CRUD component (`Tina4::Crud.to_crud`) read `?sort=` the same way, in
both its model mode and its SQL mode. The other three have no server-side sort in
their CRUD component. In model mode the sort will be resolved exactly as above. In
SQL mode it must name a column of the query's own result set. An unknown sort there
falls back to the default primary-key sort, because the component renders a page
rather than answering an API call, and the ORDER BY is still only ever built from a
resolved column.

Python's AutoCrud has no filter or sort parameter today. It isn't added here. If it
is added, this contract is the one it will implement.

### AutoCrud id routes (all four)

`GET`, `PUT` and `DELETE /api/{table}/{id}` will look the row up by its primary key,
with the id bound as a value. PHP passed the id to `load()`, which reads a string
argument as a WHERE fragment, so the id became SQL text. A request for one id could
then load, change or delete a different row. PHP now goes through the bound
primary-key path the other three already used. An id that matches no row gets a 404
and nothing changes. PHP's GraphQL schema built from an ORM model did the same with
its `id` argument, in the single-row query and the update and delete mutations. It
now takes the same bound path.

### ORM `find(filter)` (all four)

`find()` with a filter map will resolve every key with the same resolver AutoCrud
uses. An unknown key will raise the language's own invalid-argument error
(`ValueError`, `InvalidArgumentException`, `ArgumentError`, `Error`) naming the key
and the model, before any SQL. This is the second wall: AutoCrud refuses first, and
application code calling `find()` with a request's keys is refused too.

The documented raw-SQL surfaces are unchanged: `where()`, `load(filter_sql)`,
`select()`, the query builder, and the `order_by` string argument, which is
documented as a raw ORDER BY clause.

### Write keys (all four)

The same rule holds on the way in. A POST or PUT body on AutoCrud will be matched
against the declared fields through the same resolver, and a key that doesn't
resolve will be dropped. Writes drop and reads refuse, which is the split
CRUD-DEC-02 already set. PHP's deny-list becomes that allow-list. A PHP model with no
declared fields takes the table's real columns, as it does for reads.

`save()` writes only declared fields. If PHP code sets a property the model doesn't
declare, it won't reach the column list, unless the model declares nothing and that
name is a real column of its table.

The database write helpers (`insert`, `update`, `delete` and their batch forms) take
a map from the caller. Any key in the data or the filter map must be a plain
identifier, `^[A-Za-z_][A-Za-z0-9_$]*$`. Anything else raises "Invalid column name
'KEY'" before SQL is built. How a valid name is written doesn't change, so no engine
sees a new case-folding rule. Python's `quote_identifier()` passed a name that
wasn't an identifier straight through, and Node's double-quoting didn't escape. The
refusal closes both.

### DocStore fallback (all four)

Every field path the SQLite fallback turns into SQL will be split on `.`, and every
segment must match `^[A-Za-z0-9_-]+$`. That covers filter keys at any depth
(including inside `$or` and `$and`), operator fields, and sort keys. The check sits
at the one place a path is built, so no call site can step around it. A path that
fails will raise before any SQL:

```
DocStore: invalid field path 'KEY' - each dot-separated segment must match [A-Za-z0-9_-]+
```

The MongoDB provider hands back the real driver collection, and it stays that way.
ADR-0025 costed wrapping the driver and turned it down. What we prove instead,
against a real MongoDB, is that every key shape the fallback accepts returns the
same documents on both providers, and that a key it refuses raises on the fallback.
That is ADR-0025 corollary 4 as written: a query matches on both providers, "or the
fallback raises rather than silently returning nothing".

### The test gate that proves it

The contract tests only prove something if they run. Under `TINA4_REQUIRE_SERVICES=1`,
each framework's gate used to fail a skip whose reason contained certain words. A
reason worded "no reachable ..." or "... unavailable" slipped past and skipped green.
The gate now reads a tag, never a phrase, and it's the same rule in all four
frameworks:

- A skip passes only if its reason carries `[needs:X]` and X can be excused in this
  run. An untagged skip fails.
- An optional engine is excused only while its coordinate is unset:
  - `firebird` - `TINA4_TEST_FIREBIRD_URL`
  - `postgres` - `TINA4_TEST_PG_URL`, and only that spelling, because ADR-0038's
    test-environment contract retired `TINA4_TEST_POSTGRES_URL`
  - `mysql` - `TINA4_TEST_MYSQL_URL`
  - `mssql` - `TINA4_TEST_MSSQL_URL`
  - `swoole` - `TINA4_TEST_SWOOLE`
  - `oidc` - `TINA4_TEST_OIDC_ISSUER`
  - the graph engines - `TINA4_TEST_<ENGINE>_URL`
  - `postgis` - `TINA4_TEST_POSTGIS_URL`
- A service every gated run provisions is never excused: mongo, redis, valkey,
  memcached, rabbitmq, kafka, mqtt, smtp, imap, s3.
- Any other tag names a platform limit (`absent-ext=...`, `os=...`,
  `no-dac-override`) and is always excused.

A continuous integration (CI) job that never promised Firebird stays green. The lab
sets every coordinate, so a missing engine there fails.

## Consequences

- A client sending a filter or sort name the model doesn't declare now gets a 400
  where it used to get rows, an unfiltered list, or a driver error. That is the
  point of the change.
- Code that filtered by an undeclared column through `find()` will now raise. It
  should declare the field, or use `where()` with its own SQL.
- A write body key the model doesn't declare is dropped, and a map key that isn't a
  plain identifier makes `db.insert()`, `db.update()` or `db.delete()` raise.
- Node's `buildQuery()` now needs the resolver from the model. Called without one, it
  refuses every filter and sort key, which breaks any outside caller that relied on
  raw keys.
- A document key with characters outside the segment set can still be stored and
  read back whole, it just can't be queried or sorted on the fallback.

## Alternatives rejected

- **Quote every identifier, skip the allow-list.** Quoting hides a name, it doesn't
  choose it. A request could still pick any real column the model never meant to
  expose, and quoting changes case folding on two engines.
- **Validate the characters only (`\w+`).** Ruby and Node already did this. It keeps
  the SQL well-formed and still lets a request name a column nobody declared.
- **Wrap the MongoDB driver so both providers refuse the same keys.** Rejected by
  ADR-0025 for the reasons it records. MongoDB has no SQL text to escape from, so
  the refusal only has to happen where SQL is built.
