# ADR-0072: A Content-Type set with header() is the one Content-Type; settings are read when they are used

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release
Builds on: ADR-0068 (response header validation, limit-variable fallback)

## Context

Two reports against tina4-python, both reproduced on `origin/v3` of all four
frameworks on 2026-09-24 with real servers.

**tina4-python#144.** `response.header("Content-Type", "image/png")` followed by
`response(png_bytes)` sent two Content-Type headers, `application/octet-stream`
and `image/png`. With `X-Content-Type-Options: nosniff` a browser may refuse to
render the image. The other three were wrong in different ways:

| Route | Python | PHP | Ruby | Node |
| --- | --- | --- | --- | --- |
| `header("Content-Type", "image/png")` + bytes | two headers | header lost (text/plain) | Puma: two headers | kept |
| `header("content-type", "image/png")` + bytes | two headers | two headers | header lost (text/html) | kept |
| `header("Content-Type", "text/csv")` + `"a,b"` | two headers | header lost | Puma: two headers | header lost (text/plain) |
| header, then an explicit type argument | two headers | argument | Puma: two headers; WEBrick: header wins | argument |

The causes were the same shape everywhere: `header()` stored Content-Type as an
ordinary header, under whatever key case the caller used, while `response(data)`
wrote its detected type to the framework's own key.

**tina4-python#143.** `TINA4_MAX_UPLOAD_SIZE` set in `.env` was ignored. Python
read it into a module constant when `core/request.py` was imported, and `run()`
loads `.env` later, so the constant kept the 10MB default. A project that lowered
the limit accepted bigger bodies than it asked for; one that raised it still got
413 at 10MB. Node had the same constant in `request.ts`, evaluated before
`startServer()` loads `.env`. PHP (App's constructor loads `.env` before the
server reads its limits) and Ruby (`max_upload_size` reads the environment per
call) honoured `.env` already.

A scan for every environment read that runs at load time (a Python AST walk, a
Ruby Prism walk, a TypeScript compiler walk, and a grep of PHP's top-level code)
found one more: Python registered the health route under `TINA4_HEALTH_PATH` at
import, so a path set only in `.env` was never served. Nothing else in any
framework reads a setting at load time.

The same code paths also mishandled a bad limit value. Python's `int()` raised at
import. Node's `parseInt` gave `NaN`, and a `NaN` cap refuses nothing. Ruby's
`to_i` and PHP's `(int)` cast gave `0` (or a negative number), and a zero cap
refuses every request with a body. ADR-0068 section 3 already says a limit
variable that isn't a usable number falls back to its default with a warning.

## Decision

### 1. `header()` with Content-Type sets the response's one content type

`header()` (and each framework's aliases: `add_header`, `addHeader`,
`withHeaders`, Python's one-shot `headers=`) compares the name
case-insensitively. For `Content-Type` it replaces the content type instead of
adding a header, so a response carries exactly one Content-Type whatever case the
caller wrote.

`response(data)` keeps a content type set that way. Detection (JSON for a
dict/array, HTML or plain text for a string, `application/octet-stream` for bytes
where the language has a bytes type) fills in only when the route didn't set one.

A later explicit choice still replaces it: the content-type argument of
`response(data, status, type)`, and the explicit helpers (`json()`, `html()`,
`text()`, `xml()`, `file()`, `render()`, `stream()`). The rule is "the developer's
explicit choice wins over the framework's guess", not "header() wins over
everything".

### 2. A setting is read when it is used, never at load time

No framework reads an environment variable into a module constant, a class
constant or a route table while its code is being loaded. `.env` is loaded by the
framework's boot (`run()`, `startServer()`, `App::__construct`,
`Tina4.initialize!`), which runs after the framework's own modules are loaded.

- `TINA4_MAX_UPLOAD_SIZE` is read per request (Python `max_upload_size()`, Node
  `maxUploadSize()`, Ruby `Tina4::Request.max_upload_size`, PHP per request in
  `Request` and at server construction in `Server`).
- Python moves the health route to `TINA4_HEALTH_PATH` right after `run()` loads
  `.env`, keeping the route's slot in the route table so an application
  catch-all still can't shadow it, and `/health` stays registered (ADR-0016).
- A limit value that isn't a positive whole number uses the default and warns
  once, per ADR-0068 section 3. (PHP's `Request` falls back without a warning of
  its own; the built-in server's `resolveLimit` already warned at boot.)

## Test contract

Every case runs against a real server booted from a project whose `.env` carries
`TINA4_MAX_UPLOAD_SIZE=1000` and `TINA4_HEALTH_PATH=/healthz-from-dotenv`, with
those variables removed from the process environment, over a real loopback
socket, with repeated headers read raw. Ruby runs the cases on Puma and on
WEBrick. No mocks.

| Case | Python | PHP | Ruby | Node |
| --- | --- | --- | --- | --- |
| header content type replaces the detected type | red → green | red → green | red → green | green (lock-in) |
| a lowercase content type header is the same header | red → green | red → green | red → green | green (lock-in) |
| header content type survives a string body | red → green | red → green | red → green | red → green |
| an explicit content type argument wins over the header | red → green | green (lock-in) | red → green | green (lock-in) |
| without a header the detected type is used | negative | negative | negative | negative |
| max upload size from dotenv is enforced | red → green | green (lock-in) | green (lock-in) | red → green |
| a body under the dotenv limit is accepted | negative | negative | negative | negative |
| health path from dotenv is served | red → green | green (lock-in) | green (lock-in) | green (lock-in) |
| max upload size follows the environment | new helper | green (lock-in) | green (lock-in) | new helper |
| a bad max upload size falls back to the default | red → green | red → green | red → green | red → green |

Suites: Python `tests/test_dotenv_settings_and_content_type.py`, PHP
`tests/DotenvSettingsAndContentTypeTest.php`, Ruby
`spec/dotenv_settings_and_content_type_spec.rb`, Node
`test/dotenvSettingsAndContentType.test.ts`.

Mutation proof: take out the Content-Type branch in `header()` and the header
cases go red; let detection ignore the header and they go red; freeze the upload
limit at load time and the `.env` upload case goes red; skip Python's health
re-application and the health case goes red; restore the old cast and the bad
value case goes red.

## Consequences

- A route that set Content-Type with `header()` and relied on `response(data)`
  replacing it now keeps its own type. Nothing in the four frameworks' own code
  did that; a route that wants the detected type shouldn't set one.
- In Python the Content-Type no longer appears in the response's extra-header
  list; it lives in `content_type`, the one place the transport reads.
- `TINA4_MAX_UPLOAD_SIZE` in `.env` now works in Python and Node, so a project
  that set it there gets the limit it asked for, which may be lower or higher
  than the 10MB it was silently running with.
- Python's `from tina4_python.core.request import TINA4_MAX_UPLOAD_SIZE` still
  works and returns the current value; new code calls `max_upload_size()`.
- Ruby's `Tina4::Request::TINA4_MAX_UPLOAD_SIZE` is now the plain 10MB default,
  not the value of the environment at require time.

## Related

- **ADR-0068**: header validation at the call site; limit variables fall back to
  their default with a warning.
- **ADR-0016**: the health path is only ever added; `/health` is always there.
