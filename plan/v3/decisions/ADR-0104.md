# ADR-0104: an unclosed Frond `{% block %}` fails loud, superseding ADR/issue-271's silent leniency, while staying bounded against the hang

- Status: Accepted
- Date: 2026-11-05
- Supersedes: the "render a string, do not raise" contract from tina4#271
- Context: tina4-python#286 and #290 (both found in AI-agent evals; a child
  template whose `{% block %}` is never closed, or whose last `{% endblock %` is
  cut short so its `%}` is missing, rendered an empty block and served 200).
  tina4#271 (the prior fix that stopped an infinite-loop hang by making the
  block scanner lenient). Cross-framework contract change.

## Context

tina4#271 fixed a real hang: a malformed/unclosed `{% block %}` sent the
block-extraction scanner into an infinite loop. The fix made the scanner
**lenient** - on an unclosed block it stopped scanning and returned whatever it
had, so the render completed with that block **empty**. All four frameworks grew
a regression guard asserting the malformed template "must RETURN, not hang, not
raise".

That leniency is itself a trap. A single missing character (`{% endblock %}` ->
`{% endblock %`, or no endblock at all) silently drops a whole page body: the
page serves 200 with its layout and none of the block's content, and nothing in
the log points at the cause. In the reporting evals this happened in 2 of 5 runs
- the model's template held the right words, the page never showed them, and
nothing said why. Twig itself raises "Unexpected end of template" here.

The two issues are the same defect: `{% endblock %` (no `}`) is not matched by
the close-tag pattern, so the scanner sees the block as never closed, exactly
like `{% block %}` with no end at all.

## Decision

An unclosed `{% block %}` **fails loud**. The block scanner raises a clear
template error naming the open block, rather than silently rendering it empty:

- Python raises `tina4_python.frond.TemplateSyntaxError`.
- PHP raises `Tina4\FrondSyntaxError` (extends `\RuntimeException`).
- Ruby raises `Tina4::FrondSyntaxError` (extends `StandardError`).
- Node throws `FrondSyntaxError` (exported from `@tina4/frond`).

The message names the block, e.g. `{% block content %} is never closed (missing
or malformed {% endblock %})`. In debug mode the route answers 500 with that
message through the normal error path; in production the generic 500 applies and
the cause is logged (unchanged dispatch behaviour).

This deliberately **reverses tina4#271's "do not raise"** decision. It does
**not** reintroduce the hang: the scanner raises instead of looping, so it is
still bounded. The #271 regression guard in every framework is rewritten to
assert "raises AND stays bounded (no hang)", keeping the anti-hang protection
(a reintroduced loop trips the test's timeout) while locking the new fail-loud
contract.

Rationale accepted from the maintainer: fail loud for AI. An agent (or a
developer) must see the real cause, not a quietly half-rendered page.

## Consequences

- BREAKING for any template that relied on an unclosed block rendering empty.
  That was never intentional behaviour (it was #271's hang-avoidance side
  effect), so no real template should depend on it; a malformed template now
  raises at render instead of serving a blank section.
- A new public error type per framework, exported so application code and the
  dispatch layer can catch it.
- Proven by the rewritten #271 regression guard in all four frameworks, each
  mutation-proved (reverting the raise turns the guard red). Well-formed
  inheritance is unchanged and still covered.
