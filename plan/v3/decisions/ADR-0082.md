# ADR-0082: Credentials and development endpoints retain explicit trust boundaries

- **Status:** Accepted for the security release under maintainer-delegated approval
- **Date:** 2026-09-24
- **Scope:** Python, PHP, Ruby and Node.js backends
- **Decision owner:** Andre van Zuydam (release approval delegated in this task)
- **Clarifies:** ADR-0049 trusted proxy handling, ADR-0069 identifier boundaries and DEVADMIN-DEC-01
- **Supersedes in part:** DEVADMIN-DEC-01's mutation-only gate; the development access boundary also applies to reads

## Context

The release review found that initial absolute API targets could receive credentials
bound to another origin, although redirect handling already restricted them.
Request URL construction also accepted forwarded host information independently
of the trusted-proxy decision. Development routes capable of reading local files
need the same access boundary as routes which write them. These are security fixes;
they do not adopt the separate async database redesign or other pending feature PRs.

## Decision

1. Apply the HTTP client's origin policy to the final initial target as well as
   redirects. After all default and per-call header merges, an off-origin target
   must receive neither Authorization nor Cookie credentials bound to the configured
   client origin. This is case-insensitive and includes cookie-jar injection,
   uploads, downloads and streaming paths. Same-origin credentials still work.
   An application intentionally authenticating to another service uses a client
   bound to that service's origin. Do not infer trust from a hostname prefix.
2. Trust forwarded host and protocol only when the actual transport peer satisfies
   the existing trusted-proxy policy. Use the raw peer for that decision, never
   an address supplied by forwarded headers. Untrusted forwarded values cannot
   change the request's authority or scheme.
3. Apply the development endpoint boundary to GET, HEAD and OPTIONS as well as
   mutations. Combine the raw-peer restriction, an allowed Host and browser origin
   checks; same-site alone is not same-origin. Remote access to non-MCP development
   routes requires the dedicated development/MCP token, not the general application
   API key. Invalid host or origin checks must not be bypassed by that token.
4. Preserve the separately documented MCP transport API_KEY fallback in features
   101, 103 and 127. This release does not claim to revoke that existing MCP
   contract globally. It narrows authorization of non-MCP development routes.
5. Resolve and confine development filesystem targets before checking sensitive
   paths. Reject secret files and directory-boundary escapes, including symlinks
   and sibling-prefix paths. Database identifiers selected through development
   endpoints must satisfy the existing identifier policy and be quoted correctly.
6. Keep the /health version contract unchanged. Containers must report the exact
   released version so the publication gate can verify what is running.

## Evidence and compatibility

Each backend must retain real HTTP/dispatch and filesystem regressions for accepted
and refused requests. Cross-origin requests must be observed at a separate real
listener without transmitting real credentials. Proxy tests cover both an untrusted
peer and an explicitly trusted peer, and both host and protocol. Development tests
must traverse the real gate and witness denied access or the absence of a write.

Applications relying on credential forwarding to another origin must bind a separate
client to that origin. Remote development access must use the dedicated token and
allowed host configuration. These changes intentionally tighten the security boundary;
they are not a new production authentication system or an ISO certification claim.

The named regression cases are mapped in `security_boundaries_contract.json` and
`devadmin_contract.json`. Focused security suites pass in all four implementations;
the fixture audit reports 367 mapped invariants, 40 owed and zero broken across the
repository. That audit checks named coverage, not execution. Exact final-head full
lab verification remains a separate release gate and is pending lab access.

The API suites are `test_api_cross_origin_token.py`, `ApiCrossOriginTokenTest.php`,
`api_cross_origin_token_spec.rb` and `apiCrossOriginToken.test.ts`; proxy and dev
surface suite paths are recorded in the fixtures. Positive cases retain same-origin
credentials and permitted development access; negative cases observe stripped
credentials at real listeners and refused dispatch or filesystem access.
