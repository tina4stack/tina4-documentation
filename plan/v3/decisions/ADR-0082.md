# ADR-0082: Outbound auth is same-origin only; X-Forwarded-Host is trusted only behind a trusted proxy

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4-python, tina4-php, tina4-ruby, tina4-nodejs (the `Api` HTTP client and the `Request` URL builder)
- **Decision owner:** Andre van Zuydam
- **Governs fixture:** `plan/v3/fixtures/trust_boundary_headers_contract.json`
- **Extends:** ADR-0019 (the trusted-proxy allow-list keyed on the raw socket peer)

## Context

Two findings from the September 2026 Medium security audit concern the boundary
between data the framework controls and data an untrusted party supplies through
a header or a request path. They are recorded here at the level of the contract;
the exploit detail lives with the fixes, not in this log.

1. **F5 — the outbound `Api` client leaked its configured credentials to another
   host.** The client already stripped the `Authorization` (and cookie-jar
   `Cookie`) header when a *followed redirect* crossed to a different origin. It
   did not apply the same rule to the *initial* request target: a request path
   that was itself an absolute, off-origin URL (including the userinfo form
   `base@evil/x`, which resolves the host to `evil`) reused the configured
   credentials and sent them to the attacker-chosen host.

2. **F6 — `X-Forwarded-Host` was trusted from any peer when building
   `request.url`.** The absolute request URL the framework exposes (the base for
   password-reset links, cache keys, and open-redirect targets) was built from
   `X-Forwarded-Host` sent by whoever connected. `X-Forwarded-For` was already
   gated on the trusted-proxy allow-list (ADR-0019); the host header was not.

## Decision

Both are settled the same way — a value only crosses the trust boundary when its
source is trusted — identically in all four frameworks.

1. **Outbound credentials are same-origin only.** The `Api` client attaches the
   configured `Authorization` and cookie-jar `Cookie` headers **only when the
   resolved request target is same-origin (scheme + host + effective port) as the
   configured base URL.** This is the same cross-origin strip already applied to
   followed redirects, now applied to the initial request target as well. A path
   that resolves to a different origin still executes, but carries no configured
   credentials. Each framework reuses its existing same-origin helper
   (`_same_origin` / `sameOrigin` / `same_origin?`).

2. **`X-Forwarded-Host` is honoured only behind a trusted proxy.** When building
   the absolute `request.url`, `X-Forwarded-Host` is consulted **only when the
   raw socket peer is a trusted proxy** under `TINA4_TRUSTED_PROXIES` — the exact
   gate ADR-0019 already applies to `X-Forwarded-For`. Otherwise the host comes
   from the connection's own `Host` (falling back to the server name), never from
   a forwardable header. The scope of this decision is `X-Forwarded-Host` only;
   the `X-Forwarded-Proto`/scheme contract is unchanged.

Neither knob is new configuration: F5 needs none, and F6 reuses the existing
`TINA4_TRUSTED_PROXIES`. An operator who terminates at a declared proxy sees no
behaviour change; an operator with no declared proxy now gets the connection's
own host, which is the safe default.

## Consequences

- A caller that deliberately points `Api` at a second origin must set that
  origin's credentials explicitly on a client configured for it; the base
  client's credentials are never forwarded off-origin. This matches
  requests/httpx behaviour and is the intended break.
- Deployments behind a reverse proxy MUST list the proxy in
  `TINA4_TRUSTED_PROXIES` for `request.url` to reflect the external host, exactly
  as they already must for the client IP. This is called out in the upgrade
  notes.
- Each fix ships with a red-first regression test in all four frameworks (a
  negative case proving the leak/forgery is closed and a positive twin proving
  same-origin credentials and trusted-proxy forwarding still work).
