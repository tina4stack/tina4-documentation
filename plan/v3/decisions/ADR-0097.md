# ADR-0097: Zero dependency governs WASM adoption — browser-side yes, a backend runtime no by default, the parity engine behind a spike

- Status: Proposed
- Date: 2026-10-15
- Deciders: maintainer
- Supersedes: none
- Related: ADR-0002 (metrics engine lives in the Rust client), the Feature 36 security-header set (COOP shipped 2026-10-15); the plan at [plan/v3/WASM-PLAN.md](../WASM-PLAN.md)

## Context

WebAssembly (WASM) keeps being proposed as a way to make Tina4 faster, to run its
logic at the edge, and — most seductively — to end cross-language drift by
compiling one pure component once and calling it from all four frameworks. That
last idea aims straight at Tina4's deepest maintenance cost: the same pure logic
reimplemented four times and kept in step by contract fixtures. The `?`→`%s`
placeholder translator drifted exactly this way (tina4-python#138, re-surfaced in
#227); the Mongo SQL provider exists four times.

But a WASM *runtime* is itself a dependency, and Tina4's whole promise is zero
runtime dependencies. The runtime cost is not uniform:

- **Node** ships WASM in the engine — free.
- **Python** needs `wasmtime-py` (or `wasmer`).
- **PHP** needs an extension (`wasmer-php`) or an FFI shim.
- **Ruby** needs a `wasmtime` gem.

So any WASM decision collides with the zero-dependency promise in three of the
four backends, and the collision must be decided deliberately rather than drifted
into.

The forcing trace for the parity-engine idea specifically:

- To **kill** drift, the WASM module must be the ONLY implementation — which
  forces a WASM runtime into Python, PHP and Ruby and breaks zero dependency.
- To **keep** zero dependency, the four native implementations stay and WASM is an
  opt-in fast path — but then nothing is deleted; WASM is a fifth implementation
  to keep in sync, so drift is not killed, it is widened.

Either the promise breaks or the drift stays. The idea does not survive the
constraint as stated.

## Decision

Zero dependency is the governing constraint for WASM, and it sorts WASM use into
three standing positions:

1. **Browser-side WASM is endorsed and carries no backend dependency.** The app
   brings its own `.wasm`; Tina4's only job is to serve the isolation headers that
   unlock it. COOP shipped 2026-10-15 (`TINA4_COOP`, default
   `same-origin-allow-popups`); a `TINA4_COEP` opt-in (default unset) completes
   `crossOriginIsolated` for apps that want `SharedArrayBuffer` / WASM threads.
   This is the recommended first and primary investment.

2. **A backend WASM runtime is NOT adopted by default.** No framework gains a
   mandatory WASM-runtime dependency. The Rust client may target `wasm32` for its
   pure analysers (metrics engine, SQL grammar, language detector) because that is
   the client, not the four frameworks, and changes no framework's dependency
   footprint.

3. **The parity engine is a time-boxed spike behind an explicit go/no-go gate,
   never a commitment.** A Rust→`wasm32` build of one pure component (the SQL
   translator) is wired into Node only (where WASM is free) and measured against
   the cost of a fifth implementation plus a runtime dependency. It extends to
   Python/PHP/Ruby ONLY if the Node pilot shows a genuine maintenance reduction
   AND an acceptable dependency story for the other three. The predicted outcome
   is no-go on zero-dependency grounds; the spike exists to settle the argument
   with data and record the result here.

## Consequences

- Phase 1 (browser compute) can be scheduled now; it is additive and breaks
  nothing. The `TINA4_COEP` knob lands in all four frameworks with a Feature 36
  contract case, exactly as COOP did.
- Native, fixture-governed parity remains the mechanism that keeps the four
  frameworks honest. WASM does not replace it, and the contract fixtures stay the
  source of truth.
- A future proposal to make any framework depend on a WASM runtime must supersede
  this ADR explicitly, with the maintenance-reduction evidence the spike was
  designed to produce.

## Alternatives rejected

- **Make a WASM module the single implementation of a pure component (kills
  drift).** Rejected by default: it breaks zero dependency in Python, PHP and
  Ruby. Re-openable only via the Phase 3 spike's evidence.
- **Ship WASM as an opt-in accelerator alongside the four native
  implementations.** Rejected as a standing goal: it adds a fifth implementation
  to synchronise without deleting any, widening the very drift it claims to fix.
- **Run the backend itself on WASM (php-wasm, Pyodide, ruby.wasm).** Parked: each
  runtime's build is large and it fights "Simple."
