# ADR-0048: CORS keeps deny-by-default; wildcard-credentials and per-origin warnings change

Date: 2026-08-10
Status: Proposed
Supersedes: the silent wildcard-plus-credentials fallback and the
per-distinct-origin warning clauses of ADR-0018. ADR-0018's deny-by-default,
204-on-denial and allow-list `Vary` decisions remain; ADR-0013 (a preflight
carries `Allow`) is unchanged. Full contract: `features/033-cors-middleware.md`.

## Context

ADR-0018 denied by default and stated the wildcard must never pair with
credentials, but the shipped code warned and silently dropped credentials, and
logged one warning per denied origin. The re-audit (feature 33) found that
attacker-chosen origins therefore grew an unbounded ledger and log, that PHP
never enabled CORS in a normal application, that Python froze policy before
`.env` loaded, and that `Access-Control-Expose-Headers` did not exist.

## Decision

- A wildcard origin combined with credentials FAILS startup (supersedes warn and
  drop), per Feature 1's fail-outright principle.
- Denial diagnostics are bounded: no per-origin ledger and no per-origin warning;
  optional bounded sampling only, and the origin value is never retained.
- One immutable `CorsPolicy` is resolved after Feature 1 loads env; six typed
  `TINA4_CORS_*` keys are validated at startup.
- `Access-Control-Expose-Headers` is added (default `X-Request-ID`).
- The Fetch preflight predicate (OPTIONS + Origin + Access-Control-Request-Method)
  is canonical, and the final response-unwind stage owns every `Access-Control-*`
  field so a handler cannot override policy.

## Consequences

- Applications pairing `*` with credentials now fail to boot; PHP gains automatic
  CORS in a normal application.
- The behavior is gated by `cors_contract.json` and four thin runners in the
  build phase.
