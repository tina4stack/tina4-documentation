# ADR-0077: Frond escapes by default; trusted output is a SafeString type only

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4-python, tina4-php, tina4-ruby, tina4-nodejs (the Frond template engine)
- **Decision owner:** Andre van Zuydam
- **Governs fixture:** `plan/v3/fixtures/frond_expression_{corpus,expected}.txt`
  (the shared byte-identical corpus, extended with the `esc-*` cases)

## Context

Frond auto-escapes template output so that a value placed in `{{ ... }}` is safe
in HTML by default, and a developer opts out only with an explicit `raw`/`safe`
filter. An audit of the four implementations found several places where that
promise did not hold. They are described here at the level of the contract; the
exploit detail lives with the fix, not in this log.

1. **PHP marked trusted output with an in-band marker string.** PHP prepended a
   fixed byte sequence to a value to mean "already safe", and the output layer
   treated any value containing that sequence as raw. A user value that happened
   to contain those bytes was therefore emitted unescaped. Python, Ruby and Node
   already used a real `SafeString` type and did not have this problem.
2. **A filter applied after `e`/`escape`/`raw` kept the safe flag.** In PHP and
   Node, `replace`/`format`/`join` run after an escape filter produced output
   that was still marked safe, so the transformed (attacker-influenced) string
   went out unescaped.
3. **`data_uri` marked a client-supplied media type as raw.** A caller-controlled
   `type` field could break out of the attribute the data URI was placed in.
4. **Lists, dicts and objects were not escaped.** Python, Ruby and Node escaped
   only plain strings on output, so a structured value carrying markup rendered
   raw. PHP already escaped them.
5. **`js_escape` was marked safe but left `<`, `>`, `&`, `/` and quotes intact**
   in all four, so its output could still break out of a `<script>` block or an
   HTML event attribute.
6. **The sandbox was bypassable.** PHP invoked a function named by a data string
   (`is_callable`), Python reached the object graph through dunder attributes,
   Python/Ruby/Node let `{% set %}`, `{% for %}` and `{% if %}` read a variable
   outside the allow-list, Ruby called any zero-argument method, and Node reached
   an inherited prototype method (the `Function` constructor).
7. **`e('js'|'url'|'css'|'html_attr')` ignored the strategy** and HTML-escaped
   instead.
8. **`json_encode` does not escape `"`.**

## Decision

1. **Trusted output is carried only by a real `SafeString` type**, never by an
   in-band marker string. PHP adopts the `SafeString` class the other three
   already use, and every producer (`e`, `raw`, `safe`, `nl2br`, `json_encode`,
   `data_uri`, `js_escape`, macro output, `set` blocks, `dump`, form tokens,
   template inheritance) returns a `SafeString`. A value is emitted verbatim if
   and only if it is a `SafeString`. User data can no longer forge the raw flag.

2. **Escaping is decided at the output boundary from the value's type, not a
   persistent flag.** A filter that transforms a `SafeString` returns a plain
   string, which is escaped at output. `e`/`escape` therefore no longer set a
   standing "safe" flag; only `raw`/`safe` (and a value that is already a
   `SafeString`) suppress escaping.

3. **Auto-escaping covers every non-`SafeString` value**: a plain string is
   HTML-escaped, and a list/dict/object is escaped on its rendered string form.
   `null`, booleans and numbers render through the existing output contract and
   carry no HTML-significant characters, so they are unchanged.

4. **`data_uri` confines a client-supplied media type** to a strict
   `type/subtype` grammar and falls back to `application/octet-stream` otherwise.

5. **One escape strategy per name, shared by `js_escape` and `e(strategy)`,
   byte-identical across the four frameworks** (Twig-compatible):
   - `js` — every character outside `[A-Za-z0-9,._]` becomes `\xHH` (a single
     byte) or `\uHHHH` (a UTF-16 code unit; an astral character emits a surrogate
     pair). This neutralises `<`, `>`, `&`, `/` and both quotes, so the output is
     safe in a `<script>` block and in an HTML event attribute. `js_escape` is
     this strategy.
   - `url` — RFC-3986 `rawurlencode`: the unreserved set stays, everything else
     is percent-encoded.
   - `css` — every character outside `[A-Za-z0-9]` becomes `\HHHHHH ` (six hex
     digits, space-terminated).
   - `html_attr` — every character outside `[A-Za-z0-9,.\-_]` becomes `&#xHH;`.
   - `html` (the default) — HTML entity escaping.
   An **unknown strategy raises**, so a typo can never silently pass a value
   through unescaped.

6. **The sandbox allow-list governs every variable read.** A whole expression is
   gated — output, `if` conditions, `set` right-hand sides and `for` iterables
   alike — so none can smuggle a blocked variable. An expression that reaches for
   a dunder / prototype / constructor attribute is refused. A string in template
   data is never invoked as a function (PHP calls only a real closure the
   application placed in the context); an object method call reaches only a
   public, own, non-reflection accessor (Ruby and Node block reflection,
   metaprogramming and process-control methods; Node additionally cannot reach an
   inherited prototype method).

7. **`json_encode` keeps its current bytes and is documented, not changed**
   (clause below). It escapes `<`, `>`, `&`, `'`, U+2028 and U+2029 as `\uXXXX`,
   which makes it safe inside a `<script>` block and inside a single-quoted HTML
   attribute, but it does **not** escape `"`. This matches Twig's `json_encode` /
   Jinja2's `tojson`: the output is JSON that is also valid JavaScript, and the
   quote is left so the JSON stays readable. It is therefore **unsafe inside a
   double-quoted HTML attribute**; use a single-quoted attribute or `e('html_attr')`
   there. Changing it to escape `"` would break byte-parity with Twig and with
   every existing template that inlines JSON into a `<script>` block, for a case
   the documented guidance already covers, so the bytes stay and the safe
   contexts are documented.

Normal templates are unchanged: the shared `frond_expression` corpus renders
byte-identically before and after, and it is extended with `esc-*` cases that
lock the js/url/css/html_attr strategy bytes across all four frameworks.

## Consequences

- PHP's in-band marker constant and its consumer checks are removed.
- `js_escape`'s output bytes change from backslash escapes to `\xHH`/`\uHHHH`.
  The result is still a valid JavaScript string literal and is now also safe in
  an attribute; the four frameworks agree byte-for-byte. Per-framework tests that
  asserted the old backslash form are updated to the new contract.
- Under the sandbox, a `for` loop over a collection now requires that collection
  to be on the allow-list, matching the Python master. One Node sandbox test that
  iterated a non-allow-listed collection is updated to allow it.
- Each fixed item ships a named regression test in every affected framework,
  proven by mutation, plus the shared corpus cases.

## Alternatives considered

- **Strip the marker bytes from user input instead of removing the marker.**
  Rejected. A blocklist on request data is fragile; a real `SafeString` type
  makes the raw flag unforgeable by construction.
- **Make `json_encode` escape `"`.** Rejected (clause 7): it breaks Twig parity
  and the primary `<script>`-inlining use, for a case documentation covers.
- **A looser js escaper (only quotes and backslash).** Rejected: it does not make
  the output safe in an HTML attribute or against `</script>`.
