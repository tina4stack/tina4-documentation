# ADR-0043: The paginate envelope is seven snake_case keys, derived from the query

Date: 2026-08-07
Status: Accepted
Supersedes: the SYNTHESISE verdict in features/024-paginated-results.md

## Context

`toPaginate()` / `to_paginate()` turns a `DatabaseResult` into a paginated JSON
envelope. Measured 2026-08-05, one query (`limit=20 offset=40`, page 3 of 13)
against a real 250-row table, the four frameworks gave four answers:

| | page | per_page | total | total_pages | records |
|---|---|---|---|---|---|
| Python | 1 | 20 | 250 | 13 | 20 |
| PHP | 3 | 20 | 250 | 13 | 20 |
| Ruby | 3 | 20 | 20 | 1 | 0 |
| Node | 1 | 10 | 20 | 2 | 10 |

Only PHP was correct on all five. Ruby returned ZERO records for a valid page.
Three root causes, all cross-framework: `.count` was the true COUNT in python/php
but rows-returned in ruby/node; `page` was derived from the offset only in PHP;
ruby+node re-sliced `records` by the absolute offset against an array that was
already just that page. On top of the values, the envelope carried duplicate
keys - `totalPages` AND `total_pages`, `count` AND `total`, `data` AND `records`,
plus node's `perPage` - so the same integer shipped twice under two spellings in
one dict, in every API response.

## Decision

**The method takes NO arguments and derives every field from the query that ran.**

```
per_page    = the query's limit
page        = floor(offset / limit) + 1
total       = the true total for the filter (a COUNT probe), NEVER rows returned
total_pages = ceil(total / per_page)
records     = the rows the query returned, VERBATIM, never re-sliced
limit       = the SQL limit actually applied
offset      = the SQL offset actually applied
```

To read page 3, FETCH page 3 (`limit=20, offset=40`) and call the method with no
arguments. An argument cannot be honest: a `DatabaseResult` holds no connection,
so `to_paginate(page=6)` can only re-slice rows already in memory and then claim
`total_pages` for pages it can never reach. **Passing an argument RAISES** - a
removed parameter is a hard error, never a silent reinterpretation (the audit's
inverted-flag rule).

**The envelope is exactly seven snake_case keys in all four:** `records`, `total`,
`page`, `per_page`, `total_pages`, `limit`, `offset`. A JSON key is data and does
not change spelling by host language, so the payload is snake_case everywhere; only
the METHOD name follows each language's convention. `data`, `count`, `totalPages`,
`perPage`, `has_next`, `has_prev` are removed from the envelope.

## Consequences

- BREAKING. `.count` / `.total` become the true COUNT for the filter in Ruby and
  Node (they reported rows-returned), which reaches into the read path, not just
  the four `toPaginate` methods. The argument form is removed. The duplicate and
  camelCase keys vanish, so any consumer reading `data`, `count`, `totalPages`,
  `perPage`, `has_next` or `has_prev` must move to the canonical seven.
- PHP is the reference: it already derives page/per_page/total from the result. It
  still needs the argument form removed (raise on any arg) and the duplicate keys
  culled.
- Gated by `pagination_contract.json` (5 invariants) with a named suite in all four.
- This is why unbounded-by-default with explicit pagination is a correctness
  requirement, not a preference: a paginate envelope is only honest if `total` is
  a real `COUNT(*)`, never the length of a capped read.
