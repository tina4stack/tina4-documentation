# ADR-0027: a session `write()` ttl of zero means "use the configured default", not "never expires"

- Status: accepted
- Date: 2026-08-04
- Context: ADR-0024 (a pluggable subsystem's contract), session contract fixture
  invariant `ttl-is-honoured-by-every-backend`

## Context

Every session handler in all four frameworks exposes the same method shape:

```
write(session_id, data, ttl = 0)
```

The four frameworks did not agree on what a `ttl` of zero means, and the
disagreement was invisible because both readings produce a working session store
in ordinary use. Measured on 2026-08-04 at v3 HEAD, against real Redis 7,
Valkey 8, memcached 1.6.45, MongoDB 7 and real SQLite:

| Framework | `write(id, data)` with no ttl |
| --- | --- |
| PHP | "use the handler default" on all six backends |
| Ruby | "use the handler default" on all six backends |
| Python | "use the handler default" on redis, valkey, mongodb, memcached; "NEVER EXPIRES" on file and database |
| Node | "use the handler default" on memcached only; "NEVER EXPIRES" on file, database and mongodb |

The consequence is not academic. With `TINA4_SESSION_TTL=2` and a bare
`handler.write(id, data)`, a real 4-second sleep left the record alive on
five of six Node backends and on two of six Python backends, while the same call
expired correctly on PHP and Ruby. An operator moving an app between frameworks,
or between backends within one framework, got a different session lifetime from
identical application code. That is precisely the failure ADR-0024 exists to
prevent, and because a session lifetime is an authentication outcome rather than
a storage one, it is a security divergence rather than a cosmetic one.

Node's reading was not an accident. `packages/core/src/sessionHandlers/databaseHandler.ts`
records it as a deliberate fix for a real earlier bug: a zero ttl used to be
silently replaced with 3600, so an application asking for a non-expiring session
quietly received a one-hour one. That fix is locked in by
`session_mongo_zero_ttl_never_expires` in `test/sessionExpiryContract.test.ts`.
Any resolution has to answer that objection rather than reintroduce the bug.

## Decision

**A `ttl` of zero or less on `write()` means "use the handler's configured
default", and that default is resolved from `TINA4_SESSION_TTL` (3600).**

**"Never expires" remains fully expressible: set `TINA4_SESSION_TTL=0`.** The
handler default is then zero, the stored deadline is zero, and every read path
already treats an absent or zero stamp as "never expires" - the contract settled
by the session expiry work and unchanged here. So the capability Node's earlier
fix protected is preserved; it moves from a per-call argument to configuration,
which is where a session lifetime belongs.

Two properties this decision does NOT change, both load-bearing:

1. The ttl is consumed at WRITE time and baked into an absolute deadline.
   Nothing at read time consults a handler's ttl, so a reader configured with a
   different ttl can never judge another writer's record.
2. An absent or zero STORED stamp still means "never expires" and is still
   guarded out of the comparison rather than fed into it. This ADR is about the
   ttl ARGUMENT, not the stored stamp.

## Authority

Under ADR-0012 (standard > mainstream frameworks > libraries > internal
precedent):

- **Standard tier: no hit.** PHP's `SessionHandlerInterface::write()` carries no
  ttl at all, so the language standard does not decide it.
- **Mainstream frameworks: they point at the configured default, not at
  immortality.** Django's `get_expiry_age()` returns the CONFIGURED age when a
  session carries no explicit expiry. Laravel takes the lifetime from session
  config, never from a per-call zero. express-session's stores take the lifetime
  from configuration and the cookie rather than a per-write argument.
- **Libraries: same.** connect-redis reads `else ttl = this.ttl` - an absent or
  unusable per-call value falls back to the CONFIGURED default (86400), not to a
  key with no expiry.
- **Internal precedent: 2 of 4 frameworks already did this on every backend**
  (PHP and Ruby), and the two that did not were internally inconsistent, which
  is the weakest possible position to defend.

No tier supports "a zero per-call ttl means immortal". The mainstream tier is
unanimous the other way, so it binds.

## Consequences

- Python's `FileSessionHandler` and `DatabaseSessionHandler` now resolve a
  write-time default from `TINA4_SESSION_TTL`. Landed 2026-08-04.
- Ruby's file, redis, valkey, mongodb and database handlers now resolve their
  default from `TINA4_SESSION_TTL` instead of a hard-coded 86400, and
  `Session#save` forwards its own ttl. Landed 2026-08-04. Breaking: the Ruby
  default lifetime changes from 86400 to 3600. Migration: set
  `TINA4_SESSION_TTL=86400` to keep the old lifetime.
- PHP already satisfied this and needed no change.
- **Node is OWED.** Its file, database and mongodb handlers still read a zero
  ttl as "never expires", and `session_mongo_zero_ttl_never_expires` pins that
  reading. Closing it means changing those three handlers to resolve a default
  from `TINA4_SESSION_TTL`, and re-expressing that test as
  "`TINA4_SESSION_TTL=0` means never expires" rather than "a per-call ttl of 0
  means never expires". Node's end-to-end behaviour is already correct, because
  `Session` reads `TINA4_SESSION_TTL` and forwards it on every save - the gap is
  at the handler boundary, which is the layer this ADR governs.

## Alternatives rejected

- **Zero means never expires, everywhere.** Rejected: no authority tier supports
  it, it makes the ordinary case (a configured session lifetime) the one that
  needs an explicit argument at every call site, and it turns a forgotten
  argument into an immortal session - a security failure mode, not a storage
  one.
- **Forbid zero and require an explicit ttl on every write.** Rejected: it
  removes the ability to express "never expires" entirely, and it is a breaking
  change to every call site in all four frameworks for no gain over reading the
  configured default.
