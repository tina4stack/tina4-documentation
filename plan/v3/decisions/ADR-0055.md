# ADR-0055: Metrics measures production code and reports evidence honestly

- **Status:** Accepted
- **Date:** 2026-08-16
- **Applies to:** Feature 121
- **Target:** 3.14.0

## Question

What does `tina4 metrics` measure, and what may its test signal claim?

## Decision

The native engine measures production source by default. It excludes conventional
test and spec files, test directories, Python `conftest.py`, and TypeScript
declaration files. A repeatable `--exclude GLOB` removes project-specific paths.
`--include-non-production` restores test, spec, and declaration files when a
developer wants to inspect them.

Each nested callable owns its decisions. This rule covers Python lambdas, PHP
closures and arrow functions, Ruby blocks and lambdas, TypeScript and JavaScript
arrow functions, and Rust closures. Equivalent code must produce equivalent
callable boundaries in every supported language.

Type-2 duplicate fingerprints ignore comments. Python docstrings remain part of
the program because Python evaluates them as string expressions.

The JSON field is `has_referencing_test`, never `has_tests`. It means the engine
found concrete evidence that a conventional test references the source: a
dedicated filename, a parsed import or require, or a whole exported symbol. It
does not mean the test ran. It does not mean the test passed. It does not claim
line, branch, or behavior coverage.

Missing reference evidence produces the informational offender
`no_test_reference`. It never fails a `warn` or `error` gate.

## Why

A production score should not rise because a repository has many tests or type
declarations. A test badge must say what the engine observed, not what it hopes
is true. One scope rule also prevents the same function from changing score when
an engineer ports it to another Tina4 language.

## Consequences

- Historical file counts, callable counts, duplicate findings, and ranks change.
- JSON consumers must read `has_referencing_test`; no compatibility alias ships
  before the 3.14.0 stability boundary.
- Framework adapters and dev-admin remain consumers of the native JSON contract.
- Adding another language requires the same production discovery, callable,
  decision, import, symbol, clone, and parse-health fixtures.

No new runtime package is required. The native client continues to own its
tree-sitter grammars.
