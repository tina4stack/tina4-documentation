# ADR-0108: a failing seed file fails loud: the seed-directory runner stops at it and raises, and `seed` exits non-zero, all four frameworks

- Status: Accepted (implemented in all four: tina4-python#331, tina4-php#375 + #376, tina4-ruby#186 + #188, tina4-nodejs#214)
- Date: 2026-11-22
- Context: found by the Windows framework-bugs work
  (`plan/v3/windows-framework-bugs.md`, tina4-documentation#218), where Node's
  `FakeData.seedDir()` was fixed to import a real path and the reviewer noticed
  that it then swallows any seed file that throws. Applies ADR-0104's rule (fail
  loud for AI) and Feature 113's contract ("a failed seeder fails
  `tina4 seed`"). Cross-framework contract change.

## Context

A seed file is application code: it inserts the rows an app needs to run. When
one throws, that is a bug in the app, and whoever ran the seeder (a developer, an
AI agent, a deploy script) needs to hear about it. Today what happens depends on
the language and on whether the API or the CLI ran the file. Read from source on
`origin/v3` (python bf16cdc4, php 924815eb, ruby ffdbb65a, nodejs f39297b8):

| Surface | Python | PHP | Ruby | Node |
|---|---|---|---|---|
| API runner (`seed_dir` / `seedDir`) | `except Exception: pass`: silent, nothing logged, the run carries on | `require` lets it throw: stops at the file | logs `Seeder: Failed to run`, carries on, returns `nil` | `catch {}`: silent, nothing logged, the run carries on |
| CLI `seed` | uncaught: traceback, stops, exit 1 | uncaught: stops, non-zero exit | **runs no seed at all**: `seeder.rb` is autoloaded only through `Tina4::FakeData`, so `Tina4.seed_dir` is undefined there and the command dies with `NoMethodError` (exit 1) | runs every file, then "Some seeds failed", exit 1 |
| Does the API runner call the entry point `generate seeder` writes? | **no**: it runs the module body, but never calls `run(db)` (the CLI does) | **no**: it `require`s the file and records `'loaded'`, but never calls the returned closure (the CLI does) | yes (the file body is the seed) | **partly**: it calls a `default()` export, never the named `run()` that `generate seeder` writes |

So the same broken seed file is silent in two frameworks, logged-but-green in a
third, and loud in the fourth. Python and Node's API runners return a list that
simply leaves the failed file out, and Ruby's logs it and carries on. Three of
the four API runners also skip the generated seeder's entry point and report
that file as done. `tina4ruby seed` does fail, but for the wrong reason: it
never reaches a seed file (the Ruby CLI row, found while implementing this
ADR).

## Decision

1. **The seed-directory runner fails loud.** `seed_dir` (Python, Ruby),
   `seedDir` (PHP, Node) runs the seed files in sorted order. If a file raises,
   the runner logs an error naming the file and the cause, and then raises.
   The raised error names the failing file, carries the original error as its
   cause, and lists the files that completed before it. No later file runs.
2. **Stop at the first failure; do not run the rest and report at the end.**
   Seed files are numbered because later files build on earlier ones (an
   `orders` seed needs the `customers` rows). Running the dependants after a
   failed parent produces a run of misleading foreign-key errors and a
   half-seeded database, and buries the one error that matters. Python's and
   PHP's CLIs already stop at the first failure.
3. **On success the runner returns the files it executed, as a list of paths,
   in order** (Python's shape). Ruby returns that list instead of `nil`; PHP
   returns it instead of a `basename => 'loaded'` map.
4. **The runner executes every seed shape the CLI does.** Python's `seed_dir`
   calls a module's `run(db)` with the bound default database, and PHP's
   `seedDir` calls a callable the file returns: the shapes `generate seeder`
   writes, which `tina4py seed` and `tina4php seed` already call. Node's
   `seedDir` calls a `default()` export, or else the named `run()` that
   `generate seeder` writes. A runner that reports a seed it never ran is the
   same bug as one that hides a seed that failed.
5. **One file-selection rule:** `.py` / `.php` / `.rb` / `.ts` and `.js` files,
   sorted by name, skipping any file whose name starts with `_` (Python's and
   Ruby's rule; PHP and Node adopt it).
6. **CLI `seed` in all four** prints the failing file and its cause, stops, and
   exits 1. The `tina4` client propagates that code (Feature 113), so a failed
   seeder fails `tina4 seed` and any deploy step built on it. Rows already
   written by earlier files stay written: seed files are not wrapped in one
   transaction (they may run DDL, and MySQL/Firebird auto-commit it).
7. **Ruby's dev-admin seed runner** (`run_seeds_payload`) follows the same rule:
   it stops at the first failing file and answers
   `{seeded, failed: 1, error: "<file>: <message>"}`.

There is no lenient switch at file level. A seed file that wants to tolerate a
failure catches it itself. Row-level seeding is unchanged: `seed_orm` /
`seed_table` keep their counted `SeedSummary {seeded, failed, errors}` and the
`strict` re-raise (Feature 028). Those failures are counted and returned, never
silent, and a file can opt into `strict` to turn them into a file failure.

## Rejected

- **Log and skip (Python's and Node's API behaviour, Ruby's everywhere).** A
  green run over a seed that did not run is a silent failure: the developer
  finds out later from an empty table, and an AI agent never finds out. That is
  exactly what ADR-0104 reversed for Frond.
- **Run everything, then raise one aggregate error (Node's CLI).** Louder than
  skipping, but it still runs dependants against a missing parent (decision 2),
  and the first, real cause arrives mixed in with the cascade it caused.

## Consequences

- BREAKING in Python and Node: an app that calls `seed_dir` / `seedDir` over a
  folder with a broken seed file now gets an exception instead of a shorter
  list. In Ruby, `tina4ruby seed` now runs the seed files at all (it loads the
  seeder first) and exits 1 on a failing file, and `seed_dir` raises and
  returns a list instead of `nil`. In Python, PHP and Node, the runner now
  calls the generated seeder's entry point (before, the API silently did not
  seed it), and PHP returns a list.
- Owed in each framework, test-first, no mocks, each test proved red by
  mutation: a real seed folder on disk with `001_ok`, `002_raises`, `003_ok`;
  the runner raises naming `002_raises`, `001_ok` ran, `003_ok` did not; the CLI
  `seed` exits 1 with the file named in its output; a clean folder returns the
  ordered list; a `_`-prefixed file is skipped; PHP's runner calls a returned
  closure, Python's calls `run(db)` and Node's calls `run()`; the Ruby CLI
  runs a seed file at all.
