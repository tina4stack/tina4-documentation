# ADR-0040: Ruby's file queue adopts the canonical store layout

- **Date:** 2026-08-05
- **Status:** Accepted
- **Scope:** `tina4-ruby` - `lib/tina4/queue.rb`,
  `lib/tina4/queue_backends/lite_backend.rb`, `lib/tina4/dev_admin.rb`. Breaking
  for any existing Ruby app with jobs on disk.
- **Relates to:** [ADR-0024](ADR-0024.md) (one env var changes the backend and
  nothing else), and the dev-admin queue-path defect fixed the same day in
  tina4-nodejs, tina4-python and tina4-php.

## The problem, measured

The dev-admin queue panel listed one directory and counted another. Measured
2026-08-05 (macOS 15.5 arm64, Ruby 4.0.2, real Puma, real HTTP, real job files):

| endpoint | before | after |
| -------- | ------ | ----- |
| `/queue/topics` | `["ghost-topic-never-real"]` | `["legacy","mixed","orders"]` |
| `?topic=mixed` | jobs 0, stats sum 3 | jobs 3, stats sum 3 |
| `?status=pending` | jobs 0 (the parameter was never read) | jobs 1, equal to `stats.pending` |

Ruby diverged further than the other three. Its lite backend wrote
`<cwd>/.queue/<topic>/<id>.json` while the panel scanned
`<cwd>/data/queue` - two different trees, so `/queue/topics` could never list a
real topic. And `TINA4_QUEUE_PATH`, honoured by Python, PHP and Node, was read
**nowhere in the repository**: a documented variable that silently did nothing
in one framework of four.

## The decision

Ruby adopts the canonical layout:

```
<TINA4_QUEUE_PATH | data/queue>/<topic>/<id>.queue-data
```

replacing `<cwd>/.queue/<topic>/<id>.json`. The layout is defined once on
`Tina4::Queue` and is the single answer both the backend and every dev-admin
queue handler ask, so a list and a count can never again describe different
sets.

Because the move would otherwise strand every job in an existing app's
`.queue/`, the lite backend performs a **one-time rescue**: the first backend to
resolve its store moves every legacy `*.json` into the new store, renaming to
`*.queue-data`, preserving structure, never overwriting a destination, and
logging the count at INFO.

Jobs are pending work somebody is waiting on. Silently orphaning them is a
data-loss outcome, not a cosmetic one, which is why the migration is part of the
decision rather than a follow-up.

## Alternatives considered

**(a) Fix only the dev-admin path.** Rejected. It leaves Ruby unable to share a
store with the other three, and leaves a documented environment variable a lie in
one framework of four.

**(b) A permanent read-fallback to the legacy path.** Rejected. It doubles every
read path in the backend (13 methods) and in the dev-admin reader, forever, and
it re-creates the two-stores-one-panel problem this change exists to remove.

**(c) Migrate only when the new store is absent.** Rejected. In a rolling
upgrade an old instance keeps writing to `.queue/` after the new store exists,
and those jobs are exactly the ones that would be stranded.

## Consequences

- Jobs move on first use with no operator action, and loudly.
- **Every existing Ruby app is affected, including those that already set
  `TINA4_QUEUE_PATH`.** Because Ruby ignored the variable, those operators' jobs
  are also in `.queue/` and they need the migration too. An earlier draft of this
  work assumed they were unaffected; that was wrong.
- Pending jobs and reservations now interoperate with a Python, PHP or Node
  store. **Dead letters do not** - Ruby keeps a shared `<base>/dead_letter/`
  tagged by topic while the others use per-topic `<base>/<topic>/failed/`. That
  is a second breaking change with its own migration and is deliberately not
  taken here.
- Steady-state cost is one `Dir.exist?` check.
- Anything exporting `TINA4_QUEUE_PATH` now genuinely redirects the store, which
  is correct and which broke three spec files that had been getting isolation for
  free from `Dir.chdir`. They now pin their own stores.

## What the change exposed

One assertion in `dev_admin_spec` - `expect(data["jobs"]).to eq([])` - was
**unfalsifiable** before this work: the handler never listed pending jobs, so it
read `[]` whatever was on disk. Other queue specs survive only because they use
randomised topic names, which is luck rather than isolation. A suite-wide
per-example store pin in `spec_helper.rb` remains the robust answer and is not
done here.

## Verification

5024 examples, 0 failures at seeds 12345, 98765 and 4242 on the lab host (Ubuntu
24.04.4 LTS x86_64, Ruby 3.2.3, `TINA4_REQUIRE_SERVICES=1`). Baseline was 5007,
so the delta is exactly the 17 new examples. Mutation-proved in 14 separate
parts, every mutation confirmed applied by md5 and every restore byte-exact.

Two gates existed only because mutation testing found them missing: a `../`
path-traversal case for the topic sanitiser, which first came back 0 failures
and was therefore an untested security fix, and the corrupt-file branch backing
the sum invariant.
