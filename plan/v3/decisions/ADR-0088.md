# ADR-0088: the framework's own inline styles and scripts run under the strict default CSP via a per-response nonce

- Status: accepted
- Date: 2026-10-01
- Context: SECHDR-DEC-01 (the strict default Content-Security-Policy
  `default-src 'self'`), the security-headers contract fixture
  (`securityheaders_contract.json`) and the http-hardening contract
  (`http_hardening_contract.json`)

## Context

Tina4 serves `Content-Security-Policy: default-src 'self'` by default
(SECHDR-DEC-01, secure-by-default). But the framework's OWN pages - the welcome
page a fresh `tina4 init` project shows first, the dev toolbar, the error
overlay, the Swagger UI, the dev-admin dashboard and the gallery - emit inline
`<style>` blocks, inline `<script>` blocks and `style="..."` attributes. A
browser refuses every inline style and script under `default-src 'self'`
("Refused to apply a stylesheet because its hash, its nonce, or 'unsafe-inline'
appears in neither the style-src nor the default-src directive"), so a brand-new
project loads with no styling at all and its images appear not to load.

The failure is invisible to `curl`, which does not enforce CSP, and surfaces
only in a real browser - which is why it shipped. Worse, the documented remedy
(the one-time warning tells the operator to "set TINA4_CSP to a policy that
allows them") steers a frustrated developer toward `'unsafe-inline'`, which
globally re-enables inline scripts and gives up exactly the cross-site-scripting
protection the strict default exists for. The default, as shipped, pressured
users into the insecure workaround.

Three ways to let the framework's own inline content run were on the table:

- **Relax the default to `'unsafe-inline'`.** Rejected: it discards CSP's core
  protection, the opposite of the goal.
- **Hash every inline block.** Rejected: brittle (any edit to the block breaks
  the hash), and it cannot cover content injected at runtime (the dev-reload
  client), nor `style=` attributes.
- **Mint a nonce per response and name it in the header.** Chosen. A nonce is
  the mechanism CSP provides for exactly this: allow this response's own trusted
  inline content, and nothing else.

## Decision

Keep the strict default CSP. Make the framework's own inline content clean under
it with a per-response nonce, and de-inline what a nonce cannot cover.

1. **One cryptographically-random nonce per response** (128 bits), generated on
   first access and held for the life of the request so the header and the body
   always agree regardless of which is produced first.
2. **Inject `'nonce-<X>'` into both `style-src` and `script-src`** of the emitted
   CSP - for the default policy (`default-src 'self'` becomes
   `default-src 'self'; style-src 'self' 'nonce-<X>'; script-src 'self' 'nonce-<X>'`)
   AND for a user-set `TINA4_CSP`, deriving those directives from `default-src`
   (fallback `'self'`) when they are absent, so the framework's own content
   always runs. Never add `'unsafe-inline'` or `'unsafe-hashes'`.
3. **Stamp `nonce="<X>"` on every inline `<style>` and `<script>`** the framework
   emits. A `<script src="...">` needs none.
4. **De-inline every framework `style="..."` attribute into a class**, and
   de-inline inline `on*=` event-handler attributes to `addEventListener`,
   because a nonce covers a `<style>`/`<script>` ELEMENT but never an inline
   style or event-handler ATTRIBUTE.
5. **Expose the nonce to application templates** as the template global
   `csp_nonce()` and on the response object (`response.csp_nonce` /
   `$response->cspNonce` / idiomatic equivalent), so app developers serve their
   own inline blocks the same way: `<style nonce="{{ csp_nonce() }}">`.
6. **A route that sets its own CSP keeps it.** The framework fills in only a
   header that is absent.

## Authority

Under ADR-0012 (standard > mainstream frameworks > libraries > internal
precedent): the CSP Level 2/3 standard defines nonces as the sanctioned way to
allow specific inline scripts and styles under a strict policy, and the browser
vendors' and OWASP's guidance is to prefer a per-request nonce over
`'unsafe-inline'`. No tier supports shipping a framework whose own pages force
the operator to `'unsafe-inline'`.

## Consequences

- A fresh project renders correctly under the strict default with no
  configuration, and the protection stays: an injected inline script that lacks
  this response's random nonce still will not run. The change is a security
  improvement in practice - it removes the incentive that was pushing operators
  to `'unsafe-inline'` - even though adding a nonce to `style-src`/`script-src`
  is, at the header level, a controlled relaxation of pure `'self'`.
- App developers get a first-class, documented way (`csp_nonce()`) to serve
  inline content under the same policy, and are steered toward classes and
  `addEventListener` over inline `style=`/`onclick=`.
- The nonce is per-response and random, so any test or contract that asserts the
  CSP must assert its STRUCTURE (a nonce is present in style-src and script-src,
  and the body's inline tags carry that response's nonce), never a byte-equal
  string. `securityheaders_contract.json` and `http_hardening_contract.json`
  change shape accordingly and move with this ADR.
- Cross-origin resources (CDN fonts/scripts, `data:` URIs, a separate
  API/WebSocket host) remain blocked by the default - unchanged, and still
  called out in the one-time `TINA4_CSP` warning.
- The contract is shared: PHP, Ruby and Node.js mirror the nonce generation, the
  header injection and the de-inlining, with the Python reference
  (`fix/csp-nonce-inline`, tina4-python #190) leading.

## Known follow-up

`crud.twig` (and its siblings) carry a few row-level `onclick=` handlers that
pass per-row JSON; a nonce cannot cover an event-handler attribute, so these
need event-delegation wiring and their own tests across all four frameworks.
Their `<script>` blocks are already nonce'd. Tracked separately, not a blocker
for this ADR.
