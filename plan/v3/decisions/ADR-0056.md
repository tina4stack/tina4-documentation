# ADR-0056: Configuration-first OIDC hands identity into Tina4 sessions

Date: 2026-08-17
Status: Accepted
Supersedes: none (introduces Feature 136)

## Context

Tina4 has local JWT authentication and server-side sessions but cannot complete an
enterprise SSO login. Applications therefore rebuild discovery, redirects, callback
validation, role mapping, refresh and logout. A self-hosted OIDC service is a usual Tina4 deployment,
but these operations are standard OpenID Connect operations.

The owner set two boundaries: SSO normally hands the verified identity into Tina4's
existing session, and the feature must follow Tina4's configuration-first methodology.

## Decision

- The runtime implements provider-neutral OpenID Connect, not provider adapters.
- Configuration is issuer, client id, optional client secret, scopes and redirect URI.
  The issuer's discovery document supplies endpoints, capabilities and signing keys.
- The runtime and conformance contract are provider-neutral. Named providers appear only
  in documentation recipes; the live gate uses a disposable standards-compliant server.
- Browser login uses Authorization Code with PKCE S256. SAML, implicit and password
  grants are outside this feature.
- A successful callback regenerates the Tina4 session id before attaching identity.
  Provider credentials remain reserved server-side session data; the browser receives
  only the ordinary Tina4 session cookie.
- Subsequent requests restore a normalized identity into `request.user` before the
  existing secured-route gate. There is no parallel SSO-only authorization system.
- Identity contains `issuer`, `subject`, `username`, `email`, `name`, `roles`, and
  `groups`. Raw tokens never enter `request.user`, logs, errors or `session.all()`.
- Refresh atomically replaces credentials in the same session. Failure removes the SSO
  identity. Logout always destroys the local session before attempting provider logout.
- Conformance uses real providers over real sockets and real Tina4 session storage. A
  fake OIDC server or mocked HTTP client cannot prove this contract.
- Introspection is the zero-extra-package default. JWKS verification is opt-in only when
  the application installs a suitable cryptography capability; cryptography is never hand-written.

## Consequences

Feature 64 remains the token-primitive owner and Feature 65 remains the session owner.
Feature 136 owns OIDC configuration/discovery, browser flow, provider validation,
identity normalization and their handoff. A future language implements the same fixture
without copying provider-specific branches from an existing runtime.
