# ADR-0042: The messenger uid is the IMAP UID, never a sequence number

Date: 2026-08-07
Status: Accepted
Supersedes: none

## Context

`inbox()` and `search()` return a `uid` for each message, and `read(uid)` /
`mark_read(uid)` / `delete(uid)` take one back. A caller stores that id and uses
it later. Measured on 2026-08-06 against a live GreenMail with all four
frameworks asked the same question about the same mailbox, two of them returned a
number that means a different message tomorrow.

IMAP gives a message two numbers. The UID is stable for the life of the mailbox.
The sequence number is the message's position in the current view, and it
renumbers whenever any client expunges anything below it. Before the first
expunge the two are identical, which is exactly why four independently written
contract suites all passed while two were wrong.

The probe forced the difference. Send P1, P2, P3; expunge P1. By sequence the
mailbox is now `{1: P2, 2: P3}`; by UID it is `{2: P2, 3: P3}`. Asked for the id
of P3:

| Framework | reported id for P3 | numbering |
|---|---|---|
| Python | `2` | sequence (WRONG) |
| Node | `2` | sequence (WRONG) |
| PHP | `3` | UID |
| Ruby | `3` | UID |

Each framework was internally consistent: reading back by its own reported id
worked on an unchanged mailbox, so every existing test passed. The defect only
shows once another client expunges, and then it is silent. No error, no crash,
just the wrong message returned for an id stored yesterday. Python and Node
fetched with the sequence-number form of the IMAP commands (`FETCH`, `STORE`)
while asking for the id with `SEARCH`, so the id they handed out and the commands
they addressed it with were the same wrong numbering end to end.

This is the same defect shape the queue fixture caught one layer down: an
identifier that is stable in one implementation and volatile in another, from one
API that four clients are told to trust equally.

## Decision

The `uid` returned by `inbox`, `search`, and `unread` is the IMAP UID, never a
sequence number, in all four frameworks. Every fetch or store addressed by that
id uses the UID form of the command: `UID SEARCH`, `UID FETCH`, `UID STORE`. An
id handed to a caller today addresses the same message for the life of the
mailbox.

## Consequences

- Python moved all eight call sites to the UID form (`3237383`); Node moved nine
  commands to `UID SEARCH` / `UID FETCH` / `UID STORE` (`c1b28fd`). PHP and Ruby
  were already correct.
- The rule is pinned by the `msg-uid-is-a-real-uid` invariant in
  `messenger_contract.json`, with a named regression suite in every framework
  that drives the real expunge, so the two numberings genuinely diverge in the
  test rather than sitting identical.
- A sequence number is never a valid public id from this subsystem again. A test
  that reads back on an unchanged mailbox is not proof; the expunge is the proof.
