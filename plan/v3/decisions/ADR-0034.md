# ADR-0034: A test never asserts on a server-global metric

- **Date:** 2026-08-04
- **Status:** Accepted
- **Scope:** Every test in all four frameworks that measures a shared service -
  MongoDB, Redis, Valkey, memcached, PostgreSQL, MySQL, RabbitMQ, Kafka.
- **Relates to:** [ADR-0024](ADR-0024.md) (the swap must work),
  [ADR-0025](ADR-0025.md) (the DocStore contract).

## The problem, measured

`client-lifecycle-is-bounded` is a real invariant: repeated `get_collection()`
must not grow connections without bound. All four frameworks proved it by
reading MongoDB's `serverStatus.connections.current` and asserting

    rounds[2] - rounds[1] <= 2 && rounds[2] < 60

`connections.current` is **server-global**. It counts every client connected to
that mongod, not the one the test owns. Measured 2026-08-04 against the shared
lab MongoDB 7.0.39, with the DocStore code UNCHANGED and correct:

| what else was connected | what the test read | verdict |
| ----------------------- | ------------------ | ------- |
| nothing (idle box)      | ~6                 | passes  |
| one other agent         | `[88, 89, 90]`     | passes  |
| 45 further real clients | `[193, 194, 195]`  | **FAILS** |

The delta half was correct throughout - the pool really had plateaued. Only the
absolute ceiling moved, and it moved because of somebody else's work. That is
not a gate; it is a coin flip that happens to be weighted by how busy the lab
is. It fails during exactly the parallel work where a green signal matters
most, and it "passes" on an idle box no matter how badly the code leaks.

This is not the first instance. The cache subsystem shipped the same defect in
a different costume: `cacheStats()['size']` read memcached's global
`curr_items`, so it counted every other tenant's keys.

## The decision

> **A test may only assert on a measurement it OWNS. Where a shared service
> exposes a global counter, the test must scope the measurement to its own
> client, or not assert on that number at all.**

Concretely, in order of preference:

1. **Scope it.** Most services expose a per-client view. MongoDB: set an
   `appName` in the connection string - a standard option every official driver
   honours, so nothing in the framework needs to know about it - and count with
   `$currentOp` + `idleConnections` filtered on that name. The same run that
   read `[193, 194, 195]` globally reads a flat `[3, 3, 3]` scoped.
2. **Drop the assertion** if no clean per-client view exists on the supported
   server versions, keeping only the deltas the test genuinely controls.

Scoping is strongly preferred, and the DocStore case shows why option 2 is a
real loss rather than a tidy simplification: under a mutation that restores the
one-client-per-call leak, the DELTA still passes (`[37, 37, 35]`) and **only
the ceiling catches it**. Deleting the ceiling would have left a test that
looked stable and had stopped detecting the very bug it was written for.

## Two obligations that come with scoping

1. **Prove the probe is not blind.** A scoped count that matches nothing
   returns zero, and every "did not grow" assertion then passes vacuously. Each
   suite asserts FIRST that it can see at least one of its own connections, so a
   mis-typed tag fails the test instead of silently disarming it.
2. **Tighten what scoping now permits.** Once the number is owned, weak
   assertions written to tolerate other tenants should be replaced by the real
   ones. `close()` released "fewer connections than before" - which a stranger
   disconnecting satisfies on its own - becomes **exactly zero of ours**.

## Consequences

- Four suites changed; no framework code changed. The invariant they prove is
  unchanged and is now measured correctly.
- The rule generalises to any shared-service metric a test might reach for:
  Redis `INFO clients` / `connected_clients`, memcached `curr_items` and
  `curr_connections`, PostgreSQL `pg_stat_activity` without a filter, broker
  queue depths on a shared vhost. If another process can move the number, the
  assertion is not a gate.
- The audit is a grep, and it is worth re-running whenever a suite starts
  measuring a service: search for the global-counter names above and check that
  every hit is filtered to something the test created.
