# ADR-0039: Defend, report, then replace. Never fork a dependency.

- **Date:** 2026-08-05
- **Status:** Accepted
- **Scope:** Every third-party runtime dependency in tina4-python, tina4-php,
  tina4-ruby and tina4-nodejs: database drivers, broker clients, and anything
  else the frameworks do not implement themselves.
- **Relates to:** the zero-dependency promise in
  [00-VISION](../00-VISION.md), and the existing hand-rolled transports
  (`RespClient`, `MongoWireClient`, the Kafka RecordBatch v2 encoder).

## The problem, measured

Backlog #60 recorded that "node-firebird SRP login fails ~12% of the time on
Firebird 5". Over two days we came within one decision of forking the driver,
and within two of writing our own from scratch.

Then we measured it properly. On the lab host (Ubuntu 24.04.4 LTS x86_64, live
Firebird 5 on 127.0.0.1:3050), 100 bounded attach attempts per version:

| node-firebird | result |
| ------------- | ------ |
| **1.1.10** - what `package.json` pinned | `OK 87, ERROR 13` - a 13% authentication failure |
| 2.14.1 | `OK 60, ERROR 0` |
| **2.14.3** - latest, released four days earlier | `OK 60, ERROR 0` |

The failure was real, reproducible and exactly the reported rate. It was also
**fixed upstream long ago**. `"node-firebird": "^1.1.9"` forbids the entire 2.x
line, so every Firebird test had run against a driver with a 13% auth failure
rate, for as long as the pin had been there.

Upstream was not neglected either: last push four days before, one open issue,
zero open issues mentioning the symptom. There was nothing to report and nothing
to fork. There was a version number to change.

Two mistakes made it look worse than it was, and both are worth recording
because they are ordinary mistakes anyone repeats. An unbounded probe turned a
fast error into an apparent 16-minute hang, so a measuring instrument inherited
the defect it was measuring. And the installed version was checked on a laptop
rather than on the host that actually runs the suites, where it was 13 major
versions older.

What survived the correction is the framework half, which Tina4 owns whatever
the driver does: `packages/orm/src/adapters/firebird.ts` awaited `fb.attach()`
in a bare promise with **no timeout**. Node unbounded, PHP no Firebird connect
timeout, Ruby none. A driver that can hang is a driver we bound, on any version.

## The decision

**Step zero: check your own pin, and check it on the machine that runs the
code.** Before concluding that a dependency is broken, confirm which version is
actually installed where the failure was observed, and compare it against the
latest release. This costs two commands. Skipping it nearly cost a fork.

Then three steps, in this order, every time.

**1. Defend in our own layer first, always, and immediately.**

A bad outcome for a Tina4 user is a bad outcome regardless of whose code caused
it. Bound the call, guard the value, surface the failure. This ships today, it
protects everyone on the currently published version of the dependency, and it
is ours to test. It is not contingent on anybody upstream doing anything.

This step is not optional and it is not a workaround to be removed later. A
dependency that can hang is a dependency we bound, permanently.

**2. Report upstream, with the reproduction.**

The reproduction is the valuable part and we already have it by the time we get
here. Filing it costs almost nothing and helps every other consumer. Do it.

**3. Replace with a minimal client we own, when the dependency keeps failing.**

Not a fork. A small thing that implements the subset Tina4 actually needs.

This is already the house style and it already works: `RespClient` speaks the
RESP commands the session and cache layers use, `MongoWireClient` implements
`find_one`/`upsert`/`delete_one`/`delete_many` over OP_MSG and nothing else, and
the Kafka producer hand-rolls RecordBatch v2 because Kafka 4.x dropped the
Produce versions the old libraries emit. None of those is a general driver. Each
is a few hundred lines covering exactly one framework's needs, with a
third-party client still preferred when it is present.

**Forking is rejected outright.** Forking a database driver means owning its
security surface, its protocol correctness and its version churn forever. For a
project whose entire proposition is zero dependencies, taking on someone else's
permanent maintenance burden is the worst available outcome. If a dependency is
bad enough to fork, it is bad enough to replace with something smaller that we
understand completely.

## The line that keeps step 3 safe

Hand-rolling is right for **wire protocols** and wrong for **cryptographic
primitives**.

- **Cryptographic primitives always come from the language's own standard
  library** - `OpenSSL::HMAC`, `hashlib`, `node:crypto`, `openssl_*`. Never
  hand-rolled, and equally never a third-party gem or package. Tina4 already
  does this: HS256/384/512 and the opt-in RS256 use stdlib OpenSSL in all four,
  which is why the `jwt` gem and the `bcrypt` dependency could both be removed.
- **Wire protocols are ours to implement**, because they are specified,
  testable against a real server, and small once scoped to what we use.

The distinction is not "hard versus easy". It is whether a subtly wrong
implementation fails loudly (a protocol desync fails immediately and visibly) or
silently (weak crypto looks identical to strong crypto until it is broken).

## Alternatives considered

**(a) Pin and wait for upstream.** Rejected. It leaves users hanging - here,
literally - for as long as upstream takes, and it makes our reliability
somebody else's schedule.

**(b) Fork and patch.** Rejected, as above. It also splits us from the
ecosystem's security fixes, which is the exact liability a zero-dependency
project exists to avoid.

**(c) Vendor a minimal client immediately, skipping step 1.** Rejected. Writing
a new transport is slower than adding a timeout, and users need the defence
first. Step 3 is a considered response to a repeated failure, not a reflex.

## Consequences

- Every dependency call that can block gets an explicit bound, with a clear
  error naming the cause and the setting that tunes it. This is now a review
  item, not a judgement call.
- We accumulate small owned transports over time, which is the intended
  direction and consistent with the zero-dependency promise.
- We carry no forks, so we never inherit an upstream security backlog.
- **Owed:** the Firebird connect is still unbounded in Node, PHP and Ruby.
  Closing it needs a new environment variable for the connect timeout, which
  lands in all four together or not at all. This is no longer urgent - the
  driver it was defending against was simply out of date - but a connect that
  can block forever is still a connect we bound.
- A stale range that forbids the fixed line is the same defect class as a
  missing pin: both mean the version running is not the version anyone chose.
  `^1.1.9` was presumably written when 1.1.9 was current and never revisited.
