# ADR-0063: Scaffolding envelope v1.1 — edit-hints + next-steps + surfacing test_paths

Status: Proposed
Date: 2026-08-26
Ships in: 3.13.120

## Context

ADR-0062 (3.13.117) gave every `generate` verb a resolution envelope
(`generate_v1`) that named `class_name` / `table_name` / `file_path` /
`routes` / `transformations`. It told the caller WHERE files went.

It did not tell the caller:

- **What to edit next inside the generated file.** A first-time user or an
  AI agent that scaffolded a model still had to open the file and figure
  out where to add their next field, relationship, or validation. There
  was no in-line pointer.
- **What to do after generating.** Nothing named the follow-up commands
  (`tina4 migrate`, `tina4 serve`, `curl http://...`). The agent had to
  reverse-engineer the next step from stack traces or from the
  `tina4-developer-<lang>` skill.
- **Where the matching tests live.** The envelope already carried a
  `test_paths[]` key but the human stderr block never printed it, so a
  reader saw only the model + migration + routes and missed the test
  file.

Together those three omissions made the resolution block informative
about what HAPPENED but silent about what HAPPENS NEXT. An AI-agent
loop that leans on the resolution block for guidance had to fall back
to prose search elsewhere.

## Decision

Envelope bumps additively to `generate_v1_1`. Two new keys plus one
key surfaced:

- `resolution.edit_hints[]` — one entry per `tina4:edit` marker found
  in the freshly-written files. Shape: `{file: string, line: integer,
  label: string}`. Emitted in the human stderr block under
  `Edit these lines:`.
- `resolution.next[]` — a curated short list of actionable next steps
  the generator names, based on the verb it just ran and the resolved
  paths. Shape: `[string]`. Emitted in the human stderr block under
  `Next:`.
- `resolution.test_paths[]` — ALREADY in the envelope since v1. Now
  surfaced in the human block as a `tests` line alongside the existing
  `class` / `table` / `routes` / `migration` lines.

`commands --json` advertises the new envelope so agents can gate on it:

```json
{"commands": [...],
 "resolution_contract": {"version": "1.1", "envelope": "generate_v1_1"}}
```

Every `v1` key is preserved. Existing `--json` consumers stay valid.
Callers that read `next[]` or `edit_hints[]` know they need envelope
`>= 1.1`.

### Marker syntax

Language-native comments, short actionable label:

| Language | Syntax |
|----------|--------|
| Python   | `# tina4:edit <label>` |
| PHP      | `// tina4:edit <label>` |
| Ruby     | `# tina4:edit <label>` |
| Node/TS  | `// tina4:edit <label>` |

The label is a colleague-voice pointer, not a full sentence — `add
fields here`, `set auth guard`, `customise the list projection`. No
period, no question mark. 1–5 words.

### Marker placement rule

Markers live in **generator templates**, not in a runtime scanner.
Baked-in beats grepped-in:

- The template author owns the copy of the hint.
- No parser risk — a comment that looks like a marker but isn't never
  gets surfaced (the scanner is a plain literal-string match on
  `tina4:edit`, nothing more).
- Fresh scans of the generated file surface the same markers, so the
  hint persists across `--dry-run` (in-memory render), a real run
  (file on disk), and manual `grep -rn tina4:edit src/` later.

1–3 markers per template, at genuine first-edit spots. Never
over-mark; noise dilutes the signal.

### Human stderr block shape (canonical example)

```
Generated model Order
  class      Order  (in src/orm/Order.py)
  table      orders  (auto-pluralized: 'order' is a SQL reserved word)
  routes     /orders, /orders/{id}
  migration  migrations/2026...create_orders.sql
  tests      tests/test_order.py

Edit these lines:
  src/orm/Order.py:14   add fields here
  src/orm/Order.py:16   add relationships here

Next:
  1. Edit src/orm/Order.py to add fields beyond the default 'name'
  2. Apply the migration:  tina4 migrate
  3. Try it:               tina4 serve  ->  curl http://localhost:7146/orders
  4. Add CRUD scaffolding: tina4 generate crud Order --skip-model
```

Sections with empty arrays are omitted from the human block. The JSON
envelope always includes the arrays as `[]` when nothing applies —
schema shape is stable.

## Test contract

Per language, five real-subprocess tests:

1. **Positive-envelope** — `generate model Foo --json --dry-run` returns
   a valid `generate_v1_1` envelope with populated `edit_hints[]` and
   `next[]`.
2. **Manifest** — `commands --json` returns
   `resolution_contract.version == "1.1"` and
   `envelope == "generate_v1_1"`.
3. **Human-block** — bare `generate model Foo` writes files AND stderr
   contains both `Edit these lines:` and `Next:` headers with real
   content.
4. **Marker-match** — each envelope `edit_hints[i]` `{file, line}`
   corresponds to a real `tina4:edit` marker line in the actual file
   (open the file, seek to the line, assert the line starts with the
   marker syntax + carries the same label).
5. **Empty-arrays legal** — a verb with no natural next-steps still
   returns valid JSON with `next: []`; a template with no markers still
   returns valid JSON with `edit_hints: []`.

Mutation-gate test 4: strip a marker from a copy of the generated file
(via `sed` in a tmpdir), rerun the parser subroutine, assert that
edit_hint entry is gone. Restore, assert it returns.

All tests are real subprocess. No mocks. `mkdtemp` per test.

## Consequences

- Every existing verb (the 15 that ship in 3.13.119) gets its
  templates marker-baked in 3.13.120 as part of this ADR. Four-language
  parity is preserved — every verb gains markers in every backend at
  the same tag.
- New verbs planned for 3.13.121-3.13.123 (`error-page`, `cache`,
  `session`, `health`, `ai`, `graphql`, `sse`, `docstore`, `wsdl`,
  `realtime`, `messenger` — see the scaffolding-coverage audit) ship
  with edit-hints and next-steps as a contract requirement from day
  one.
- The `--table X --quote` override flag reserved by ADR-0062 is
  unaffected. It stays parsed but not yet wired (that is
  tina4-python#123's decision to make).
- The envelope stays a public contract. A future breaking change bumps
  to `v2` under its own ADR.
- The scanner is a literal string match, not a parser. If a project
  contains user code carrying `tina4:edit` markers, `tina4 doctor` or a
  future `tina4 edit-hints` verb can grep the whole `src/` tree for a
  project-wide "what still needs my attention" list. Comments have zero
  runtime effect; users strip them freely when done.
