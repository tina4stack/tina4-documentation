# ADR-0100: the CSP nonce is not injected into a directive the app opted into `'unsafe-inline'`

- Status: accepted
- Date: 2026-10-23
- Context: refines ADR-0088 (the per-response CSP nonce), the security-headers
  contract fixture (`securityheaders_contract.json`), SECHDR-DEC-01 (the strict
  default `default-src 'self'`); tina4-php#330

## Context

ADR-0088 mints one nonce per response and injects `'nonce-<X>'` into `script-src`
and `style-src` so the framework's own inline content runs under the strict
default policy. The injector added the nonce to whatever CSP it was handed -
including an app's own `TINA4_CSP` - because "it works for the default policy and
for a user-set policy alike" read, at the time, like a feature.

It is a regression. Under CSP Level 2 and later a browser **ignores
`'unsafe-inline'` in any directive that also lists a nonce or a hash**. So an app
that had deliberately set, say, `script-src 'self' 'unsafe-inline'` through
`TINA4_CSP` - the ordinary state of an app not yet ready for a nonce-only policy -
had every one of its inline `<script>` blocks, `style="..."` attributes and
`on*=` handlers silently blocked the moment the framework appended its nonce.
There was no setting to turn the injection off. The failure never showed up in
`curl` or a server-side test, only in a real browser, which is why it shipped and
survived from 3.13.143 to 3.13.153 (tina4-php#330).

The app's explicit `'unsafe-inline'` is a deliberate choice. The framework must
not quietly cancel it.

## Decision

When the injector reaches `script-src` or `style-src` and the directive's
resolved value already carries `'unsafe-inline'`, it adds **no** nonce:

- a directive **present** in the policy with `'unsafe-inline'` is left exactly as
  the app wrote it;
- a directive **absent** from the policy whose fallback `default-src` carries
  `'unsafe-inline'` is **not** spawned with a nonce - it falls back to
  `default-src` on its own, so the inline the app allowed keeps working.

Everything else is unchanged. The strict default policy (`default-src 'self'`,
no `'unsafe-inline'`) is still nonced in both directives, so the framework's own
inline content runs exactly as ADR-0088 intends; an explicit directive that does
not opt into inline (`script-src 'self' https://cdn.example`) is still nonced;
and a directive that opts into inline on one axis but not the other (inline
scripts, strict styles) gets the nonce only on the strict axis. The framework's
own inline assets, when the app has chosen `'unsafe-inline'`, simply ride that
same allowance - they need no nonce because inline is already permitted.

This keeps the contract honest: the framework hardens the *default*, and respects
an operator who has explicitly chosen otherwise, rather than overriding them.

## Consequences

- An app that sets `'unsafe-inline'` in `TINA4_CSP` renders again; the nonce no
  longer cancels its inline content.
- An app on the strict default loses nothing - the nonce mechanism is untouched.
- The rule is per-directive and identical across all four frameworks, pinned by
  the `csp-nonce-respects-unsafe-inline` invariant in `securityheaders_contract.json`
  and proven on the real injector (a pure string transform, no mocks) in each.
- An app that WANTS the strict nonce-only policy keeps it by not writing
  `'unsafe-inline'` - the framework never adds it, only declines to fight it.
