# ADR-0092: tina4-go CLI support - `tina4 init go` scaffold and a tree-sitter-go grammar for `tina4 metrics`, gated by parse health

Status: Accepted (2026-10-01)
Date: 2026-10-01
Context: scoping spike, `plan/go/ARCHITECTURE.md`
Relates to: ADR-0002 (metrics engine in the Rust CLI), the Pascal-declined precedent (`tina4/src/metrics.rs` `pascal_is_not_claimed`)

## Context

The `tina4` Rust CLI already treats a language as a small, closed set of touch
points. `tina4 init` dispatches to a `scaffold_<lang>` function for python, php,
ruby, nodejs and tina4js. `tina4 metrics` measures a corpus with tree-sitter, and
five grammars are wired today - Python, PHP, Ruby, TypeScript (also serving JS) and
Rust - through a `Lang` enum and a handful of `match` sites. Rust was added so the
engine could measure its own language. Pascal was DECLINED: `tree-sitter-pascal`
could not parse Delphi 10.3+ inline loop variables, 51.5% of the tina4delphi corpus
fell in parser ERROR regions, and the CLI refuses any grammar below
`MIN_PARSE_HEALTH = 0.95`. A missing number is recoverable; a confident wrong one
is not.

Go needs both touch points to be a first-class Tina4 target: `tina4 init go` to
scaffold a project, and a `go` arm in the metrics engine so the maintainability and
complexity gate covers Go code the same way it covers the other five.

## Decision

1. **`tina4 init go`** adds a `scaffold_go(path)` writing `go.mod`, the entry file
   (`main.go` / `app.go`), and `.gitignore`, reusing the shared directory set and
   the `.env` writer. The alias/validation lists, the `scaffold_project` dispatch,
   the language prompt, usage strings, and the runtime/package-manager checks each
   gain a `go` arm. `tina4 serve` gains a Go detection marker (`go.mod` / `main.go`),
   a `default_port` (the next free after nodejs 7148), a `cli_name`, and the
   compile-and-bounce serve path of ADR-0089.

2. **`tina4 metrics` Go grammar** adds one `tree-sitter-go` crate and a `Go` variant
   to the `Lang` enum, which the compiler then forces through every per-language
   `match` (extension map, `is_code_line`, `is_decision`, `is_scope_boundary`,
   `is_function_node`, `is_class_node`, `is_type_decl_node`, `is_import_node`,
   `extract_import_specs`, `resolve_import`, inline-test detection). `.go` maps to
   `Lang::Go`.

   The grammar ships ONLY if it clears the same bar Pascal failed: the Go corpus
   must parse at >= 95% health (`MIN_PARSE_HEALTH`). Unlike Pascal, Go has a mature,
   actively maintained `tree-sitter-go`, so clearing the bar is expected - but it is
   proven by a `go_parse_health` test on the real tina4-go source, not assumed, and
   if it ever falls short `.go` is left unclaimed exactly as `.pas` is.

## Estimated binary-size cost

One grammar crate. The five current grammars total about 6 MB of C parser code; the
most recent single addition, `tree-sitter-rust`, cost +1.07 MB (8.68 MB -> 9.75 MB,
macOS arm64, size-optimised release profile). `tree-sitter-go` should land in the
same ~0.5-1 MB range. No other Cargo change is required for the grammar itself.

## Resolved (2026-10-01)

- **Default Go port: 7149** (the next free after Node's 7148). Confirmed.
- **CLI work is sequenced LATE, after the core is real.** The port runs on plain
  `go build` + `go test` (and the fixture contract runner of Phase 0) until the
  framework core exists; only then are `tina4 init go`, the `tina4 serve` Go arm
  (ADR-0089), and the `tina4 metrics` grammar wired. This keeps the early phases
  unblocked by CLI work and matches the roadmap's ordering (CLI in Phase 5).
- The metrics grammar still ships ONLY if the real tina4-go corpus parses at >= 95%
  health (`MIN_PARSE_HEALTH`), proven by a `go_parse_health` test, never assumed.

## Consequences

- `tina4/Cargo.toml` gains one crate; `src/metrics.rs`, `src/init.rs`,
  `src/detect.rs`, `src/main.rs` each gain a Go arm.
- The metrics gate (`tina4 metrics --fail-on`) then holds tina4-go to the same
  maintainability and complexity floor as the other five languages.
