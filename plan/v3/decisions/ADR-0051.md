# ADR-0051: Systemic ORM row-cap - unbounded reads, pagination the only limiter

Date: 2026-08-10
Status: Proposed
Supersedes: none (net-new cross-cutting decision). Builds on ADR-0043 (Accepted), which
established unbounded-by-default as a correctness requirement for the PAGINATE envelope
(a `total` is only honest if it is a real `COUNT(*)`, never the length of a capped read);
this ADR EXTENDS that same rule across all five ORM read paths, not just the read feeding
pagination. Consolidates the row-cap clauses that `features/023-scopes.md`,
`features/021-relationships.md`, `features/022-imperative-relationships.md` and
`features/024-paginated-results.md` each surface; those feature docs point here for the
single rule.

## Context

The ORM read surface carries a silent default row cap in five different places, with four
different values, measured across the four languages:

| read path | default cap |
| --- | --- |
| `scope()` | 20 (Python/PHP/Node) / unbounded (Ruby) |
| `has_many()` | 100 (Python/PHP/Node) / unbounded (Ruby DSL) |
| `QueryBuilder#get` | unbounded (its `LIMIT 100` was deliberately removed) |
| `Model.where` | 20 (Python/PHP/Node) / nil (Ruby) |
| `Model.all` | 100 (Python) |

This is not five bugs; it is one missing decision applied inconsistently five times. Every
one of these truncates SILENTLY, which is the one behaviour a caller cannot detect without
counting rows they do not have. Feature 24 turns it from a preference into a correctness
requirement: a paginate envelope's `total` is a `COUNT(*)` over the filter, but if the read
feeding the result is silently capped at 100, a 250-row table reports `total = 100` and
`total_pages = 5` - both wrong, and wrong in a way that looks authoritative. The envelope
launders a truncation into a fact.

## Decision

- **Every ORM read is unbounded by default.** No read path (`scope`, `has_many`,
  `QueryBuilder#get`, `where`, `all`, and any future path) carries a silent default row cap.
  This matches the precedent already set when `QueryBuilder#get`'s `LIMIT 100` was removed.
- **Explicit `limit`/`offset` is the ONLY thing that limits rows.** A caller that wants a
  bounded read asks for one; pagination is that ask. A scope's declared `limit`/`offset`
  reach `where` (fixing the Ruby scope bug), and they are honored, not silently dropped.
- **`total` is always a true `COUNT(*)` over the filter**, never the length of a returned
  page and never a capped read. A paginate envelope cannot report a number a capped read
  produced.
- **Removing a cap is breaking and permitted before 3.14.** A caller that unknowingly relied
  on an implicit cap now receives all matching rows; the migration is to add an explicit
  `limit`/pagination where a bound is wanted. One `Breaking:` entry covers the whole surface.

## Consequences

- Breaking across `scope`, `has_many`, `where`, `all` and the imperative relationship methods
  in the languages that currently cap; additive where a path was already unbounded (Ruby, and
  `QueryBuilder#get`).
- The enforcement gate is Feature 24's honest-total case: a 250-row table, a 20-row page,
  `total == 250`. It fails today wherever a read in the chain truncates, so it is the single
  test that proves the whole rule rather than a note in a plan.
- Each affected feature's fixture asserts no-silent-truncation (a read over more rows than the
  old cap returns them all), and the pagination fixture asserts the honest total.
- Gated in the build phase by the shared fixtures for Features 5, 21, 22, 23 and 24 across
  four fail-closed runners; no framework code changes in the audit phase.
