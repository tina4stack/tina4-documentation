# ADR-0030: A query-cache key names the DATABASE it came from

- **Date:** 2026-08-04
- **Status:** Accepted
- **Scope:** The persistent DB query cache in all four frameworks. The key
  format is a wire-visible contract because entries outlive a process.
- **Relates to:** [ADR-0024](ADR-0024.md) (the swap must work),
  [ADR-0012](ADR-0012.md) (settle contracts against real-world frameworks),
  [ADR-0021](ADR-0021.md) (session identity never reaches a cache key).

## The decision

> **A query-cache key is derived from `engine://host:port/database` plus the SQL
> plus the parameters. Two databases sharing one cache backend can never serve
> each other's rows.**
>
> Credentials are excluded. Nothing per-process is included.

## The defect this closes

Measured on 2026-08-01 and re-measured at `v3` HEAD on 2026-08-04, in all four
frameworks. The key was the SQL and the parameters and nothing else:

| framework | key |
| --------- | --- |
| python | `sha256(sql + str(params))` |
| php | `hash('sha256', sql . json_encode(params))` |
| ruby | `SHA256(sql + params.to_s)` |
| nodejs | `` `query:${sql}:${paramStr}` `` |

Nothing names the connection. So on ANY shared backend two databases cross-serve
each other's rows: two apps pointed at one Redis, or one app with a primary and
an analytics connection, silently read each other's data.

Reproduced against a real PostgreSQL 16.14 and a real Redis 7.4.10 with two
databases on ONE server differing only in name: the analytics database was
served the primary database's row.

The reason this is worse than it first reads: **identical SQL text across
tenants is the COMMON case, not an edge case.** A multi-tenant deployment runs
the same application, so it issues the same statements. The collision was the
normal outcome, not a corner.

This is a data-isolation failure wearing a caching costume. It is the same
class as ADR-0021's finding that one user's response could be served to
another, and it gets the same answer: the thing that distinguishes two callers
has to be IN the key, or the two callers must not share a cache.

## What is deliberately NOT in the key

**Credentials.** Two reasons, either sufficient. A password in the key means
every rotation silently cold-starts the cache. And a shared backend's key
namespace is visible to every tenant of that backend, so a secret must never be
folded into it. The username is out for the same reason plus a second: two
connections differing only by role read the SAME rows and should share the
entry.

**Anything per-process.** No pid, no object id, no random salt. Those would
isolate the databases by accident, and destroy the entire point of a SHARED
cache - no instance would ever hit another instance's entry, so the cache would
be a per-process cache with a network round trip bolted on. This is pinned by a
negative test in all four (`the cache key is stable for the same database`),
because it is the obvious wrong way to make the positive test pass.

## Breaking, and the migration

**Every entry already in a persistent cache becomes a MISS on upgrade**, because
the key format changed. Nothing needs to be done: the cache refills from the
database on first read. Expect one cold-cache period per deployment, sized by
`TINA4_DB_CACHE_TTL`. Call `cache_clear()` once after deploying if you would
rather the old entries were removed than orphaned.

Applications not running `TINA4_DB_CACHE=true` are unaffected.

This cost is accepted rather than mitigated. A cold cache is safe. Cross-served
rows are not, and there is no key format that is both compatible with the old
one and correct.

## Why not the alternatives

**Separate the backends instead of the keys.** Telling operators to give each
database its own Redis makes correctness depend on deployment discipline, and
fails silently when someone does not. ADR-0024 rule 1 is that the developer's
code is written against the CONTRACT: a contract that is only safe under an
undocumented deployment constraint has not been kept.

**A configurable key prefix.** Also correct if set, also silent if not, and it
is one more thing that can disagree with the URL - exactly the two-places-hold-
one-fact shape ADR-0024 already rejects for `_BACKEND` versus `_URL`.

**Hash the whole URL.** Simplest, and wrong: it puts the password in the key.

## How it is held

`plan/v3/fixtures/cache_contract.json`, invariant
`the-cache-key-carries-database-identity`, with the four suites it names. The
negative cases carry the weight: key stability for one database, and credential
exclusion.
