# ADR-0067: Database drivers and optional servers are application dependencies, never framework runtime dependencies

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release (tina4-ruby, tina4-nodejs, tina4 CLI)

## Context

Tina4's core promise is zero third-party dependencies. By September 2026 the
four frameworks had drifted apart on one question: who installs a database
driver, or a server the app may never run?

- **Python** had it right. `dependencies = []`, `sqlite3` is in the standard
  library, and every other driver is an extra the app asks for
  (`tina4-python[postgres]`), imported lazily with an install hint.
- **PHP** had it right. The PDO drivers are PHP extensions the app enables;
  composer only suggests them.
- **Node** listed `pg`, `mongodb`, `redis` and the AWS S3 SDK as
  `optionalDependencies`. npm installs optional dependencies by default, so
  every `npm install tina4-nodejs` pulled four drivers the app may never load.
- **Ruby** declared `sqlite3` as a hard runtime dependency (tina4-book#100:
  `tina4 init ruby && tina4 serve` crashed without it), plus the Puma server,
  and a string of gems Ruby already ships or that Tina4 could own:
  `gem install tina4ruby --explain` listed 15 gems.

A driver declared by the framework installs for every app, whatever database
it uses. It also compiles native code on install (sqlite3, pg), widens the
supply-chain surface, and pins a version the app may need to move.

## Decision

A database driver, a queue or cache client, or an optional server is an
**application** dependency. The framework never declares it at runtime. It
loads it lazily at the point of use, and when it is missing it fails there
with a message that names the fix.

1. **Lazy load, actionable error.** The first connection to an engine loads
   its driver. A missing driver raises the language's load error with the
   package name and the command that adds it, in the shape the other drivers
   already use:

   ```
   The 'sqlite3' gem is required for SQLite connections. Add gem "sqlite3"
   to your Gemfile (tina4 init ruby does this for you), or install one of:
       bundle add sqlite3     # if your project uses Bundler
       gem install sqlite3    # bare driver
   ```

   Nothing loads a driver at boot unless the configuration asks for that
   engine, so an app without the driver still boots.

2. **The scaffold declares what the scaffold uses.** `tina4 init <lang>`
   binds a SQLite database in `.env`, so the generated manifest carries the
   SQLite driver where the language does not ship one: `gem "sqlite3"` in the
   Ruby Gemfile. `tina4 update` and `tina4 upgrade` add that line to an
   existing Ruby Gemfile that lacks it, so a project scaffolded while
   tina4ruby still bundled the driver keeps its database on the next update.
   "SQLite works out of the box" is kept by the scaffold, not by the gem.

3. **Per framework.**

   | Framework | Before | After |
   | --- | --- | --- |
   | Python | `sqlite3` stdlib, extras for the rest | unchanged |
   | PHP | PDO extensions, composer `suggest` | unchanged |
   | Node | `pg`, `mongodb`, `redis`, S3 SDK as `optionalDependencies` (installed by default) | optional `peerDependencies` (never installed); `node:sqlite` is built in |
   | Ruby | `sqlite3` runtime gem; Puma runtime gem | `sqlite3` in the scaffold Gemfile, lazy `Tina4.require_sqlite3!`; Puma opt-in, the built-in stdlib server by default |

4. **Development dependencies are allowed.** A framework repo may keep a
   driver as a development dependency so its own suite can exercise the real
   engine (tina4-ruby keeps `sqlite3`, `pg`, `mongo` that way). It is never
   installed for an app.

5. **What the language already ships is used, not declared.** Tina4 does not
   declare a default gem or package (Ruby's `json`), and where the language
   moved something out (Ruby's `base64`, `net-smtp`, `net-imap`, `rexml`), the
   small slice Tina4 needs is owned in the framework on the standard library
   (`Tina4::Base64`, `Tina4::SmtpClient`, `Tina4::ImapClient`,
   `Tina4::XmlParser`) instead of being declared.

## Test contract

- A real process that genuinely cannot load the driver (Ruby: no Bundler, an
  empty gem home, every other activated gem on the load path) opens a SQLite
  connection and gets the actionable message; the same process boots when no
  SQLite database is configured.
  (`tina4-ruby/spec/sqlite3_optional_spec.rb`)
- The gemspec / package manifest is checked: no runtime dependency outside the
  pinned set, and the replaced or moved names may never come back.
  (`tina4-ruby/spec/zero_dependency_gemspec_spec.rb`)
- The CLI scaffold writes the driver line, and the update path adds it to a
  real Gemfile exactly once. (`tina4/src/init.rs` tests)
- Proof run: a fresh `tina4 init ruby` served `/health` and a SQLite-backed
  route; the same project with the line removed failed at boot with the
  message above.

## Consequences

- `gem install tina4ruby` stops compiling sqlite3 for apps that use
  PostgreSQL, and `npm install tina4-nodejs` stops pulling four drivers.
- An existing Ruby app that relied on tina4ruby to bring sqlite3 must declare
  it. `tina4 update` does that for it; an app updated by hand gets the error
  message above, which says what to add.
- A driver's version is the app's choice, so the framework has to keep working
  across the driver versions an app is likely to pick.
