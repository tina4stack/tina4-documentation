# ADR-0105: the Kafka queue backend durably commits consumer-group offsets and consumes externally-produced records, in all four frameworks

- Status: Accepted
- Date: 2026-11-05
- Context: tina4-python#274 (a Kafka consumer never committed offsets for
  externally-produced records, so the group never advanced and replayed the
  topic on every restart), ADR-0022 (the queue's at-least-once promise and its
  decisions 2, 3, 4 and 8), the Tina4 #264 raw-produce contract. Cross-framework
  conformance change, not a new contract.

## Context

ADR-0022 (2026-08-01) already settled what the queue promises and how Kafka must
keep it: decision 2, "on Kafka a retry re-produces the record and commits past
the original"; decision 3, "an acknowledgement names its message ... never held
in a single slot"; decision 4, "complete() is terminal ... never redelivered,
including across a consumer restart"; and decision 8, whose forward fix for Node
was "a persistent connection held on the backend instance, the way Python, PHP
and Ruby already do it ... it is what makes the backend correct, and the refusal
stands only until it lands."

The measured table in ADR-0022 showed every framework's Kafka backend VIOLATING
that contract, and the violations were still live:

- Python committed only when a record's payload carried a top-level `id`. An
  externally-produced record (Debezium CDC, another service) has none, so it was
  popped as job id "unknown", never committed, and every restart or rebalance
  replayed the topic. Two in-flight records that shared a payload id also shared
  one commit slot (tina4-python#274).
- PHP tracked its read position only in memory and `acknowledge()` was a no-op,
  so every consumer replayed the whole topic from offset 0 on restart. An
  id-less external record also crashed `pop()` (the Job requires an id).
- Node drove Kafka through a stateless child process per operation, kept no
  cursor, always fetched offset 0, and had no acknowledge at all - it could
  never drain a topic. The Queue facade REFUSED `new Queue("kafka")` outright as
  ADR-0022 decision 8's holding position.
- Ruby committed with a bare `@consumer.commit`, which commits the consumer's
  whole polled position and ignores which message is acknowledged - the "single
  last-message slot" decision 3 forbids. Its `from_payload` read a nil "payload"
  off a bare external record, losing the data.

So #274 as reported was Python-specific, but the same defect family - Kafka
offsets not committed durably per-record - was present in all four.

## Decision

The Kafka backend in every framework durably commits consumer-group offsets,
per-record, and consumes externally-produced records. Concretely:

- An acknowledge (complete/fail/reject/retry) commits the offset JUST PAST the
  acknowledged record (`offset + 1`), keyed to THAT record, never a single
  last-slot or the whole polled position. The consumer resumes from the
  committed offset, so a completed job is never re-delivered, including across a
  restart (ADR-0022 decisions 2, 3, 4). A job popped but not acknowledged still
  replays - at-least-once is preserved.
- An externally-produced record (no Tina4 envelope, hence no top-level id) is
  consumable: its whole value is delivered as the payload, byte-for-byte, and
  its `topic:partition:offset` coordinate becomes its id, which is what the
  acknowledge maps back to the offset. The low-level read that exposes a record
  exactly as it sits on the wire stays bare, so the #264 raw-produce contract
  (a foreign consumer reads the unenveloped schema) is unchanged.
- Offset ops go to the group coordinator, resolved with FindCoordinator and
  retried while a fresh cluster is still creating `__consumer_offsets`. The
  frameworks that speak the wire protocol by hand (PHP, Node) use the lowest
  non-flexible API versions - FindCoordinator v1, OffsetFetch v1, OffsetCommit
  v2, the "simple consumer" pattern (generation -1, empty member id) - so no
  JoinGroup/Heartbeat membership is needed and the existing framing helpers
  apply, the same rationale as the Produce v3 / Fetch v4 floor.
- Node lands ADR-0022 decision 8: the connection is now PERSISTENT, held in a
  worker thread with its own event loop (the socket, the read cursor and the
  committed offsets live there), driven synchronously from the main thread over
  a SharedArrayBuffer and `Atomics.wait`. `new Queue("kafka")` is no longer
  refused. RabbitMQ stays refused until it gets the same treatment.

This is CONFORMANCE to ADR-0022, not a new contract: decision 5's named Kafka
exceptions remain exactly `size()` returns 0, dead-consumer reclaim via the
consumer-group session timeout, and no native priority. Offset durability was
never one of them.

## Consequences

- A Kafka consumer of any topic - Tina4-produced or external - now advances and
  survives a restart in all four frameworks, instead of replaying from the
  seed. This is the behaviour the docs always described.
- BREAKING in Node in the useful direction: `backend: "kafka"` was refused and
  now works. Ruby's commit semantics change from whole-position to per-record;
  an app relying on the old imprecise commit (there is no correct reason to) sees
  tighter, correct redelivery.
- A new low-level bare read (`dequeue`) sits beside the normalising consume path
  in PHP and Node so the #264 wire-fidelity test keeps inspecting raw bytes
  while the Queue facade gets an id for every record.
- Proven against a live broker in each framework (no mocks): a completed job does
  not replay across a restart, an un-acknowledged job DOES replay (the negative
  control, which proves it is the durable commit and not an in-memory cursor that
  suppresses the replay), and an external record is consumed byte-for-byte and
  commits durably. Each gate is mutation-proved - disabling the commit (or, in
  PHP, the resume) turns the positive and external cases red while the control
  stays green. Python ships as tina4-python#276; PHP, Ruby and Node as
  `fix/kafka-durable-offsets-274`.
