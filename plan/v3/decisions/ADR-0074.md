# ADR-0074: Every database connection is lent to one borrower at a time, with an async twin for every call

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4-python (Database facade, ORM, the sqlite/postgres/mysql/mssql/firebird/mongodb/odbc adapters); the shape is the reference the other three frameworks will follow
- **Decision owner:** Andre van Zuydam
- **Governs fixture:** `plan/v3/fixtures/pool_isolation_contract.json`
- **Supersedes:** nothing. No accepted ADR decided connection lending or the async surface before this one; it writes the contract down for the first time.

## Context

The report was plain: "psycopg2 is blocking routes". Measured on `v3` against the real engines, on the built-in server and uvicorn alike, three separate faults were sharing the blame.

A synchronous driver call made from an `async def` route ran on the event loop itself. While the statement was in flight every other request on that loop waited for it, so a two-second query made a no-database `/ping` wait three-and-a-half seconds. `fetch()` made it worse by running the statement twice - once for the rows, once for a COUNT it did not always need.

The pool underneath was the second fault. The default `pool=0` shared one connection, so a second database request queued behind the first, and, worse, two concurrent requests shared a single transaction - a rolled-back insert was committed by another request's commit. The `ConnectionPool` that did exist handed the same adapter to several threads at once on a round-robin, and its checkin did nothing. MySQL's server process died under it; MSSQL and Firebird answered 500.

The third fault only showed itself once the first two were fixed. ODBC's `execute()` committed every statement inside an open transaction, so a later `rollback()` had nothing left to undo.

## Decision

One rule governs the connection, and one rule governs the call.

**A connection is lent to one borrower at a time.** `ConnectionPool` (`tina4_python/database/pool.py`) is bounded and exclusive. `checkout()` blocks until a connection is free, up to `TINA4_DB_POOL_TIMEOUT` (30 seconds), and then raises `DatabasePoolExhausted` - a `TimeoutError` subclass whose message names `TINA4_DB_POOL`, so the fix travels with the failure. Every facade operation borrows a connection and returns it. A transaction, and a manual-commit write, keeps its connection for the length of the context through a `ContextVar` - thread-local for synchronous code, task-local for a coroutine - so a nested facade call lands on the same connection and two contexts can never read or commit inside each other's transaction. A context that ends with a connection still open rolls it back and returns it, so a forgotten commit cannot leak one.

**Every call has an async twin.** `run_async()` and the `*_async` methods on `Database`, the ORM and the query builder borrow their connection on the event loop and then run the very same synchronous method on the pool's own worker thread. The loop stays free, the results and the errors are identical on every engine, and no new dependency joins the framework to make it happen. When `TINA4_DEBUG` is on, a synchronous database call made on a thread that is running an event loop warns once for that route and tells the developer how to fix it - declare the route with a plain `def`, or `await` the async twin. The warning asks the loop whether it is running through the supported `asyncio.get_running_loop()`, behind the debug gate, so it never touches the hot synchronous path in production.

**`fetch()` runs the statement once.** The COUNT probe runs only when the page cannot prove the total on its own; a shared `_total_from_page()` helper reads the total straight off a short or empty page, and Postgres wraps the probe it does need in a SAVEPOINT so a failed COUNT cannot poison an open transaction. A one-second statement that used to take 1.96 seconds now takes 0.99.

**SQLite writes begin immediately.** A SQLite transaction opens with `BEGIN IMMEDIATE`, which takes the database's write lock at the start instead of on the first write, so an open transaction and a waiting standalone writer no longer deadlock each other; an in-transaction statement skips the process write lock because the `BEGIN IMMEDIATE` already holds it.

The default pool size is 10. It is big enough that ordinary concurrent requests never queue, small enough that a handful of workers stay well under PostgreSQL's default of a hundred connections, and connections open lazily so an idle app still holds one. `pool=0` keeps its documented meaning of a single connection, now lent exclusively rather than shared. An in-memory SQLite database is always one connection, because a second one would open a different, empty database.

## How this reconciles with ADR-0086

ADR-0086 owns SQLite path resolution - which file a connection string opens, whether a parent directory is created, and the refusal of a relative path that escapes the project root. This ADR owns what happens to a connection once it exists - how it is lent, how a transaction holds it, and, for SQLite, how the write lock is taken. The two never touch the same decision. The pool asks the resolver for a path and then opens connections to whatever it returns; `BEGIN IMMEDIATE` changes when SQLite's own write lock is acquired, not which file is locked. ADR-0086's `0775` parent-creation and its escape refusal are unchanged, and the pool honours the single resolved path for every connection it opens to a file-backed SQLite database.

## Backward compatibility

Synchronous callers keep working with no change to their code. The one deliberate behavioural difference is the default: an unset `pool=` used to mean one shared connection and now means `TINA4_DB_POOL`, or 10 when that is unset too. That change is the point - the old shared connection is exactly what let two requests commit inside each other's transaction. An application that never set `pool=` will now open up to ten connections instead of one; an application that wants the old single connection pins it with `pool=0` or `TINA4_DB_POOL=0`, and it is now lent exclusively, so it serialises rather than corrupting.

## Consequences

- Concurrent requests no longer share a connection or a transaction, on any engine. The `pool_isolation_contract.json` fixture enumerates the invariants - a connection is never lent to two borrowers at once, a transaction keeps one connection until it commits, exhaustion raises `DatabasePoolExhausted` naming `TINA4_DB_POOL`, a cancelled async call returns its connection, and a sync call on the event loop warns once per route - and each carries a real regression test, no mocks, proven on every engine the lab provisions.
- The async twins give an `async def` route a way to reach the database without blocking the loop, with identical results to the synchronous call.
- The ODBC transaction-flag fix means `rollback()` inside an ODBC transaction now undoes what was written.
- An application that leaned on the old shared-connection default - two requests seeing one transaction - was relying on a bug and will change behaviour; the remedy is a real pool, which is now the default.

## Alternatives considered

- **A connection per request, opened and closed each time.** Rejected: opening a connection to Postgres or MSSQL on every request is the cost the pool exists to avoid, and it caps concurrency at the server's connection limit with no backpressure of its own.
- **A separate async driver per engine (asyncpg, aiomysql, motor).** Rejected: it doubles the adapter surface, forces a new runtime dependency for each engine, and would drift from the synchronous path it is meant to mirror. Running the proven synchronous method on a worker thread keeps one code path and one set of results.
- **Leaving `fetch()` to always COUNT.** Rejected: the second statement is pure waste on the common case of a page that already knows its own total.
