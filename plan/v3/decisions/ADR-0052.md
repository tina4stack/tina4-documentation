# ADR-0052: Frond extension registration scope follows the call target

Date: 2026-08-14
Status: Accepted
Supersedes: none (resolves Feature 56 EX-DEC-01)

## Context

Frond exposes `add_filter`, `add_global`, and `add_test` on both the class and an
instance. Before this decision, all four implementations made an instance call
write through to the class registry. A registration intended for one renderer
therefore leaked into every renderer constructed later in the process, surprising
applications and breaking test isolation.

## Decision

- A call on the Frond class is process-global. Every Frond instance constructed
  after that class registration inherits it.
- A call on a Frond instance is instance-local. It changes that renderer only and
  never writes the class registry.
- The rule applies identically to filters, globals, and tests in Python, PHP, Ruby,
  and Node.js, using each language's idiomatic method spelling.
- Existing flattened-at-construction lookup remains unchanged. This ADR does not
  make class registrations retroactive to instances that already exist.

## Consequences

This is breaking before 3.14.0 for code that accidentally relied on an instance
registration leaking globally. Such code must register on `Frond` itself. Code
wanting per-renderer customization keeps calling the instance method and now gets
the isolation that call target communicates.

The shared `frond_extensibility_contract.json` fixture and its four named suites
gate class propagation plus instance isolation for filters, globals, and tests.
