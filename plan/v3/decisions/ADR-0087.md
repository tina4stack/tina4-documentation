# ADR-0087: a session's expiry slides on activity - a request that touched a stored session re-writes it to move the deadline forward

- Status: accepted
- Date: 2026-10-01
- Context: ADR-0024 (a pluggable subsystem's contract), ADR-0027 (a zero `write()`
  ttl means the configured default), the session concurrent-save merge
  (`fix/session-save-keeps-a-concurrent-logout`), session contract fixture
  invariant `ttl-is-honoured-by-every-backend`

## Context

The concurrent-save fix taught every framework's `Session.save()` to re-read the
stored record and merge only this request's own changes onto it, so a request in
flight across a logout no longer writes a stale whole-snapshot back and logs the
user in again. While proving that fix against real backends, a second,
pre-existing divergence surfaced - this time in WHEN a session's expiry clock
resets. Measured 2026-10-01 at v3 HEAD against a real file backend:

| Framework | a read-only request's `save()` | expiry measured from |
| --- | --- | --- |
| PHP | re-writes the (unchanged) record | last ACTIVITY (any request) |
| Python | writes nothing | last CHANGE |
| Ruby | writes nothing | last CHANGE |
| Node | writes nothing | last CHANGE |

The ttl VALUE already agreed across the stack (ADR-0027); what disagreed is the
moment the absolute deadline is stamped. PHP re-writes an unchanged session on
every request that reads it, so the `now + TINA4_SESSION_TTL` deadline moves
forward and the session expires after a span of INACTIVITY. The other three
write nothing when a request only read the session, so the deadline is frozen at
the last write and the session expires a fixed span after its last CHANGE, even
while the user is actively clicking.

The consequence is not academic, and it is a security-and-usability outcome, not
a storage one. With `TINA4_SESSION_TTL=1800`, a user reading pages every few
minutes stays logged in indefinitely on PHP (each request slides the deadline)
but is logged out 30 minutes after their last write on the other three - mid
session, while active. Identical application code, a different session lifetime
per framework: precisely the divergence ADR-0024 exists to prevent.

## Decision

**A session's expiry slides on activity. Any request that started a session the
store already holds re-writes it on `save()` - writing the re-read, merged
record - which re-stamps the backend deadline to `now + TINA4_SESSION_TTL`.
Expiry is therefore measured from the last request that touched the session, not
from its last change.**

The re-write is the SAME merged record the concurrent-save contract already
computes, so sliding the deadline never clobbers a concurrent change: a
read-only request writes back exactly what the store holds now (plus nothing of
its own), and a request that did change something writes its merge. The existing
guards are unchanged and take precedence over the slide:

- A request with NO session (no id issued, or the id was never adopted) writes
  nothing - there is no deadline to move.
- A session another request ENDED (the record is gone) is not re-created to
  slide it: the request forgets it and ends, exactly as the concurrent-save
  contract says, and no cookie goes out.
- A backend read that FAILED leaves the deadline untouched and keeps the dirty
  flag for a later retry - an unreachable store never silently drops or extends
  a session.
- `TINA4_SESSION_TTL=0` still means "never expires" (ADR-0027): the slide
  re-stamps a zero deadline, which every read path still treats as immortal.

PHP already behaves this way and is the reference for this decision. Python, Ruby
and Node adopt it.

## Authority

Under ADR-0012 (standard > mainstream frameworks > libraries > internal
precedent):

- **Standard tier.** PHP's native session is sliding by construction: the
  session file's mtime is touched on every `session_start()`, and garbage
  collection is measured from that mtime, so the language standard the framework
  mirrors expires on inactivity. Tina4's own `TINA4_SESSION_TTL` is documented as
  the span of inactivity after which a session expires.
- **Mainstream frameworks lean sliding for the inactivity promise.** Laravel's
  `session.lifetime` is "the number of minutes ... the session is allowed to
  remain idle", and it re-writes the session each request so idleness, not age,
  is what expires it. `express-session`'s `rolling` option exists for exactly
  this and is the recommended setting for an idle-timeout. Django is the
  static-by-default outlier (`SESSION_SAVE_EVERY_REQUEST` is opt-in), so the tier
  is not unanimous - but the behaviour an operator means by "a session that times
  out after N minutes" is the sliding one, and it is the only one that does not
  log an actively-working user out mid-session.
- **Internal precedent: PHP already does this**, and a session lifetime is an
  authentication outcome, so a split is a security divergence, not a cosmetic
  one (the ADR-0024 test).

## Consequences

- **PHP is the reference and needs no change.** Its `Session::save()` already
  re-writes an unchanged record to move the deadline forward, asserted by
  `testADowngradeStaysDownWhenTheSlowRequestOnlyRead` and the read-only
  expiry-forward assertion in `SessionConcurrentRequestsTest`.
- **Python, Ruby and Node are OWED and land in `fix/session-save-keeps-a-concurrent-logout`.**
  `Session.save()` re-writes the merged current record for a request that started
  a stored session even when this request changed nothing, re-stamping the TTL.
  The "a read-only request writes nothing" test is replaced by "a read-only
  request moves the expiry forward" (the stored deadline advances, the stored
  data is unchanged), proven against a REAL backend on a real clock - no mock.
- **No-mock correction (Python).** The Python PR tested the unreachable-backend
  and read-only paths with `monkeypatch` on the store's own `read`/`write`. That
  violates the no-mock rule and diverged from the siblings, which point a REAL
  Redis handler at a closed port and read outcomes off a real file store. Python
  is brought to the real approach in the same pass.
- **Cost, accepted.** A read-only request now issues one backend write to slide
  the deadline. That is one write per request that calls `save()` on a stored
  session - the price of an inactivity timeout, and what PHP-native and Laravel
  already pay. It stays concurrent-safe because the write is the merged current
  record, not a stale snapshot.

## Alternatives rejected

- **Freeze expiry at last change (the Python/Ruby/Node behaviour).** Rejected: it
  logs an actively-working user out mid-session and contradicts the documented
  "expires after N of inactivity" promise. It is also the minority position
  internally (1 of 4 did the opposite).
- **Make sliding opt-in (a `TINA4_SESSION_ROLLING` flag), default off.** Rejected
  for now: it keeps the stack behaving differently out of the box unless an
  operator discovers the flag, and the inactivity timeout is what Tina4 already
  documents. A flag to opt OUT (fixed-age sessions) can be added later under its
  own ADR if an application needs an absolute cap; it does not block closing the
  divergence.
