# ADR-0087: WebMCP lets a running Tina4 app hand an agent its own actions as tools

- **Status:** Accepted
- **Date:** 2026-09-28
- **Scope:** tina4-js (the `tina4js/webmcp` client module) and the Frond render path in all four backends (tina4-python, tina4-php, tina4-ruby, tina4-nodejs); the client module is the reference the Frond bridge follows
- **Decision owner:** Andre van Zuydam
- **Governs fixture:** `plan/v3/fixtures/webmcp_contract.json` (owed; Phase 2 writes it, see `plan/webmcp.md`)
- **Supersedes:** nothing. No accepted ADR decided a runtime tool surface before this one; it writes the contract down for the first time.

## Context

An agent that wants to use a web app today reads the screen. It looks at the rendered page, guesses which element is the "filter" control, clicks it, waits, reads the screen again, and hopes the layout did not move. The page never told it what it can do; the agent reverse-engineered it from pixels, and a small style change breaks the whole guess.

WebMCP is the other way round. A running app declares its own actions - `filterOrders`, `checkout`, `addToCart` - as Model Context Protocol (MCP) tools, each with a name, a JavaScript Object Notation (JSON) schema for its arguments, and a handler. The agent asks the app what it can do, gets a real list, and calls a tool directly. No scraping, no clicking, no guessing. The browser's emerging `navigator.modelContext` surface is where this is standardising, so an agent that speaks it should find a Tina4 app already talking.

This is NOT the dev surface Tina4 already ships. Feature 101 mounts an MCP server at `/__dev/mcp` behind `TINA4_DEBUG`, and that surface is about coding AGAINST the project - query the database, read the live API index, run a migration - for a tool like Claude Code driving the framework while a developer builds. WebMCP is the production cousin: it is about USING the running application the developer shipped, its own business actions, with the end user present. One is a workbench for the person writing the code; the other is a control surface on the app the code became. They must never be conflated, they carry different trust, and a tool on one is not a tool on the other.

Tina4 renders in two ways, and the two ways force two different answers to one question: where does a tool's handler actually run?

- A **tina4-js single-page application (SPA)** renders in the browser. The state lives in signals, right there on the page. A tool that filters the order list only has to read and write those signals, so it registers and runs in the page, and no server is involved at all.
- A **Frond-rendered page** is templated on the server. The page the browser holds is HTML the backend already produced; the logic that would answer a tool call lives back on the server, in Python, PHP, Ruby or Node. A tool here cannot do its work in the page, because the thing it needs to touch is not in the page. It has to bridge to the backend.

So the same author writing `webmcp.tool('filterOrders', ...)` needs the same API in both places, but under it the call travels two different roads.

## Decision

Tina4 gains WebMCP as an opt-in capability, and four things are settled.

**1. The author API conforms to the standard AND wraps it.** Tina4 implements the browser `navigator.modelContext`-style registration surface directly, so an agent that already speaks the standard finds the app's tools with no Tina4-specific knowledge. On top of that surface sits the Tina4-idiomatic wrapper, `webmcp.tool(name, schema, handler, { risk })` - declarative, signals-aware, one call to register one tool. The wrapper is what a Tina4 developer writes; the conformance layer is what the agent reads. The author API is identical in both execution modes below, so a tool moves between an SPA page and a Frond page without its declaration changing.

**2. There are two execution paths, and which one runs is decided by how the page was rendered, not by the author.**

- On a **tina4-js SPA page the tool registers and runs in the page.** The handler is a browser function that reads and writes signals. There is no backend round-trip, no server dependency, and this is the default - it is the core of the module and the common case.
- On a **Frond-rendered page the tool call bridges to the backend.** The page declares its tools, the agent invokes one, the request crosses to the server, the server runs the handler against the real application state, and the result comes back. The backend bridge is REQUIRED only for the Frond/server-side-rendered (SSR) case. It is conditional, never the default, and it is exactly the piece of work that lands in all four backends, because Frond rendering exists in all four.

**3. Consent is tiered by the risk a tool declares.** Every tool carries a risk level. A `risk: 'read'` tool is read-only - it filters, it searches, it reads state - and it is auto-allowed, because reading the thing the user is already looking at needs no ceremony. A `risk: 'write'` tool mutates or has a side effect - it checks out, it deletes, it sends - and it will be surfaced to the user through a Tina4 user-interface primitive and executed only after the user explicitly approves it. The tiering applies in both execution modes: an SPA write tool prompts in the page, and a Frond write tool prompts before the bridge runs, with the consent decision enforced server-side so the surface cannot be driven past it.

**4. It ships as an optional, tree-shakeable, zero-dependency module.** The client side is `tina4js/webmcp`, imported only by an app that wants it, and it adds nothing to an app that does not. The Frond bridge is an optional per-backend capability, off unless the app turns it on. Tina4's core stays zero-dependency; WebMCP does not change that, because it is a module you opt into, not a tax the core pays. "On all four frameworks" is satisfied honestly: every backend already serves a tina4-js frontend, so the client module reaches all four the day it ships, and the Phase 2 Frond bridge brings the SSR path to all four behind one shared contract.

## Why the render mode decides the path, and the author never sees it

The temptation is to pick one execution model and make everything obey it. Both single choices are wrong for Tina4, and the reason is the same: Tina4 genuinely has two rendering modes, and neither one is a second-class citizen.

Force everything through the backend and an SPA tool that only wanted to flip a signal now needs a live server it never needed before - a frontend feature made to depend on a backend, which is the wrong default for the mode that has no backend logic at all. Force everything into the page and a Frond tool cannot reach the server state that is the only place its work can happen. The render mode already knows the answer, so the render mode decides, and the author writes one declaration either way. That is the whole point of putting the wrapper over the conformance layer: the ergonomics stay flat while the plumbing underneath forks.

## Why read is quiet and write asks

A consent prompt on every tool call trains the user to click "allow" without reading, which is worse than no prompt, because it looks like safety and is not. Reading the order list the user is already staring at is not a moment that deserves a modal. Checking out is. So the risk level the tool declares is the gate: read flows, write asks, and the ask is a real Tina4 UI primitive the user recognises, not a browser dialog the agent could race. On the Frond path the approval is enforced on the server, so an agent cannot reach past the prompt by calling the bridge directly - the bridge itself will refuse a write it has no consent for.

## Consequences

- Phase 1 ships `tina4js/webmcp` on its own: the `webmcp.tool()` API, the `navigator.modelContext` conformance shim, tool lifecycle tied to the component and signal lifecycle (a tool registers when its component mounts and unregisters when it unmounts, so a tool never outlives the page state it drives), the tiered-consent UI primitive, JSON-schema tool descriptions, and a tree-shakeable zero-dependency export. It reaches all four backends immediately, because all four serve a tina4-js frontend.
- Phase 2 ships the Frond bridge at parity across Python, PHP, Ruby and Node. A page declares its tools in the Frond route or template, the server registers them and exposes them over a production MCP surface distinct from `/__dev/mcp`, and a shared `webmcp_contract.json` fixture (the ADR-0024 one-fixture-one-checker pattern) behaviour-locks the four so they answer a tool call the same way. Each framework carries real, no-mock regression tests that drive a real tool call end to end.
- The production MCP surface opens real questions the Phase 2 plan owns and this ADR flags: authentication and consent on a server surface an agent can reach, the session model that ties a tool call to the user whose consent it carries, and abuse of a server-side tool that reaches outbound. These share the trust-boundary posture of ADR-0082 (credentials and development endpoints keep explicit trust boundaries) and the two-layer capability-plus-authorization gate feature 101 already proves for `/__dev/mcp`; the WebMCP surface inherits that discipline rather than inventing its own.
- Tina4's zero-dependency core is unchanged. The client module and the bridge are both opt-in, and an app that ignores WebMCP pays nothing for it.

## Alternatives considered

- **A Tina4-native tool API only, no conformance layer.** Rejected: the browser is standardising on `navigator.modelContext`, and an agent will speak that. A native-only surface risks diverging from what agents actually call, so a standard-speaking agent would find nothing. Conforming AND wrapping gets both - the agent reads the standard, the developer writes the ergonomic wrapper.
- **Always prompt for consent.** Rejected: a prompt on every read is noise, and noise trains the user to approve without reading, which defeats the consent it pretends to provide. Read auto-allows; write asks.
- **Backend-only execution for every tool.** Rejected: it couples a frontend feature to a live backend even for an SPA tool that only touches signals in the page. That is the wrong default - the backend bridge is for the Frond case that genuinely needs the server, and nowhere else.
- **WebMCP in the tina4-js core rather than an optional module.** Rejected: it would put the bundle cost on every app whether it wants the feature or not, and it breaks the opt-in ethos that keeps the core lean. It ships as `tina4js/webmcp`, tree-shakeable, imported only when wanted.
- **A blanket production-MCP surface added to all four backends.** Rejected: it is over-broad. Only the Frond SSR case needs the backend to run a tool. Adding a general runtime MCP mount to every backend would build a large, always-on server surface for a case that does not need it, when the scoped Frond bridge covers the one render mode that does.
