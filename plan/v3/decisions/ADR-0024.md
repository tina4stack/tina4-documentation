# ADR-0024: The swap must work - a provider is an env var, never a code change

- **Date:** 2026-08-01
- **Status:** Accepted
- **Scope:** EVERY pluggable subsystem in all four frameworks - database adapters,
  session backends, cache backends, queue backends, DocStore, the WebSocket
  backplane, and anything pluggable added later.
- **Relates to:** [ADR-0004](ADR-0004.md) (best implementation prevails),
  [ADR-0012](ADR-0012.md) (settle contracts against real-world frameworks),
  [ADR-0023](ADR-0023.md) (the queue case that surfaced this).

## The principle

Owner, 2026-08-01:

> "It allows a developer to use sqlite on local and upgrade it to the environment
> they have on the server."
> "This principle is a core one across the whole of tina4."

Stated so it can be checked:

> **The developer's code is written against the CONTRACT, never the PROVIDER.**
> Swapping the provider - sqlite for postgres, file for kafka, memory for redis,
> local for production - changes ONE env var and NOTHING ELSE. Identical
> application code, identical OBSERVABLE outcome, on every provider.

The engine or protocol may differ underneath. What the developer WRITES, and what
they can READ BACK, must not.

## Why this needs to be written down

It was already the design intent everywhere - `Database` over five engines,
DocStore's SQLite fallback for Mongo, four session backends, seven cache
backends, four queue backends. But it was NEVER STATED, so each subsystem
rediscovered the same failure independently, and each time it was found by
accident rather than by a check.

Measured breaks, all found on 2026-08-01, all the same shape:

| subsystem | how the swap broke |
| --------- | ------------------ |
| queues    | Python dead-letters into a private `failed/` DIRECTORY; PHP and Ruby publish to a `<topic>.dead_letter` QUEUE. A dead-letter handler written locally on the file backend finds NOTHING after deploying onto Kafka. |
| queues    | Node's `rabbitmq` and `kafka` backends THROW at construction. You can develop locally on file and then CANNOT move to the server's environment - the app does not start. |
| sessions  | ADR-0021 hashed the on-disk NAME. That invalidated file and memcached sessions and NOT redis/valkey/mongo/database. One upgrade, different outcome per provider. |
| cache     | `RedisBackend.clear()` is a no-op on the raw RESP path - the DEFAULT zero-dependency install - in Python, PHP and Ruby. The advertised global write-invalidation does not hold by default. |
| database  | PHP Postgres `affectedRows` always returned 0 on update (the only adapter not routing writes through `execute()`); MySQL reports the FIRST id of a multi-row insert, not the last. |
| database  | Transactional DDL exists only on PostgreSQL. The same migration file that applies atomically on postgres half-applies on mysql/sqlite/firebird. Shipped as a DOCUMENTED CAVEAT - which under rule 2 is a defect, not a resolution. |

Every one is the same defect: **the abstraction promises substitutability and one
provider quietly does not deliver it**, and it is discovered in production.

## The rule

1. **Same code, same observable outcome.** If a developer must write a conditional
   on the configured provider, the abstraction has failed.
2. **A documented caveat is still a broken swap, and it gets FIXED.** Owner,
   2026-08-01: "If something is broken on postgres then it needs to be fixed."
   Writing "on mysql this differs" in a docblock does not make the swap work - it
   records that it does not, and then everyone stops looking. A caveat is a BUG
   REPORT filed against ourselves, not a resolution.

   There is no "acceptable divergence" tier. An earlier draft of this ADR had one,
   and the transactional-DDL caveat walked straight through it. If the contract
   promises it, every provider does it, or the contract is narrowed so it no
   longer promises what one provider cannot deliver. Both are honest; a footnote
   is not.

   **The open case this settles:** migrations are documented as per-file atomic,
   but only PostgreSQL has transactional DDL - mysql, sqlite and firebird
   auto-commit it, so a multi-statement migration that fails midway leaves earlier
   statements applied. That has been shipped as a caveat. Under this rule it is a
   defect with two honest exits: make the runner emit a compensating path on the
   auto-commit engines, or narrow the contract to "one logical change per file,
   atomicity NOT promised" and say so in the API, not in a footnote. Deciding
   which is owed; leaving it in a docblock is not an option.
3. **No provider may silently do less.** A method that exists and no-ops is worse
   than one that is absent - absent fails loudly at the call site. If a provider
   cannot honour an operation it must RAISE, naming the provider and the
   operation.
4. **The zero-dependency default counts.** It is the provider every developer
   starts on, so a break there is the one most likely to reach production
   unnoticed. `RedisBackend.clear()` no-opping on the default RESP path is
   exactly this.
5. **Every pluggable subsystem declares its contract in ONE place**, and a new
   provider is written against that, not by reading a sibling implementation.
6. **The contract is machine-checked by a SHARED FIXTURE plus ONE checker
   script** - not a runner per framework. See the mechanism section below; the
   proven pattern adds ZERO code to the four frameworks.

## The CONFIGURATION surface must be uniform too

Substitutability is not only about runtime behaviour. If every subsystem invents
its own way to be pointed at a provider, the developer learns four dialects to do
one thing, and the swap is harder than the code it was meant to simplify.

`Database` already demonstrates the right form and is the reference: ONE URL,
`driver://host:port/database`, five engines, and the SCHEME selects the provider.

Measured on 2026-08-01, nothing else follows it:

| subsystem | selects the provider by      | points at it with |
| --------- | ---------------------------- | ----------------- |
| Database  | the URL SCHEME               | `TINA4_DATABASE_URL` + `_USERNAME` / `_PASSWORD` |
| Cache     | `TINA4_CACHE_BACKEND` (name) | `TINA4_CACHE_URL` + `_USERNAME` / `_PASSWORD` |
| Session   | `TINA4_SESSION_BACKEND` (name) | **no `_URL`** - `TINA4_SESSION_MONGO_URI`, per provider |
| Queue     | `TINA4_QUEUE_BACKEND` (name) | nothing uniform - per-backend vars |

Three problems, each already a known bug shape:

1. **The provider is stated twice and the two can disagree.** Cache and session
   need `BACKEND=redis` AND `URL=redis://...`. Two places holding one fact, with
   nothing checking they agree - the same shape as the credential env drift that
   cost two debugging sessions today. The Database has no such problem because
   the scheme IS the selection.
2. **Session config grows PER PROVIDER.** `TINA4_SESSION_MONGO_URI` means adding
   Redis needs `TINA4_SESSION_REDIS_URL`, and so on. A config surface that grows
   with the provider list is the opposite of substitutable - the whole point is
   that adding a provider changes nothing the developer touches.
3. **`TINA4_SESSION_MONGO_URI` and `TINA4_SESSION_MONGO_URL` BOTH exist.** Two
   spellings for one value. Exactly `_USER` vs `_USERNAME`, which was green for
   months only because a stale container hid it.

**Decision: every pluggable subsystem takes the Database's form.**

    TINA4_<SUBSYSTEM>_URL       driver://user:pass@host:port/name
    TINA4_<SUBSYSTEM>_USERNAME  optional override
    TINA4_<SUBSYSTEM>_PASSWORD  optional override

The SCHEME selects the provider, so a separate `_BACKEND` name cannot contradict
the URL. `_BACKEND` is retained as an accepted alias for the transition and for
the providers that genuinely have no URL (memory, file), where it stays the
selector.

Consequences:
- One dialect to learn, and it is the one the Database already taught.
- Adding a provider adds a SCHEME, not an env var.
- `known_vars()` in the CLI stays the single source of truth for the env surface
  (see the env-uniformity work), and `check_env_contract` can then assert the
  shape mechanically rather than by inspection.

## Do it with as little code as possible

Owner, 2026-08-01: the other core principle is to implement things with AS LITTLE
CODE AS POSSIBLE. That constrains how this ADR is satisfied, and an earlier draft
of it broke the rule.

MEASURED, the existing pattern costs almost nothing:

  plan/v3/fixtures/dispatch_contract.json   167 lines   (the contract)
  plan/v3/fixtures/health_contract.json     133 lines
  scripts/audit-dispatch-contract.py                    (ONE checker)
  scripts/audit-health-contract.py                      (ONE checker)

and **zero lines in any of the four frameworks.** The fixture is an INDEX of
invariants; each names the suite that proves it, and the four suites carry
IDENTICAL case names so they compare line by line. The checker reads the index
and verifies the cases exist. The proof lives in tests that already had to be
written anyway.

An earlier draft of rule 6 said the fixture is "run against every provider in all
four frameworks", which implies a data-driven RUNNER per framework - sixteen new
pieces of machinery to check something the existing tests already assert. That is
the cure being bigger than the disease. Corrected.

So the cost of holding a subsystem to this ADR is: one JSON file, one entry in an
existing checker, and case names in tests that must exist regardless. If a
proposal to satisfy this ADR costs materially more than that, the proposal is
wrong, not the principle.

The same rule applies to the CONTRACT surface itself. When PHP declares a
`QueueBackend` interface and the other three do not, the minimal answer is NOT to
hand-write three more interfaces to drift apart - it is ONE shared contract file
that all four are checked against. Fewer places to state one fact is the whole
point; it is also, not coincidentally, what stops the drift this ADR exists to
prevent.

## Why the shared fixture is the mechanism, not an extra

The subsystems that already have one are the subsystems where drift stopped being
found by accident: `fixtures/dispatch_contract.json` (8 invariants, 108
case x framework pairs) and `fixtures/health_contract.json`. The write-path
fixture found 5 real bugs on the way in.

Everything in the table above is a subsystem WITHOUT a fixture. That is not a
coincidence, and it is the same lesson as `check_env_contract`: a principle
nobody executes is a principle that drifts. A note is not a control.

Owed, and not yet built: `queue_contract.json`, `session_contract.json`,
`cache_contract.json`, `docstore_contract.json`. The database write path is
partly covered by the existing write-path fixture.

## What a provider audit asks

For each operation on the contract, for each provider:

- Does it return the same SHAPE?
- Does the data land somewhere the contract's own reader can find?
- Does a subsequent read see the same thing?
- On failure, does it fail the same way - raise vs falsy vs silent?
- Does anything no-op?

## Non-goals

This is not a demand that providers perform identically. Postgres is faster than
SQLite; Kafka scales past a file. PERFORMANCE and CAPACITY are properties of the
deployment and are expected to differ.

Nor does it forbid provider-specific FEATURES reached explicitly - a caller who
asks for a Postgres-only capability by name has left the contract knowingly, and
that is fine.

What it does NOT excuse is a defect on any one engine. PostgreSQL in particular is
the engine most Tina4 deployments actually run, so "it only breaks on postgres" is
the worst possible reading of a bug, not a mitigating one.

The rule governs the CONTRACT surface only: what the documented API promises must
be true of every provider that claims to implement it.
