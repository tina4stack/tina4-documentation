# ADR-0036: find() is DEFERRED, and there is ONE sort contract

- **Date:** 2026-08-04
- **Status:** Accepted
- **Scope:** `DocStore` in all four frameworks - what `find()` returns, and what
  `sort()` accepts on it.
- **Relates to:** [ADR-0025](ADR-0025.md) (the fallback imitates the driver -
  core rule unchanged and applied here), [ADR-0035](ADR-0035.md) (which recorded
  this defect as open), [ADR-0012](ADR-0012.md) (settle a contract against
  real-world libraries), [ADR-0024](ADR-0024.md) (the swap must work).

## The problem, measured

The framework's own documented PHP example, from `tina4-php/CLAUDE.md`:

```php
foreach ($orders->find(['total' => ['$gt' => 5]])->sort('total', -1)->limit(10) as $doc)
```

works on the SQLite fallback and **fatals on a real MongoDB**:

    Error: Call to undefined method MongoDB\Driver\Cursor::sort()

`MongoDB\Collection::find($filter, $options)` EXECUTES, and the
`MongoDB\Driver\Cursor` it returns has no `sort`, `limit` or `skip` at all,
because by then the query is already on the wire. PHP's driver takes those as
find() OPTIONS.

This is ADR-0025's defect class - a spelling that works on the fallback and
breaks on the swap - and it is simultaneously a First Principle violation,
because it is a PUBLISHED example that does not run.

Checking the whole grid rather than the one reported symptom found more. Four
chain cases, two providers, four frameworks - 32 combinations, measured
2026-08-04 against a real MongoDB 7.0.39:

| framework | provider | `sort(field, dir)` | `sort(map)` | `sort(pairs)` | `sort.skip.limit` |
| --------- | -------- | ------------------ | ----------- | ------------- | ----------------- |
| php    | fallback | ok | **TypeError** | ok | ok |
| php    | mongo    | **fatal** | **fatal** | **fatal** | **fatal** |
| ruby   | fallback | ok | ok | ok | ok |
| ruby   | mongo    | **ArgumentError** | ok | **TypeMismatch** | **ArgumentError** |
| node   | fallback | ok | **TypeError** | ok | ok |
| node   | mongo    | ok | ok | ok | ok |
| python | fallback | ok | **ValueError** | ok | ok |
| python | mongo    | ok | ok | ok | ok |

**10 of 32 failed.** The failures divide into two distinct defects:

1. **PHP's chain does not exist on the driver** (5 of the 10). The whole of
   PHP's Mongo column, plus the map spelling on its fallback.
2. **The MAP spelling was fallback-broken in THREE frameworks** (php, node,
   python). It worked on every driver and raised on the fallback:
   `TypeError: DocStoreCodec::extract(): Argument #1 ($field) must be of type
   string`, `TypeError: keyOrList is not iterable`, and
   `ValueError: too many values to unpack (expected 2)`. All three have the same
   cause - iterating a map as though it were a list of pairs.

Ruby's own divergence is the mirror image: its fallback accepted all three
spellings and `Mongo::Collection::View#sort` takes exactly ONE spec document, so
the two-argument form the framework documents raised `ArgumentError` and the
pairs form reached the server as an ARRAY and came back
`[14:TypeMismatch]: Expected field sort to be of type object`.

## The decision

> **1. `find()` is DEFERRED on both providers.** It returns a chainable query
> that ACCUMULATES `sort`/`limit`/`skip` and executes only when iterated or
> materialised. It never issues a query itself.
>
> **2. There is ONE sort contract.** `sort()` accepts a field name plus a
> direction, a list of `[field, direction]` pairs, OR a `field => direction`
> map - and all three mean the same thing on both providers, in all four
> frameworks.

Both follow ADR-0025's surviving core rule rather than competing with it. A lazy
chainable cursor is what `Mongo::Collection::View` and pymongo's `Cursor` already
are; the three sort spellings are exactly what pymongo and the Node driver
already accept. ADR-0012's authority order puts a mainstream library's API above
internal precedent, and here two of our own implementations were already correct,
so the work was to bring the other two to that shape, not to invent one.

## What changed, per framework

| framework | change |
| --------- | ------ |
| **php** | `getCollection()->find()` returns `DocStoreQuery`, a deferred chainable query that calls `find($filter, $options)` once, at materialisation. `Cursor::sort()` and `DocStoreQuery::sort()` both go through `docStoreSortSpec()`. |
| **ruby** | `MongoView#sort` normalises all three spellings to the driver's single spec document. `Cursor#sort` shares the same `DocStore.sort_spec`. |
| **node** | `Cursor.sort` accepts an object or a `Map` via `sortSpec()`. The chain already worked on both providers. |
| **python** | `Cursor.sort` accepts a `Mapping` via `sort_spec()`. The chain already worked on both providers. |

**Python is the master and Python was broken**, so it was FIXED here rather than
left as the thing the others imitate. The alternative - mirroring a master defect
into three frameworks to preserve parity - produces four broken frameworks and
calls it consistency.

### PHP's deferred query, and why it is not a facade

`DocStoreQuery` re-declares exactly four members (`sort`, `limit`, `skip`, and
the materialisers `getIterator`/`toArray`/`toList`) and forwards everything else
to the driver cursor through `__call`. That keeps ADR-0035's property: nothing on
the driver becomes unreachable.

**Iteration semantics are the fallback's, deliberately.** Building the chain
issues NO query; materialising issues exactly ONE; iterating a second time issues
another, because a `MongoDB\Driver\Cursor` can only be walked once and the
fallback re-runs its SQL per iteration. Nothing is buffered, so a large unlimited
result still streams rather than being pulled into an array to make re-iteration
work.

The rejected alternative was executing in `find()` and re-executing on each
chained call. It would pass a naive test and issue N queries for one chain.

## The canary, flipped

ADR-0035 pinned this defect as a canary: the PHP harness asserted that the
fallback cursor's fallback-only method set was exactly `['sort', 'limit',
'skip']`, so the gap could not widen unnoticed. That assertion now asserts `[]`.

A canary that documents a defect is worth having; a canary that documents a
CLOSED defect is a lie waiting to be believed, so it was flipped rather than
left to rot.

`docstore_contract.json`'s `the-call-site-surface-is-identical` gains the case
`the cursor chain works on both providers`, asserted in all four suites, against
both providers, using all three sort spellings. It asserts three things a
narrower test would miss:

- **skip composes** with sort and limit;
- **an ascending sort actually ascends** - a direction that was ignored entirely
  would pass a descending-only test;
- **the chain is LAZY** - a document inserted after the chain is built but before
  it is iterated must appear, which a query that ran inside `find()` would fail.

## Consequences

- The PHP CLAUDE.md caveat added by ADR-0035 - "cursor chaining is FALLBACK-ONLY
  ... do not chain if the app will ever run on Mongo" - is DELETED, because it is
  no longer true. The documented example runs on both providers now.
- ADR-0035's "Still open" section is closed. Both items it recorded (PHP's
  cursor gap, Ruby's two-argument sort) are fixed here.
- `getCollection()->find()` on the PHP Mongo path returns `Tina4\DocStoreQuery`
  rather than a wrapped `MongoDB\Driver\Cursor`. Every documented operation is
  unchanged; a class check on the return value is not, which is the same
  consequence ADR-0035 already carries for the collection itself.
- The map sort spelling is newly ACCEPTED on the fallback in php, node and
  python. That is additive - no spelling that worked before stopped working.

## What this does NOT decide

Whether `find()`'s SECOND positional argument should mean the same thing on both
providers. The fallback takes a projection there; the drivers take an options
document (`['projection' => [...]]`). ADR-0036 leaves that alone: the deferred
query passes whatever it is given straight through as driver options, so the
Mongo path takes the driver's spelling. Unifying it is a separate breaking change
and needs its own measurement.
