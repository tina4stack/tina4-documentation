# ADR-0083: The built-in GraphQL route is CSRF-safe and its fan-out is bounded

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4-python, tina4-php, tina4-ruby, tina4-nodejs (the GraphQL engine and its built-in route)
- **Decision owner:** Andre van Zuydam
- **Governs fixture:** `plan/v3/fixtures/graphql_transport_contract.json`

## Context

Two findings from the September 2026 Medium security audit concern the built-in
GraphQL transport and the cost of a single query. Recorded at the level of the
contract; exploit detail lives with the fixes.

1. **F4 — the built-in GraphQL route was open to cross-site requests.** A GET to
   the endpoint executed whatever operation it was given, including a mutation —
   and a cross-site GET carries the victim's cookies. The POST handler accepted a
   JSON body sent as `text/plain`, which a cross-site HTML form can send without
   a CORS preflight, so a forged form could drive a mutation.

2. **F2 — a single query's fan-out was unbounded.** The existing depth guard
   bounds selection-set *nesting*, but not *width*: a fragment that spreads
   another fragment many times (a "fragment bomb") stays shallow while expanding
   to millions of resolved fields, and a query with thousands of aliases of one
   field is not deep at all. Separately, a deeply nested query overran the
   *parser* before the execution-time depth guard could run — in Ruby as a
   `SystemStackError` (which is not a `StandardError`, so it escaped the
   handler's rescue as a 500), and in PHP by exhausting the process.

## Decision

Identical behaviour in all four frameworks.

1. **No mutations over GET.** The GET handler executes with mutations disallowed;
   a mutation operation received over GET is refused with a clear error. GET
   remains available for read-only queries and introspection.

2. **The POST route requires an `application/json` content-type.** A request body
   without it is refused (HTTP 415). Because a browser cannot send
   `application/json` cross-site without a CORS preflight, this forces the
   preflight — and its same-origin / allow-list check — for any cross-site
   caller, while same-origin XHR/`fetch` and server clients (which set
   `application/json`) are unaffected.

3. **A query's expanded node count is bounded.** `TINA4_GRAPHQL_MAX_NODES`
   (default `1000`; `<= 0` disables) caps the expanded selection tree — fragments
   expanded, every field including each alias counted — computed before any
   resolver runs. A fragment bomb or alias explosion is rejected with a clear
   complexity error. The count is query-structure only, so a legitimate query
   over a large result list is unaffected; the counter is itself capped by the
   budget so the check cannot be turned into the attack.

4. **The parser's own recursion is bounded.** The parser enforces
   `TINA4_GRAPHQL_MAX_DEPTH` while building the selection tree, so a deeply nested
   query fails with a clean, caught parse error instead of overflowing the parser
   stack (Ruby) or exhausting the process (PHP). Ruby raises a `GraphQLError` (a
   `StandardError`) at the bound so it can never escape as a 500.

## Consequences

- `TINA4_GRAPHQL_MAX_NODES` joins `TINA4_GRAPHQL_MAX_DEPTH` as a per-deployment
  DoS knob with the same default and semantics across the four frameworks.
- A client that POSTed GraphQL with a non-JSON content-type must set
  `application/json`; a client that ran mutations over GET must use POST. Both
  are intended breaks and are called out in the upgrade notes.
- Each control ships with a red-first regression test in all four frameworks
  (fragment bomb, alias explosion, deep-nest parser bound, and the CSRF GET/POST
  cases), each with a positive twin so it cannot pass vacuously.
