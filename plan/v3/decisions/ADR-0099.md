# ADR-0099: Tina4-Driven Development (T4DD) - plan-driven development; the plan is the spine, and spec, ADR, fixture and task plan are its layers

- Status: Accepted
- Date: 2026-10-19
- Deciders: maintainer
- Supersedes: none
- Related: ADR-0098 (Spec-Driven Development - the spec layer this sits over), ADR-0004 (best implementation prevails), ADR-0024 (one shared fixture + one checker per pluggable subsystem), ADR-0043 (a documented contract cites its ADR); the `plan/` tree itself; the `tina4-maintainer` and `tina4-developer-*` skills

## Context

Tina4 already runs on one rule the maintainer skill states first: no work happens
off-plan, and every instruction is allocated to a plan. The `plan/` tree is where
the whole method lives - the master plan, the per-task plans, the decision records,
the specs and the contract fixtures all sit under it. That was never named. When we
reached for a name we borrowed "Spec-Driven Development" (SDD, ADR-0098) from the
outside toolchains (Spec Kit, Kiro) - the very ones ADR-0098 rejected as a
dependency.

The borrowed name is too small for what it labels. The spec is one layer: it carries
the WHAT (intent and the `AC-N` acceptance criteria). It does not carry the WHY (the
ADR), the executable proof (the contract fixture), or the day-to-day tracking (the
task plan with its parity dashboard, tests, bugs and commits). Calling the whole
method "spec-driven" understates the ADR + fixture + task-plan machinery that was the
core long before specs were formalised.

A borrowed name also keeps inviting the "oh, it is just X" shrug. The method is
Tina4's own, so it earns Tina4's own name.

## Decision

The method is **Tina4-Driven Development (T4DD)**, and what it is in one line is
**plan-driven development**: the plan is the spine, and the rest are its layers. The
name is Tina4's own; the subtitle says plainly how it works. This renames nothing
below it and removes nothing.

1. **The plan is the single spine.** No maintenance happens off-plan. A new request
   becomes checkboxes in a plan, never a side-quest. The `plan/` tree is the one
   place the method lives.

2. **Four layers hang off the plan, each with its own gate:**

   | Layer | Lives in | Answers | Gate |
   |-------|----------|---------|------|
   | **ADR** | `plan/v3/decisions/` | WHY - the locked cross-framework decisions | the governance tests + review |
   | **Spec (SDD)** | `plan/v3/specs/` | WHAT - intent + `AC-N` acceptance criteria | `audit-spec-coverage.py` (ADR-0098) |
   | **Contract fixture** | `plan/v3/fixtures/` | EXECUTABLE - the decision proven across four languages | `audit-contract-fixtures.py` |
   | **Task plan** | `<repo>/plan/<task>.md` | HOW - scope, parity dashboard, tests, bugs, commits | the parity dashboard itself |

3. **T4DD adds no new gate.** Its enforcement is the sum of the layer gates above,
   plus `audit-truth.py` holding the docs to code reality. A separate "T4DD gate"
   would only duplicate them, so there is none. T4DD is the framing that says how the
   layers fit, not a new mechanical check.

4. **SDD is unchanged - it is the spec layer under T4DD.** ADR-0098 stands as
   written; `plan/v3/specs/` and `audit-spec-coverage.py` keep their names and
   behaviour. T4DD is the description above SDD, not a replacement for it.

5. **T4DD is plan-first by design, and says so plainly.** In the software-engineering
   literature "plan-driven" is the disciplined counterpart to "agile" (Boehm and
   Turner). Tina4 sits on the plan-driven side on purpose - but lean: the plan is a
   living markdown file backed by executable fixtures, not a heavyweight upfront
   specification. That is the honest answer to "isn't this just agile?" - no, it is
   plan-driven, and the plan is cheap to change because a fixture, not a sign-off,
   proves it.

## Consequences

- The `plan/` tree gains a name that matches its job; the maintainer and developer
  skills can frame their existing workflow as T4DD without changing a step.
- "Proven/owed" reasoning now has a clear home per layer: an ADR locks the why, a
  spec's `AC-N` names the what, a fixture case proves it, and the task plan tracks it
  across the four frameworks.
- Nothing in CI changes: the layer gates already run. T4DD is documentation of the
  method, enforced by the gates that were already there.

## Alternatives rejected

- **Keep "SDD" as the headline name for the whole method.** Rejected: the spec is one
  layer (the what). The plan is the spine, and the ADR + fixture + task-plan layers
  predate specs. A name that labels only the spec understates the method.
- **Name it only "Plan-Driven Development" (PDD).** Rejected as the headline, kept as
  the subtitle: "plan-driven" describes the mechanism well but carries the
  agile-versus-plan baggage from the literature, and a borrowed-shape name keeps the
  method anonymous. T4DD names it as Tina4's own and uses "plan-driven" to explain it.
- **Call it agile.** Rejected: Tina4 is plan-first by design. Claiming agile to sound
  fashionable would be dishonest and invites the "just another framework" shrug. T4DD
  states the real stance and owns it.
- **Add a dedicated T4DD gate.** Rejected: T4DD is enforced by the sum of the existing
  layer gates (contract fixtures, spec coverage, doc truth, governance). A new gate
  would duplicate them and drift from them.
