# ADR-0038: One canonical TINA4_TEST_* set, enforced by a gate

- **Date:** 2026-08-04
- **Status:** Accepted
- **Scope:** Every `TINA4_TEST_*` variable read by any suite in tina4-python,
  tina4-php, tina4-ruby and tina4-nodejs, plus every `.github/workflows` file
  that sets one, plus the lab's `lab-env.sh`.
- **Relates to:** [ADR-0034](ADR-0034.md) (a test may only assert on what it
  owns), the `TINA4_REQUIRE_SERVICES` no-green-skips gate.

## The problem, measured

One test PostgreSQL had **thirteen** names, and no two frameworks read the same
set. Measured 2026-08-04 on `origin/v3` at the four HEADs, counting only real
reads (`os.environ.get`, `getenv`, `ENV[]`, `process.env`), not comments:

| variable | python | php | ruby | node |
| -------- | ------ | --- | ---- | ---- |
| `TINA4_TEST_PG_URL` | 3 | 3 | - | 2 |
| `TINA4_TEST_POSTGRES_URL` | - | **4** | - | - |
| `TINA4_TEST_PG_USERNAME` | 14 | 5 | 11 | 12 |
| `TINA4_TEST_PG_USER` | **1** | - | - | **1** |
| `TINA4_TEST_PG_PASSWORD` | 14 | 5 | 11 | 13 |
| `TINA4_TEST_PG_PASS` | **1** | - | - | - |
| `TINA4_TEST_PG_DB` | 12 | 1 | 10 | 9 |
| `TINA4_TEST_PG_DATABASE` | - | **1** | - | - |
| `TINA4_TEST_PG_DB_2` | - | - | 1 | 1 |
| `TINA4_TEST_PG_HOST` | 14 | 4 | 11 | 12 |
| `TINA4_TEST_PG_PORT` | 14 | 4 | 11 | 12 |

Python read BOTH spellings of user and password. PHP had a URL variable nobody
else knew about. The same drift ran through the other services: `MONGO_URL` and
`MONGO_URI` both meant the Mongo connection string, and a `CACHE_` infix gave
Redis, Valkey, memcached and Mongo a second name each for the same endpoint.

**This is why the same class of bug kept recurring.** Twice in one night a test
skipped, someone exported the single name that one framework happened to read,
and more tests appeared: `TINA4_TEST_PG_URL` turned up 4 Node tests that had
never executed, then `TINA4_TEST_POSTGRES_URL` turned out to gate 3 PHP sites
under a different name. Both fixes were correct. Neither could have been the
last, because there was no canonical list to check against. It was an allow-list
with no single source of truth, so it rotted by addition, the same shape as the
`UNAVAILABLE_HINTS` gate.

Two live defects fell out of the measurement itself:

1. **`TINA4_TEST_MONGO_URI` was read by all four and set by nothing.** Every
   CI workflow sets `TINA4_TEST_MONGO_URL`. The DocStore and session-fallback
   suites read `TINA4_TEST_MONGO_URI` and silently fell back to a hardcoded
   default. Same shape as the PostgreSQL case, one service over.
2. **`lab-env.sh` exported both `TINA4_TEST_PG_URL` and
   `TINA4_TEST_POSTGRES_URL`**, which is what kept PHP working and hid the
   split from everyone who only ever ran on the lab.

## How the canonical name was chosen

Not by taste. Three rules, in order:

1. **Match the framework's own runtime convention.** The runtime ships
   `TINA4_DATABASE_URL`, `TINA4_DATABASE_USERNAME`, `TINA4_DATABASE_PASSWORD`,
   `TINA4_SESSION_REDIS_HOST`, `TINA4_SESSION_MEMCACHED_PORT`,
   `TINA4_SESSION_MONGO_DB`. Test variables mirror it.
2. **Where the runtime has no equivalent, the spelling the most frameworks
   already read wins.** Smallest diff, least relearning.
3. Where those disagree, say so and pick rule 1.

The grammar that falls out is `TINA4_TEST_<SERVICE>_<ATTRIBUTE>`, exactly
mirroring the runtime's `TINA4_<SUBSYSTEM>_<SERVICE>_<ATTRIBUTE>`. The service
name follows the subsystem directly.

| decision | reason |
| -------- | ------ |
| `_USERNAME`, not `_USER` | Rule 1: `TINA4_DATABASE_USERNAME`. Rule 2 agrees (3 of 4 already read `_USERNAME`). |
| `_PASSWORD`, not `_PASS` | Rule 1: `TINA4_DATABASE_PASSWORD`. Rule 2 agrees. |
| `_DB`, not `_DATABASE` | Rule 1: `TINA4_SESSION_MONGO_DB`, `TINA4_SESSION_REDIS_DB`. Rule 2 agrees (3 of 4). |
| `PG_URL`, not `POSTGRES_URL` | Rule 2: `PG_URL` is read by 3 frameworks, `POSTGRES_URL` by 1. Both hold the same kind of value, a full postgres URL. Every other attribute already says `PG`. |
| `MONGO_URI`, not `MONGO_URL` | Rule 1: the runtime declares `TINA4_SESSION_MONGO_URI` canonical and `TINA4_SESSION_MONGO_URL` a legacy alias, in `mongodb_handler.py`. Rule 2 agrees: `_URI` is read by all four, `_URL` by two. |
| no `CACHE_` infix | **Rules 1 and 2 disagree here.** Rule 2 favours `TINA4_TEST_CACHE_REDIS_URL`, read by all four, over `TINA4_TEST_REDIS_URL`, read by one. Rule 1 wins: the runtime cache is configured by `TINA4_CACHE_BACKEND` plus a single `TINA4_CACHE_URL`, and there is no `TINA4_CACHE_REDIS_URL` anywhere in it. A consumer infix also splits one endpoint into two names, which is the defect itself: `TINA4_TEST_CACHE_REDIS_URL` and `TINA4_TEST_REDIS_HOST` addressed the same Redis, on the same default port, under two names. |

Every `CACHE_` pair was confirmed to be the same service before merging, by
comparing defaults: `redis://127.0.0.1:6379` against `REDIS_HOST` +
`REDIS_PORT` defaulting to `127.0.0.1` + `6379`, and the same for Valkey
(`6380`), memcached (`11211`) and Mongo (`27017`).

Nothing was renamed on the strength of a guess. `PgTestEnv::resolve()` in PHP
parses its URL for host, port, user and password and deliberately ignores the
database in the path, because each test owns its own database name. That
behaviour is unchanged; only the variable it reads was renamed.

## The canonical set

Services, each with the attributes listed:

| service | attributes |
| ------- | ---------- |
| `PG` | `URL` `HOST` `PORT` `USERNAME` `PASSWORD` `DB` `DB_2` |
| `MYSQL` | `URL` `HOST` `PORT` `USERNAME` `PASSWORD` `DB` |
| `MSSQL` | `URL` `HOST` `PORT` `USERNAME` `PASSWORD` `DB` |
| `FIREBIRD` | `URL` `HOST` `PORT` `USERNAME` `PASSWORD` `PATH` |
| `MONGO` | `URI` `HOST` `PORT` |
| `REDIS` | `URL` `HOST` `PORT` |
| `VALKEY` | `URL` `HOST` `PORT` |
| `MEMCACHED` | `URL` `HOST` `PORT` |
| `KAFKA` | `URL` `HOST` `PORT` `CONTAINER` |
| `RABBITMQ` | `URL` `HOST` `PORT` |
| `MQTT` | `URL` `AUTH_URL` `TLS_URL` `EMQX_URL` `USERNAME` `PASSWORD` `CA_FILE` |
| `SMTP` | `HOST` `PORT` |
| `IMAP` | `HOST` `PORT` |

Plus eight test-owned values that are not service coordinates. CI and
`lab-env.sh` never set these; a test writes or toggles them to drive a code
path: `TINA4_TEST_MODE`, `TINA4_TEST_NO_REDIS_DRIVER`,
`TINA4_TEST_WRITE_PATH_URL`, `TINA4_TEST_WRITE_PATH_USERNAME`,
`TINA4_TEST_WRITE_PATH_PASSWORD`, `TINA4_TEST_FROM_DEFAULT`,
`TINA4_TEST_FROM_CUSTOM`, `TINA4_TEST_ENV_DB_URL`.

MQTT keeps four URLs because they are four different brokers: plain,
authenticated, TLS and EMQX. That is not drift.

## Where the list lives, and why not known_vars()

The list lives in **one shared fixture**, byte-identical in all four
frameworks, the pattern already proven by `write_path_contract.json`:

    tina4-python/tests/fixtures/test_env_contract.json
    tina4-php/tests/fixtures/test_env_contract.json
    tina4-ruby/spec/fixtures/test_env_contract.json
    tina4-nodejs/test/fixtures/test_env_contract.json

The obvious alternative was the tina4 client CLI's `known_vars()`, which is
already the declared truth for runtime `TINA4_*` names. It was rejected on
evidence: `known_vars()` lives in `tina4/src/env_config.rs`, a fifth repo, and
`write_env_example()` iterates it to generate `.env.example`. A test-only name
added there would be emitted into every user's `.env.example` and would ship in
a released binary. Runtime configuration stays in `known_vars()`; test service
coordinates live in the fixture. The two lists are siblings, not one list.

## The gate

A rename alone is worthless. The next person invents a fourteenth spelling and
nobody notices until a test silently skips. So each framework carries a
`test_env_contract` test that:

1. builds the canonical set from the fixture,
2. scans that framework's own suite **and its `.github/workflows`**, and
3. fails, naming the offending variable and the file it is in, on any
   `TINA4_TEST_*` token that is not canonical.

Workflows are scanned deliberately. A CI file that SETS a name no test READS is
exactly the failure that hid 4 Node tests and 3 PHP sites. The gate has to
catch a rogue set, not just a rogue read.

Two properties keep the gate honest:

- **It cannot pass vacuously.** A scanner whose glob breaks finds nothing and
  every "no violations" assertion then passes green. Each suite asserts first
  that the scan found a healthy number of tokens and saw specific known names,
  the same obligation ADR-0034 puts on a scoped probe.
- **It is mutation-proven.** Introducing a real `TINA4_TEST_PG_FOO` read must
  turn the suite red naming that variable and its file. This was run in all
  four, not reasoned about.

### What the gate matches

A name counts only where it is USED, never where it is discussed: preceded by a
quote, by `process.env.`, by `export ` anywhere on the line, or at the start of
a line. All four share one regex, published in the fixture.

Matching every `TINA4_TEST_[A-Z0-9_]*` token instead was tried and rejected: it
flagged 15 false positives on an untouched tree, because `# canonical
TINA4_TEST_PG_HOST / _PORT` in a comment yields `TINA4_TEST_PG_`. Loosening the
other way is worse. Accepting any token that is a PREFIX of a canonical name
would silently accept `TINA4_TEST_PG_USER`, one of the exact spellings this
decision retired.

`export` must NOT be anchored to the line start. All four repos ship an
`mqtt-infra.sh` that emits `echo "export TINA4_TEST_MQTT_URL=..."`, and the
anchored form matches **zero** names in that file against the unanchored form's
five. Measured, not reasoned about. Python had it right first; the other three
were corrected to match, because a gate that means four different things in four
frameworks is not a gate.

### What the gate does NOT catch

Stated plainly so nobody trusts it further than it goes:

1. **A name built at runtime.** The trailing `+` means a quoted bare prefix
   matches nothing, so `getenv('TINA4_TEST_' . strtoupper($engine) . '_HOST')`
   is invisible. This is why the Ruby queue specs were de-interpolated rather
   than declared. The cheap close is to treat a quoted bare `TINA4_TEST_` as a
   violation; it must land in all four together or not at all.
2. **A name outside the `TINA4_TEST_` namespace**, by construction. See the
   `MONGO_TEST_URI` case below.
3. **A name used mid-line with no quote, no dot and no `export`** - inline env
   in a `run:` step, a YAML inline flow map, destructuring. None occur today in
   any of the four.

### The four defects this actually fixed

Not hypothetical. Each was a test that could not run:

| defect | effect |
| ------ | ------ |
| Node CI set `TINA4_TEST_POSTGRES_URL`; Node reads `TINA4_TEST_PG_URL` | the live-PostgreSQL assertions in `databaseUrlRedaction` and `databaseUrlCredentials` had never executed in CI |
| PHP CI set `TINA4_TEST_MONGO_URL`; no PHP test read it, and the mongo cache tests read `TINA4_TEST_CACHE_MONGO_URL`, which nothing set | CI's Mongo coordinates never reached the tests, which used a hardcoded default |
| Ruby CI set `MONGO_TEST_URI`; four Ruby specs read `TINA4_TEST_MONGO_URI` | the DocStore and cache specs fell back to `192.168.88.99`, the lab box, which a GitHub runner cannot reach |
| `TINA4_TEST_MONGO_URI` set by nothing anywhere | same fallback in all four |

Dynamic names are the remaining declared hole, and the list of them is kept at
one. PHP builds
`TINA4_TEST_DB_NONEXISTENT_ . uniqid()` to get a name guaranteed to be unset,
which is the point of that test; its literal prefix is declared in the fixture.
The Ruby queue specs used to interpolate `TINA4_TEST_#{backend.upcase}_HOST`,
which no static scan can resolve. They now use an explicit per-backend map, so
the gate can see every name. Prefer an explicit name over a clever one: the
scanner cannot check what it cannot resolve.

## Consequences

- Test-only variables, so there is no user-facing break. No application reads
  any `TINA4_TEST_*` name.
- Every `.github/workflows` reference was updated in the same pass, in all four
  repos. An unreconciled CI file would silently turn tests off, which is worse
  than the drift it replaced.
- `lab-env.sh` must drop `TINA4_TEST_POSTGRES_URL` (now `TINA4_TEST_PG_URL`,
  which it already exports) and gain `TINA4_TEST_MONGO_URI`, which nothing has
  ever set despite all four frameworks reading it.
- Adding a variable now has one procedure: put it in the fixture first, in the
  right service, then use it. A name that is not in the fixture does not exist.
