# ADR-0060: Streaming events, multimodal input, and reusable Api.stream primitives

- **Status:** Accepted
- **Date:** 2026-08-22
- **Scope:** Feature 140, streaming and multimodal AI, plus reusable HTTP streaming
- **Decision owner:** Andre van Zuydam
- **Supersedes:** ADR-0053 point 5 (the "ordered text deltas" streaming rule)

## Context

ADR-0053 shipped `Ai.chat`, `complete`, and `embed` in 3.13.101 with a deliberate,
minimal surface. Two of its scope exclusions have since become concrete blockers:

1. Streaming yields only text strings. An agent loop that reads that stream cannot
   see `tool_calls`, cannot know when the model wants to run a tool, and cannot
   distinguish a normal `finish_reason` from an early close. Callers who need this
   already hand-roll ~40 lines of raw HTTP + SSE parsing per app, defeating the
   value of the shared client.
2. Message content is required to be a string. Multimodal providers (OpenAI GPT-4o,
   Anthropic Claude vision, local llama.cpp vision builds) all accept image parts as
   an array. The current `_validate_messages` rejects these arrays with
   `AiConfigError`.

In parallel, every consumer that streams HTTP anywhere (LLMs, log tails, event
feeds, chunked downloads) re-implements a bespoke chunk reader on top of the
language's stdlib HTTP. `Api` today buffers everything into `Promise<T>` / dict /
array and returns it whole, so any streaming consumer bypasses the shared client
entirely. This is the third gap.

## Decision

Tina4 3.13.113 ships one contract in all four backend frameworks:

1. `Ai.chat(stream=True)` returns an iterator of typed `AiEvent` records. The
   union is `text_delta` / `tool_call` / `done` / `error`. Each event carries only
   the fields listed under **Event shape** below. Text is delta-per-chunk (live
   typewriter UX). Tool calls are **aggregated**: the client buffers each
   OpenAI-style `tool_calls[i].function.arguments` fragment (or Anthropic's
   `input_json_delta` events) and emits a single `tool_call` event when the
   arguments JSON parses cleanly. Malformed tool-call JSON raises `AiParseError`.
2. `Ai.chat(stream=False)` continues to return `ChatResponse`. Its shape is
   unchanged from ADR-0053.
3. `message.content` may be a string OR a list of parts. Each part is one of
   `{type: "text", text: str}` or `{type: "image", source: str}` where `source` is
   either a `data:<media_type>;base64,<payload>` URI or an `https://` URL. The
   client translates to each provider's shape internally
   (OpenAI/local: `{type: "image_url", image_url: {url}}`;
   Anthropic: `{type: "image", source: {type: "base64"|"url", media_type, data|url}}`).
   Malformed parts (unknown `type`, missing `text`/`source`, non-string values)
   fail with `AiConfigError` before any request is sent.
4. `Api.stream_bytes(url, opts)`, `Api.stream_lines(url, opts)`, and
   `Api.stream_sse(url, opts)` are new. They are the primitive, the newline-buffered
   convenience, and the SSE-framing convenience respectively. Each returns the
   language's natural iterator (Python generator, PHP `Generator`, Ruby yielding
   block, Node `AsyncGenerator`). `stream_sse` handles `data:` / `event:` / `id:` /
   `retry:` fields, blank-line event boundaries, multi-line data concatenation,
   and the OpenAI `[DONE]` sentinel.
5. `Ai.chat` streaming is implemented on top of `Api.stream_sse`. Both share one
   proto3-of-SSE reader; the language's stdlib HTTP client is the only wire dep.
6. The shared `ai_client_contract.json` fixture is extended with four new
   invariants (event-shape, tool-call-aggregation, multimodal-content-array,
   api-stream-primitives) each proven by real-socket runners in all four
   frameworks against a fixture server that replays canned SSE bytes. No mocks.
7. This is a breaking change. Callers of `Ai.chat(stream=True)` written for
   3.13.112 receive `AiEvent` records instead of strings starting in 3.13.113.
   The migration is `for chunk in stream:` becomes
   `for event in stream: if event.type == "text_delta": ...`. No shim.
   Rationale: ADR-0053 pre-1.0 stream API, feedback_no_aliases forbids alias
   methods, feedback_breaking_changes permits breaks for v3 parity.

## Event shape

```
AiEvent :=
  | { type: "text_delta",  text: string }
  | { type: "tool_call",   id: string, name: string, args: object }
  | { type: "done",        finish_reason: string, usage?: {prompt_tokens, completion_tokens, total_tokens} }
  | { type: "error",       message: string, code?: string }
```

The `done` event fires exactly once, after all `text_delta` and `tool_call`
events. `error` may fire only in place of `done` and only for errors observed
mid-stream (mid-stream 5xx from the provider, malformed JSON, dropped
connection past the retry ceiling). Pre-stream errors continue to raise
`AiHTTPError` / `AiTimeoutError` / `AiConfigError` as ADR-0053 specified.

## Public surface

| Concept | Python | PHP | Ruby | Node.js |
| --- | --- | --- | --- | --- |
| Streaming chat | `for event in Ai.chat(msgs, stream=True):` | `foreach (AI::chat($msgs, stream: true) as $event)` | `Tina4::AiClient.chat(msgs, stream: true) { \|event\| }` | `for await (const event of Ai.chat(msgs, {stream: true}))` |
| Byte stream | `Api.stream_bytes` | `Api::streamBytes` | `Api.stream_bytes` | `Api.streamBytes` |
| Line stream | `Api.stream_lines` | `Api::streamLines` | `Api.stream_lines` | `Api.streamLines` |
| SSE stream | `Api.stream_sse` | `Api::streamSse` | `Api.stream_sse` | `Api.streamSse` |
| Multimodal part | `{"type": "text", "text": ...}` / `{"type": "image", "source": ...}` | array with same keys | Hash with same keys | Object with same keys |

Names follow each language. Wire bytes, event shape, message shape, and error
behaviour are identical across languages and provider-neutral.

## Non-goals

Tool **execution** (running the tool and feeding the result back) remains
outside this ADR. The client emits the `tool_call` event; the application
runs the tool and constructs the next `Ai.chat` call itself. Agent loops,
tool registries, conversation-state helpers, and structured JSON schemas
are not in 3.13.113 and require their own audited decisions.

Vision output (image generation) and audio in/out are not in 3.13.113. If
either lands later, they extend the content-part union with `{type: "audio"}`
or add a new `image_url` in a `text_delta` sibling event; nothing in this
ADR precludes that.

Server-Sent-Events reconnection with `Last-Event-ID` is `Api.stream_sse`'s
concern only. `Ai.chat` never reconnects mid-stream (ADR-0053 rule 3: "no
retry occurs after the first delta is yielded" continues to hold; a mid-stream
disconnect surfaces as one `error` event and the iterator ends).

## Consequences

Every Tina4 application that consumed `Ai.chat(stream=True)` between 3.13.101
and 3.13.112 updates its consumer loop once. The migration is mechanical:
`chunk` → `event.text` when `event.type == "text_delta"`. Applications that
never used streaming, and applications that used only `Ai.complete` or
`Ai.embed`, are unaffected.

Application code that streamed HTTP through a hand-rolled `http.request` +
line-buffer + SSE-frame reader can be replaced with `Api.stream_sse(url)` in
one line, provider-agnostic. The 40 lines of SSE ceremony go into the
framework, once, tested once, benched once, per language.

The shared fixture grows by four cases and one new runner
(`api_stream_contract`). Each language re-runs the extended fixture on the
lab host; all four must be green before 3.13.113 tags. No test doubles: the
fixture server is a real local HTTP process reached over real sockets, per
Tina4's no-mock rule.

## Deferred / not decided

- Passing raw `bytes` (audio, video) inline in a content part. `image` is
  scoped to URL or `data:` URI. Raw-bytes parts wait for a use case.
- Provider-native tool-JSON schemas (OpenAI's `functions`, Anthropic's
  `tools`). The `tool_call` event is provider-neutral; the caller who wants
  provider-specific JSON schema plumbing writes it explicitly. A future ADR
  may add a Tina4-side tool-registry helper.
- `Ai.chat` acknowledgement path (tool_result submission). The application
  constructs the next `Ai.chat(messages=[..., {role: "tool", ...}])` call
  itself. A future ADR may add a helper for this shape.
