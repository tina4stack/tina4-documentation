# ADR-0058: RBAC is one claim-first role/permission guard in every framework

- **Status:** Accepted
- **Date:** 2026-08-19
- **Scope:** Feature 138, Role-Based Access Control (authorization guards)
- **Decision owner:** Andre van Zuydam

## Context

Tina4 authenticates (JWT via `Auth`) and gates writes by default (`@secured` /
`@noauth`), but authorization is binary: a request is authenticated or it is not.
Every non-trivial app (admin vs editor vs viewer) reinvents the same middleware
that reads a role claim and returns 403. That is a DRY failure at the ecosystem
level, and Tina4's audience (admin panels, internal tools, CRUD/business apps via
AutoCrud + dev admin) is exactly the audience RBAC serves.

RBAC also has an unbounded edge: policies, resource ownership, attribute rules
(ABAC), role hierarchies, relationship graphs (ReBAC). Shipping all of that would
delay the useful core and weaken its tests. The design must fix a small, correct
core and leave the rest to documented application middleware.

## Decision

Tina4 ships one RBAC contract in all four backend frameworks. It is claim-first,
zero-dependency, and composes with the existing auth gate.

1. **Claim-first subject.** A subject's roles and permissions come ONLY from the
   cryptographically-verified JWT payload: `roles: string[]` and
   `permissions: string[]`. No database, no new dependency, works with the
   existing `Auth.get_token(...)`. A DB-backed role/permission resolver is a
   documented extension, NOT part of the v1 core contract.

2. **Two guards, same names in every language.** `role(...)` and `can(...)`:
   Python decorators `@role("admin")` / `@can("posts.delete")`; PHP chainable
   `->role("admin")` / `->can("posts.delete")` plus `@role` / `@can` docblocks;
   Ruby `role "admin"` / `can "posts.delete"` in the route block; Node
   `.role("admin")` / `.can("posts.delete")`. Each keeps its normal casing.

3. **OR within a guard, AND by stacking.** `role("admin", "editor")` passes when
   the subject holds AT LEAST ONE of the listed roles (OR). `can(...)` is the
   same. Require several at once by stacking two guards (`@role("admin")` +
   `@can("billing.read")`), which is unambiguous and composable.

4. **Roles and permissions are independent claims.** `role()` checks `roles`;
   `can()` checks `permissions`. The core does NOT expand a role into permissions
   (that mapping is the DB-backed extension's job, or is baked in at token-mint
   time). This keeps v1 minimal and every check a pure claim lookup.

5. **Wildcards live on the GRANTED side.** A granted permission `posts.*`
   satisfies a required `posts.delete`; a bare granted `*` satisfies every `can`.
   Matching is dot-segment prefix: `posts.*` matches `posts.<anything...>` and
   never matches `users.delete`. The REQUIRED permission is always concrete; only
   what the token CARRIES may wildcard.

6. **Fail-closed with the correct status.** A guarded route with a missing or
   invalid token returns **401** (unauthenticated) - a guard implies `@secured`,
   so a guarded GET still requires auth. A valid token that lacks the role or
   permission returns **403** (authenticated, forbidden). The 401-vs-403 split is
   load-bearing: returning 403 for missing auth leaks that the resource exists and
   breaks client re-auth flows.

7. **Verified payload only.** Roles and permissions are read from the payload
   returned by the framework's token validator, never from an unverified header or
   query parameter. A spoofed `X-Role: admin` with no matching claim grants
   nothing. This closes the obvious privilege-escalation.

8. **Legacy singular `role` is coerced.** A payload carrying a singular
   `role: "admin"` string (the shape shown in current docs) is read as
   `roles: ["admin"]`. Back-compat, one direction, no other legacy shape is
   invented.

## Out of scope (deferred, documented as app middleware)

Policy objects, resource ownership ("editor AND owns the row"), attribute rules
(ABAC), role hierarchies, and permission-implied-by-role expansion in the core.
These are reachable today with the existing `@middleware` mechanism and are
revisited only on real demand, never speculatively.

## Consequences

- A new app gets real authorization with two guards and zero configuration - the
  claims already ride in the JWT it mints.
- The four frameworks share one answer key (`fixtures/rbac_contract.json`), so a
  role check behaves identically in Python, PHP, Ruby and Node.
- Because it is claim-first, revoking a role takes effect on the next token, not
  instantly - documented, and the DB-backed resolver extension is the answer for
  apps that need instant revocation.
- Pre-3.14.0 stability boundary: this is additive (new decorators/methods), so it
  breaks nothing; the singular-`role` coercion keeps existing tokens working.
