# ADR-0023: A job is acknowledged through the JOB, not through the backend

- **Date:** 2026-08-01
- **Status:** Accepted
- **Supersedes:** the acknowledgement-signature clause of [ADR-0022](ADR-0022.md)
  ("an acknowledgement names its message"). ADR-0022's at-least-once promise and
  its per-protocol reasoning stand unchanged; only the SHAPE of the ack surface
  is re-decided here.
- **Scope:** the queue backends in all four frameworks (Feature 89).

## Why this feature exists at all (owner, 2026-08-01)

> "It allows a developer to use sqlite on local and upgrade it to the environment
> they have on the server."

Same promise as DocStore: develop against the zero-dependency local backend,
change ONE env var, run on the real broker in production. The application code
does not move. The protocol is an implementation detail of the deployment, not
of the program.

That sets a much sharper bar than "every backend acknowledges somehow":

- A job written on the FILE backend locally and one written on KAFKA in
  production must be read back THE SAME WAY - `Queue(topic="<t>.dead_letter")`,
  no broker configuration, no conditional code.
- `queue.dead_letters()` must answer the same question on every backend.
- Anything a developer can rely on locally that is NOT true in production is a
  TRAP, not a convenience. It is discovered after deployment, by definition.

Both open defects are failures of exactly this promise, and are worse read this
way than as parity gaps:

**Python's `failed/` directory is a local-only behaviour with no production
equivalent.** A developer builds a dead-letter handler against the file backend,
deploys onto Kafka, and the handler finds nothing - because locally the dead
letters went into a directory only `dead_letters()` can read, and in production
they go to a topic. Silent, and only surfaces once something is genuinely poison.

**Node refusing `rabbitmq` and `kafka` at construction severs the upgrade path
outright.** You can develop locally on the file backend and then you CANNOT move
to the server's environment: the app does not start. That is not a degraded
backend, it is the promise of this feature being unavailable in one of the four
frameworks (ADR-0022 records it as a holding position pending the
persistent-connection rewrite).

## Question

ADR-0022 promised at-least-once delivery on every backend and said "an
acknowledgement names its message". Measured against the code on 2026-08-01, the
four frameworks do not share an acknowledgement surface at all:

| framework | ack surface                                        |
| --------- | -------------------------------------------------- |
| PHP       | `acknowledge(string $topic, string $messageId)`     |
| Ruby      | `acknowledge(_message)` - commits the CONSUMER position, does not name the message |
| Python    | none. It has `complete(job)` / `fail(job, error)`   |
| Node      | RabbitMQ and Kafka THROW at construction            |

So the ADR-0022 clause is true in PHP, false in Ruby, and describes a concept
Python does not have. Three signatures and one refusal is not a contract.

## Decision

**The public acknowledgement surface is job-centric: `job.complete()` and
`job.fail(error)`.** A caller never names a topic or a message id; it holds the
Job it was handed and tells that Job what happened. Backends translate to
whatever their protocol requires - an AMQP basic.ack carrying the delivery tag, a
Kafka offset commit, a Mongo status update, a file-backend reservation release.

Promote **Python's** shape to the other three - but the Job surface is the UNION
of what the four can do today, not Python's current set. Measured, Python is
MISSING two things:

| operation           | today                                      | decision |
| ------------------- | ------------------------------------------ | -------- |
| `complete()`        | Python has it                              | keep |
| `fail(error)`       | Python has it; dead-letters after max_retries | keep |
| `retry(delay)`      | Python has it                              | keep |
| `dead_letter(reason)` | **absent in Python**; PHP and Ruby have it on the BACKEND | internal only - `reject()` is the public spelling, see below |
| `reject(reason)`    | Python: literal alias for `fail()`         | **REDEFINE: reject = do not retry, dead-letter NOW** |

Two gaps this closes, both found by stress-testing the promotion rather than
assuming the reference framework was complete:

**1. There is no way to dead-letter immediately.** `fail()` only reaches the
dead-letter store after `max_retries` attempts. A consumer that recognises a
permanently poisoned message - a payload that will never parse - has no way to
say so, and must burn the whole retry budget reprocessing work it already knows
is doomed. AMQP's `basic.reject` with `requeue=false` IS that operation, so the
semantics already exist in the protocol underneath; Python simply does not expose
them. AWS SQS, Celery and Spring AMQP all offer an immediate dead-letter path.

**2. `reject` is a literal alias for `fail`.** `def reject(self, reason=""):
self.fail(reason)`, docstring "Alias for fail()". That breaks the framework's own
no-alias rule AND wastes the one name that already means "do not requeue this"
everywhere else in the industry. Redefining it costs nothing - nothing can depend
on a distinction that does not currently exist - and it is the natural spelling
for gap 1.

## The dead letter is a QUEUE, not a store (owner call, 2026-08-01)

Python is the reference for the SURFACE and the outlier on the MECHANISM.

`LiteBackend._dead_letter` writes the job into a `failed/` DIRECTORY:
"Move the job to the dead-letter (failed) directory. Terminal until a manual
retry_failed()/retry() revives it." The only ways back out are `dead_letters()`
- a polling read - or a manual revive. Nothing can SUBSCRIBE to it.

PHP and Ruby publish to `<topic>.dead_letter`, an ordinary topic. That is a real
destination: a consumer, an alerting worker or a replay job can attach to it.

**Decision: a dead-lettered job is PUBLISHED to a dead-letter QUEUE in all four.**
The convention is the producing topic plus `.dead_letter`, which PHP and Ruby
already use, so Kafka needs no change. Python moves off the directory.

Why this is the right way round, given Python wins on surface:

- A store is a graveyard you have to go digging in; a queue is something you can
  react to. Dead letters are an OPERATIONAL signal - "these payloads are poison"
  - and a signal nobody can subscribe to gets discovered weeks later.
- It is what the underlying protocols already do. Kafka has no native DLQ, so
  republishing to a `.dead_letter` topic IS the idiom. RabbitMQ routes a rejected
  message to its configured dead-letter EXCHANGE, which is a queue by definition.
  The directory was the only mechanism that matched nothing underneath it.
- It keeps `dead_letters()` working. Reading a dead-letter QUEUE still answers
  "what died", so the existing API is preserved; it gains the ability to be
  consumed rather than only polled.

Per-backend translation of `job.reject(reason)` and of `fail()` past max_retries:

| backend    | mechanism                                                    |
| ---------- | ------------------------------------------------------------ |
| file/lite  | publish to the `<topic>.dead_letter` QUEUE (was: failed/ dir) |
| Kafka      | produce to `<topic>.dead_letter` (PHP and Ruby already do)     |
| RabbitMQ   | declare and publish to the `<topic>.dead_letter` QUEUE         |
| MongoDB    | insert into the `<topic>.dead_letter` collection               |

**NOT a dead-letter exchange on RabbitMQ, and this is the whole point of the
feature.** An earlier draft of this ADR said `basic.reject` with `requeue=false`
-> the configured DLX, reasoning from what AMQP offers. That is wrong. A DLX
routes to wherever the broker's `x-dead-letter-routing-key` says - configured
OUT OF BAND, in broker config Tina4 does not own - so the identical application
code would find its dead letters at `<topic>.dead_letter` on Kafka and somewhere
else entirely on RabbitMQ, or NOWHERE if the operator never declared the
exchange.

The feature exists to make queue code UNIFORM REGARDLESS OF PROTOCOL. ADR-0022's
"each backend keeps the promise the way its protocol allows" governs MECHANISM
only; it must never reach OBSERVABLE BEHAVIOUR. The binding rule is stronger:

> Identical application code, identical observable outcome, on every backend.
> The protocol may differ underneath. What the developer writes, and what they
> can read back, must not.

So the contract is: after `job.reject(reason)`, the job is readable via
`Queue(topic="<topic>.dead_letter")` on ALL FOUR backends, with NO broker
configuration required. Tina4 declares the dead-letter queue itself.

Measured 2026-08-01: PHP, Ruby and Python's RabbitMQ backends ALREADY do exactly
this - `enqueue($topic . '.dead_letter')`, `get_queue("#{topic}.dead_letter")`,
`dl_topic = f"{self._topic}.dead_letter"`. None uses a DLX. The codebase had the
principle right and this ADR was about to regress it.

MIGRATION: existing jobs sitting in a Python `failed/` directory are not in the
new queue. `dead_letters()` must read BOTH for one release so an upgrade does not
strand jobs that already died, and the directory read is removed after that.

## Why Python, and why this is not a coin toss

1. **The documentation already says so, in all four.** Every CLAUDE.md documents
   the consumer loop as `job.complete()` / `job.fail(error)`. The PUBLIC surface
   already agrees across the family; it is the ADAPTERS underneath that drifted.
   Promoting Python makes the code match the docs rather than making the docs
   match four different codebases.

2. **"Name the message" is a leaky abstraction.** A topic plus a message id is
   enough for Kafka and for the file backend, but an AMQP ack needs the DELIVERY
   TAG from the channel that delivered it - which is not the message id and is
   not reconstructible from one. PHP's signature cannot express a correct AMQP
   ack; it only looked right because the Kafka case was the one in front of us.

3. **The Job already carries what every backend needs.** It is the natural place
   to hang the delivery tag, the offset, or the reservation token, and it keeps
   that detail out of the caller's hands entirely.

4. **It removes a whole class of caller error.** With `acknowledge(topic, id)` a
   caller can ack the wrong message, ack against the wrong topic, or ack a
   message the consumer never held. `job.complete()` cannot express any of those.

## Rejected alternatives

- **Promote PHP's `acknowledge(topic, messageId)`.** It matches ADR-0022's stated
  wording, but see reason 2: it cannot express a correct AMQP ack. Choosing it
  would mean either a wrong RabbitMQ implementation or a second, different method
  for AMQP - which is the divergence we are closing.
- **Keep both, documented as a queue-level vs adapter-level split.** This is what
  we have today, and it is precisely what let ADR-0022 assert a four-way promise
  that two frameworks did not keep. A split that nothing checks is not a design.
- **Leave Ruby's consumer-position commit as the Kafka mechanism.** It is correct
  for Kafka in isolation, but committing the consumer position acknowledges
  EVERY message up to that offset, not the one job that finished. Under a batch
  or concurrent consumer that silently acks work that has not been done.

## Consequences

- PHP and Ruby gain `complete`/`fail`/`retry`/`dead_letter`/`reject` on the Job.
  The backend `acknowledge`, `requeue` and `deadLetter` methods become internal
  translation, not public API.
- **CORRECTION to an earlier draft of this ADR:** it said only `acknowledge`
  became internal. That was wrong and would have SILENTLY DROPPED two documented
  operations - PHP and Ruby both expose `requeue` and `deadLetter` publicly and
  Python's Job had no equivalent for the latter. Promoting a reference
  implementation without diffing the full surface against the others is the exact
  defect this audit keeps finding: a contract asserted in one place that removes
  capability in another.
- Python gains `dead_letter()` and a REDEFINED `reject()`. This is the only
  framework-visible behaviour change to the reference implementation.
- Node still refuses `rabbitmq` and `kafka` at construction (ADR-0022, holding
  position). This ADR does not change that; it defines the surface those backends
  must present once the persistent-connection rewrite lands.
- **Not breaking for documented usage.** Anyone following the CLAUDE.md consumer
  loop already calls `job.complete()`. Callers reaching into a backend's
  `acknowledge()` directly - undocumented in every framework - must move to the
  Job.

## Lock-in tests (real brokers, no mocks)

Per framework, against the LIVE Kafka on 9092 and RabbitMQ on 5672:

1. push -> consume -> `job.complete()` -> the job is NOT redelivered.
2. **Negative control:** push -> consume -> exit WITHOUT completing -> the job IS
   redelivered. Without this the first test passes against a backend that
   acknowledges nothing, which is exactly how the Node Mongo queue shipped for
   two releases re-delivering every completed job.
3. `job.fail(error)` -> the job reaches the dead-letter path after `max_retries`,
   and NOT before.
4. `job.reject(reason)` / `job.dead_letter(reason)` -> the job is dead-lettered
   IMMEDIATELY, on the first call, with `attempts` still below `max_retries`.
   The negative half matters as much: prove `fail()` at the same attempt count
   does NOT dead-letter, or the test passes against an implementation where both
   paths simply give up.

A green here requires a real broker. A skipped run is not a pass.
