# ADR-0025: The DocStore fallback imitates the driver - it is never the driver's job to imitate us

- **Date:** 2026-08-03
- **Status:** Accepted
- **Scope:** `DocStore` in all four frameworks - the SQLite fallback collection,
  its cursor, and every result object either provider hands back.
- **Relates to:** [ADR-0024](ADR-0024.md) (the swap must work),
  [ADR-0004](ADR-0004.md) (the best implementation prevails),
  [ADR-0012](ADR-0012.md) (settle contracts against real-world frameworks).

## The problem, measured

DocStore advertises the swap outright: *develop against a zero-dependency local
SQLite store, switch to MongoDB in production by setting one env var*. Every
other subsystem merely aspires to substitutability. This one sells it.

On 2026-08-03 a real MongoDB was pointed at all four frameworks for the first
time. Each broke at the call site, in its own way:

| framework | what breaks | how it fails |
| --------- | ----------- | ------------ |
| php | the insert-result accessors are MUTUALLY EXCLUSIVE. Fallback: `->insertedId` works, `->getInsertedId()` absent. Mongo: exactly the reverse. | **silently** - our own documented example becomes `findOne(['_id' => null])` and the developer sees "not found" |
| ruby | `find_one` does not exist on `Mongo::Collection` | loudly - `NoMethodError` |
| node | `getCollection()` and `insertOne()` return a VALUE on the fallback and a PROMISE on the driver | **worst** - identical source changes TYPE, and a Promise is always truthy, so `if (doc)` succeeds for a document that does not exist |
| all four | a query against an array field | fallback matches nothing; Mongo matches |

There is no spelling of the PHP insert that works on both providers. That is the
cleanest statement of the defect: the two halves of an advertised swap expose
disjoint APIs.

## The evidence that settles it

The public surface of each fallback, measured against its real driver:

| framework | fallback methods | driver methods | shared | **fallback-only** |
| --------- | ---------------- | -------------- | ------ | ----------------- |
| python | 13 | 43 | **13** | **0** |
| php | 17 | 46 | 14 | 3 (`quoted`, `load`, `runDocQuery`) |
| ruby | 17 | 54 | 12 | 5 (`connection`, `dump`, `find_one`, `load_doc`, `quoted_name`) |

**Python's fallback is a perfect SUBSET of the driver.** Not one method exists
that Mongo does not also have. That is not luck - it is the rule this ADR is
about, already implemented in one framework, and it is exactly why Python's
substitutability harness passes where PHP's and Ruby's report defects.

So the decision is not a choice between two untried designs. One of them is
shipping and working.

## The decision

> **The fallback imitates the driver. Every method, signature, return shape and
> sync/async character on the fallback must exist, with the same meaning, on the
> real provider. The fallback may implement a SUBSET; it may never implement a
> DIFFERENT set.**

Corollaries, each traceable to a measured defect:

1. **No fallback-only public method.** If Mongo has no `find_one`, neither do we.
   Anything the fallback needs internally is private.
2. **Result objects use the driver's accessors.** `getInsertedId()` in PHP,
   `.inserted_id` in Python, `.insertedId` in Node, and whatever the Ruby driver
   spells it - because the driver is the half we cannot change.
3. **The sync/async character does not change with the provider.** Node's
   fallback becomes async, because a driver cannot become sync.
4. **A query that matches on one provider matches on the other**, or the
   fallback raises rather than silently returning nothing. Array fields are the
   measured case.

## The alternative, costed - and why it loses

**Option B: wrap the driver so it presents Tina4's surface.**

Superficially attractive: nobody's existing code breaks. The costs are why it
loses.

- **Four wrappers to write and maintain, not one rule.** The driver surfaces are
  43, 46 and 54 methods. A wrapper covering only today's 12-14 shared methods
  makes every other driver capability unreachable - `aggregate`, `bulkWrite`,
  `createIndex`, `watch`, sessions, transactions. The developer who needs one
  drops to the raw client and the abstraction has failed at the first real
  demand.
- **It inverts the dependency.** We would be asserting that MongoDB's API should
  look like ours. Every driver upgrade becomes our merge problem, in four
  languages.
- **It is the larger diff.** Four wrapper classes plus four cursor wrappers plus
  four result-object shims, against Option A's measured migration below.
- **It contradicts ADR-0012.** The authority order puts a mainstream library's
  API above internal precedent. pymongo's shape is the reference implementation
  of this API in every language; ours is a local convenience.
- **Python would have to REGRESS to adopt it.** The one framework that already
  satisfies the contract would grow a wrapper it does not need.

## What Option A costs, measured

Not estimated - counted on 2026-08-03:

| what changes | count |
| ------------ | ----- |
| `find_one` in tina4-ruby `lib/` | 8 |
| `find_one` in tina4-ruby `spec/` | 15 |
| `insertedId` in tina4-php `Tina4/` | 4 |
| `insertedId` in tina4-php `tests/` | 14 |
| occurrences in `tina4-documentation/docs/` | **0** |
| `CLAUDE.md` files to update | 4 |

**41 call sites and 4 CLAUDE.md files.** The public documentation site has zero
occurrences, so no published guide changes. Python needs nothing.

This is BREAKING for anyone using `find_one` or `->insertedId` against the
fallback, which is permitted for v3 parity, and it needs a `Breaking:` changelog
entry with the migration line:

    ruby   collection.find_one(filter)   ->  collection.find(filter).first
    php    $result->insertedId           ->  $result->getInsertedId()

Node's clause 3 is the larger piece of work: making the fallback async is a
signature change across its DocStore surface. It is also the one with the worst
failure mode today - a truthy Promise standing in for a document - so it earns
the effort.

## Consequences

- The fallback is permanently smaller than the driver, and that is correct. It
  is a development convenience, not a MongoDB reimplementation.
- A developer who needs a capability the fallback lacks gets a loud absence at
  the call site instead of a silent wrong answer after deploying. ADR-0024 rule
  3 already says a method that exists and no-ops is worse than one that is
  absent.
- `docstore_contract.json` gains the enforcement: `the-call-site-surface-is-identical`
  and `the-sync-async-shape-does-not-change-with-the-provider` move from OWED to
  PROVEN once each framework's substitutability harness asserts them instead of
  merely reporting them.
- The four harnesses added on 2026-08-03 already run every case against both
  providers, so the work is verifiable the moment it lands.

## What this does NOT decide

The array-query defect (clause 4) needs its own investigation: whether the
SQLite fallback can implement Mongo's array-containment semantics over JSON1 at
acceptable cost, or whether it must raise on an array filter instead. Raising is
acceptable under this ADR; silently matching nothing is not. That is measured
work, not a decision to be taken here.
