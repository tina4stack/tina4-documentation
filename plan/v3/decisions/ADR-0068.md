# ADR-0068: Response headers refuse CR, LF and NUL; built-in servers enforce the upload cap before reading the body

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release

## Context

A security audit found two defects in the Python reference, and both have
relatives in the other three frameworks.

**The body was read before the cap was checked.** The zero-dependency asyncio
server that Python falls back to when uvicorn and hypercorn aren't installed
(the shipped Docker image included) parsed the request head, then asked the
stream for exactly `Content-Length` bytes. `TINA4_MAX_UPLOAD_SIZE` was only
checked later, in `app()` and `Request.from_scope`, so the server had already
agreed to hold whatever the client declared. A client that declared a large body
and sent it slowly grew the process without a ceiling: the audit measured 77MB
to 895MB of resident memory with a 1MB cap set. The same reader crashed its own
connection task on a non-numeric `Content-Length`, crashed on a header block
past the stream limit and leaked the socket both times, ignored
`Transfer-Encoding: chunked` completely (the body arrived empty) and let a
stalled body raise an uncaught timeout.

PHP's socket server already had most of the right shape in
`Server::enforceRequestLimits`: a 431 before the head is complete, a 413 on the
declared length and a running byte counter on what actually arrives. It still
treated a non-numeric `Content-Length` as zero and didn't decode chunked bodies.

**Header values reached the wire unchecked.** `Response.header()`,
`Response.cookie()` and `Response.redirect()` accepted carriage return (CR),
line feed (LF) and NUL, and the built-in server writes header lines to the
socket as it finds them. A value that came from user input could therefore end
one header early and start another. Cookie names and values weren't validated
either, so a `;` in a value added cookie attributes the application never set.

Node's `http.ServerResponse.setHeader` already refuses these characters itself,
with a `TypeError` whose code is `ERR_INVALID_CHAR`. That's the behaviour the
other three now match.

## Decision

### 1. A response header, redirect or cookie carrying CR, LF or NUL is refused at the call site

The check runs where the developer sets the value, so the stack trace points at
the line that built it. The value is never stripped, encoded or truncated
quietly: a quietly repaired header hides the bug that produced it.

| Call | Refused when | Message (exact) |
| --- | --- | --- |
| header / add header / one-shot headers | the name isn't a valid HTTP token (RFC 9110 `tchar`) | `Header name must be a valid HTTP token ["<name>"]` |
| header / add header / one-shot headers | the value contains CR, LF or NUL | `Invalid character in header content ["<name>"]` |
| redirect | the location contains CR, LF or NUL | `Invalid character in header content ["Location"]` |
| explicit content type, file download name | the value contains CR, LF or NUL | `Invalid character in header content ["Content-Type"]` / `["Content-Disposition"]` |
| cookie | the name isn't a valid HTTP token | `Cookie name must be a valid HTTP token ["<name>"]` |
| cookie | the value, or any attribute value (path, max age, same site), contains CR, LF, NUL or `;` | `Invalid character in cookie content ["<name>"]` |

`<name>` is the header or cookie name as the caller passed it, written as a JSON
string literal, so a name that is itself broken can't break the message or the
log line that carries it. For every ordinary name this is byte-identical to
Node's own wording.

The exception type is the language's idiomatic one for a bad argument:

| Framework | Raises |
| --- | --- |
| Python | `ValueError` |
| PHP | `\InvalidArgumentException` |
| Ruby | `ArgumentError` |
| Node | `TypeError` (what `setHeader` throws natively) |

Cookie values are refused, not repaired. The one exception is a framework that
already percent-encodes the cookie value on the way out (Ruby encodes the value,
Node encodes the name and the value). It keeps encoding, because an encoded
value can't carry CR, LF, NUL or `;` to the wire, and changing it would break
every cookie it has already issued. Attribute values (path, max age, same site,
domain) are never encoded anywhere, so the refusal applies to them in all four.

Normal use is unchanged. A header value may contain any other printable
character, and several `Set-Cookie` headers on one response all reach the
client.

### 2. The built-in server won't write an unsafe header line

Headers also reach the writer from framework internals and from code that
appends to a response's header list directly. So the socket writer in each
framework's own HTTP server checks every name and value again just before it
writes them. If one fails, the server will write none of that response. It logs
an error naming the header and answers 500 with the transport shape in section
4 and the body `{"error":"Invalid response header"}`. Node gets this from
`node:http` for free. Behind uvicorn or hypercorn the server's own protocol
layer (h11 for uvicorn) does the same job.

### 3. The built-in server enforces the request limits before it buffers anything

This applies to every server that parses HTTP from a raw socket itself: Python's
asyncio fallback and PHP's `stream_socket_server`. Ruby and Node sit on a server
that parses for them (WEBrick or Puma, and `node:http`), so they meet the same
statuses through that server's own limits plus their own body reader. Ruby
isn't there yet: WEBrick reads the whole body before Tina4's cap runs.

Here's the path a request will now take through that server:

- The head will be read in bounded reads. If it passes
  `TINA4_MAX_REQUEST_HEADER` bytes (default 65536) before the blank line turns
  up, the server will answer 431 and close.
- If the head contains a bare CR, a bare LF or a NUL anywhere, it will be
  answered 400 `Malformed request head`.
- `Content-Length` must be one or more ASCII digits. Anything else, or two
  `Content-Length` headers that disagree, will be answered 400.
- `Transfer-Encoding` is accepted only as exactly `chunked`. Any other coding,
  `Transfer-Encoding` together with `Content-Length`, or chunk framing that
  doesn't parse will be answered 400.
- A declared `Content-Length` over `TINA4_MAX_UPLOAD_SIZE` (default 10485760)
  will be answered 413 before a single body byte is read.
- The body will then be read in bounded chunks (64KiB at most per read), never
  in one read of the declared size. A running count covers every body byte,
  chunked or not, and the moment it passes `TINA4_MAX_UPLOAD_SIZE` the server
  will answer 413 and stop reading.
- If the client goes quiet for `TINA4_REQUEST_TIMEOUT` seconds (default 30, 0
  switches the timer off) partway through a request, it will get 408. A
  connection that never sent a byte is closed without an answer, since there's
  no request to answer.

`TINA4_MAX_UPLOAD_SIZE` is the one body cap in every framework, and the ASGI
path in Python answers with the same bytes as the built-in server. PHP keeps
`TINA4_MAX_REQUEST_BODY` as an extra ceiling on the declared length, since
deployments already set it. No other framework adds it.

A limit variable that isn't a usable number falls back to its default with a
warning naming the variable, the same way PHP's `resolveLimit` already works.

### 4. Every transport rejection has one shape

| Cause | Status | Body (exact bytes) |
| --- | --- | --- |
| Head past `TINA4_MAX_REQUEST_HEADER` | 431 Request Header Fields Too Large | `{"error":"Request header fields exceed TINA4_MAX_REQUEST_HEADER (<limit> bytes)"}` |
| Bare CR, LF or NUL in the head | 400 Bad Request | `{"error":"Malformed request head"}` |
| Bad `Content-Length` | 400 Bad Request | `{"error":"Invalid Content-Length"}` |
| Bad `Transfer-Encoding` or chunk framing | 400 Bad Request | `{"error":"Invalid Transfer-Encoding"}` |
| Declared or running body past the cap | 413 Content Too Large | `{"error":"Request body (<bytes> bytes) exceeds TINA4_MAX_UPLOAD_SIZE (<limit> bytes)"}` |
| Partial request gone quiet | 408 Request Timeout | `{"error":"Request timed out before it was complete"}` |
| Unsafe response header (section 2) | 500 Internal Server Error | `{"error":"Invalid response header"}` |

`<bytes>` is the declared length when the refusal came from the declared
length, and the running count when it came from the counter. The 413 wording is
the one Python's ASGI path and Node already send, because it names the variable
that fixes it. PHP moves to it from `Request body too large`.

The headers are `Content-Type: application/json`, `Content-Length`,
`Connection: close` and the canonical security header set from SECHDR-DEC-01
(`X-Frame-Options`, `X-Content-Type-Options`, `Content-Security-Policy`,
`Referrer-Policy`, `X-XSS-Protection`, `Permissions-Policy`, with the same
environment overrides). There's no `Strict-Transport-Security`, because a
rejection is written before the request's scheme is known.

After writing a rejection the server half-closes and throws away whatever the
client is still sending, for two seconds at most, before it closes. Closing
with unread bytes in the kernel buffer would send a reset, and the client would
never see the answer.

## Test contract

The shared fixture is `plan/v3/fixtures/http_hardening_contract.json`. Every
case runs against the real framework with no mocks: the response cases against
the real response object, the server cases against a real server booted as a
child process and driven over a real loopback socket, with resident memory read
from the operating system.

Suites carry these case names in each language's own idiom:
Python `tests/test_http_hardening_contract.py`, PHP
`tests/HttpHardeningContractTest.php`, Ruby `spec/http_hardening_contract_spec.rb`,
Node `test/httpHardeningContract.test.ts`.

Mutation proof: take the call-site check out and the refusal cases go red; take
the writer check out and the direct-append case goes red; go back to reading
the declared length in one read and the memory case goes red.

## Consequences

- A route that used to pass user input into a header, redirect or cookie without
  cleaning it now fails loudly at that line instead of shipping a header the
  client will read differently from the developer. Clean or validate the input
  first.
- A cookie value containing `;` now raises. An application that stored
  structured data that way has to encode it (base64 or percent-encoding) itself.
- A dev or Docker deployment on Python's built-in server now honours
  `TINA4_MAX_REQUEST_HEADER` and `TINA4_REQUEST_TIMEOUT`, which used to be PHP
  only, and decodes chunked request bodies instead of dropping them.
- PHP changes its 413 wording, adds the 400 cases, decodes chunked bodies and
  adds the security headers to `sendHttpError`.

## Parity at the time of writing

Measured against `origin/v3` of each repository on 2026-09-24.

| Part | Python | PHP | Ruby | Node |
| --- | --- | --- | --- | --- |
| 1 Call-site refusal | this change | `fix/refuse-header-crlf` | owed: `header`, `redirect`, cookie name and attributes unchecked (value is encoded) | headers and redirect native; cookie attributes accept `;` (owed) |
| 2 Writer refusal | this change | owed | WEBrick refuses CR/LF values, Puma drops the line quietly | native |
| 3 Limits before read | this change | mostly present; 400, chunked, wording owed | owed: WEBrick buffers the whole body before the cap | declared and running cap present |
| 4 Rejection shape | this change | owed | 413 wording matches; security headers owed | 413 wording matches; security headers owed |

Ruby has one more defect in the same area: under WEBrick every cookie loses
`HttpOnly` and `SameSite`, because the Set-Cookie line is re-parsed by
`WEBrick::Cookie`, which doesn't know those attributes.
