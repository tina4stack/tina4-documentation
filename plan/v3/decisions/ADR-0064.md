# ADR-0064: ORM read queries return a uniform ModelCollection carrying the total

Status: Proposed
Date: 2026-09-04
Ships in: 3.13.132

## Context

`db.fetch(sql, params, limit, offset)` returns a `DatabaseResult` whose `.count`
is the true total for the filter -- the `SELECT COUNT(*)` probe result, computed
independently of `limit` / `offset` (ADR-0043, `to_paginate()`). A caller reading
one page of 20 rows can still learn there are 250 matching rows.

The ORM throws that away. `where()`, `select()`, `find()` (filter form), `all()`
and `with_trashed()` each call `db.fetch()`, hydrate `result.records` into model
instances, and return a bare `list` / `array`. The total -- already computed on
`result.count` -- is discarded. So a developer paginating through the ORM has no
way to know how many rows the filter matches without issuing a second query.

The one partial escape was Python-only and awkward: `Model.where(..., with_count=
True)` returned a `tuple[list, int]`. It existed in no other framework, fired a
SECOND redundant `COUNT(*)` (the total was already on `result.count`), and covered
only `where()`. PHP / Ruby / Node had nothing -- a developer there had to call
`count()` separately and re-write the same filter, which drifts.

The result was not uniform across the four frameworks. That is the defect.

## Decision

ORM read queries return a **ModelCollection**: the page of models AND the total
for the query. Identical behaviour in all four frameworks.

### Which methods

`where`, `select`, `find` (filter / all form), `all`, `with_trashed` return a
ModelCollection. Single-record methods are unchanged: `find(pk)`, `find_by_id`,
`find_or_fail`, `select_one`, `load` still return one model or null.

### The ModelCollection is list/array-compatible

It IS the page of models. Existing code does not change. Iterate it, index it,
slice it, count it, JSON-serialise it -- all unchanged.

| Framework | Backing type | How compatibility is kept |
|-----------|--------------|---------------------------|
| Python    | subclass of `list` | native |
| Ruby      | subclass of `Array` | native |
| Node      | subclass of `Array` | native (`Array.isArray` stays true) |
| PHP       | object: `ArrayAccess`, `Countable`, `IteratorAggregate`, `JsonSerializable` | `foreach` / `$c[0]` / `count($c)` / `json_encode` all work; `->toArray()` returns the bare array for native `array_*` calls |

PHP arrays cannot carry properties, so PHP is the one framework whose return type
changes from `array` to an object. `is_array($rows)` and native `array_map` /
`array_filter` / `array_column` on the result stop working; the mitigation is
`->toArray()`. Every internal caller in `Tina4/` (17 `is_array()` sites across
ORM/AutoCrud/CRUD, plus the scaffolded CRUD templates and the gallery) is audited
and fixed in the same change.

### The accessor is a METHOD

Same concept, language-idiomatic name:

| Framework    | Total accessor      | Envelope         |
|--------------|---------------------|------------------|
| Python, Ruby | `get_total_records()` | `to_paginate()` |
| PHP, Node    | `getTotalRecords()`   | `toPaginate()`  |

A method, not a `.total` property, on purpose: `list.count()` (Python) and
`Array#count` (Ruby) already exist, so a `.count` would shadow a built-in.
`DatabaseResult` keeps its `.count` property (it is not a list). Both expose the
identical `to_paginate()` / `toPaginate()` envelope.

`get_total_records()` returns the total rows matching the query's filter, ignoring
`limit` / `offset`, respecting soft-delete. It is sourced from `DatabaseResult.count`
(the fetch COUNT probe) -- **zero extra queries**.

### to_paginate() -- the uniform seven-key envelope

Identical bytes to `DatabaseResult.to_paginate()` (ADR-0043):

```
records, total, page, per_page, total_pages, limit, offset
```

`records` are model dicts (each model serialised the same way the framework
serialises it in a JSON response), so the client-visible JSON is uniform whether a
route returned a raw `db.fetch(...).to_paginate()` or an ORM
`Model.where(...).to_paginate()`.

- `total`       = `get_total_records()`
- `per_page`    = the query's limit
- `page`        = floor(offset / per_page) + 1
- `total_pages` = ceil(total / per_page)
- an empty page (offset past the end, or matches only on other pages) still
  reports the correct `total`

### Supersede

Python's `Model.where(..., with_count=True) -> (list, int)` is REMOVED. The
`with_count` keyword no longer exists; passing it raises `TypeError`.

Migration: `rows, total = Model.where(f, p, with_count=True)` becomes
`rows = Model.where(f, p); total = rows.get_total_records()`. In-repo call sites
migrated in the same change: the CLI list-route scaffold (now returns
`records.to_paginate()`) and the ORM parity tests.

## Test contract

Per framework, real database (SQLite for the shared cases, the no-mock rule
stands), positive AND negative:

1. **Total is outside pagination** -- seed 250 rows, `where(filter, limit=20,
   offset=40)`: `len == 20`, `get_total_records() == 250`.
2. **List/array compatibility** -- the result iterates, indexes, slices, and
   `count`s as the page of model instances; the framework's is-array / is-list
   check still holds (PHP: `foreach` + `count()` + `json_encode` + `toArray()`).
3. **to_paginate envelope** -- exactly the seven keys, values correct
   (`page`, `per_page`, `total_pages`), and `total` / `total_pages` equal to the
   same-query `db.fetch(...).to_paginate()`; `records` are dicts of the same shape.
4. **Every returning method carries the total** -- `where` / `select` / `find`
   (filter) / `all` / `with_trashed`.
5. **find(pk) still returns a single model**, not a collection.
6. **Empty page still reports the total** (offset past the end).
7. **Zero matches -> total 0.**
8. **Soft-delete** -- the total excludes soft-deleted rows for the live finders and
   includes them for `with_trashed`.
9. **Supersede (Python)** -- `where(..., with_count=True)` raises.

The shared executable fixture is `plan/v3/fixtures/ormcollection_contract.json`,
driving the identical runner in all four repos (`CONTRACT-MAP.md` row). Mutation-
prove each: break the total source (return `len(page)` instead of the probe count)
and the total-outside-pagination case must go red in every framework.

## Consequences

- **Uniform result across all four frameworks** -- the whole point. Same methods,
  same accessor concept, same envelope, same JSON.
- **Zero new queries.** The total reuses the discarded `DatabaseResult.count`.
  Python loses one query (the redundant `with_count` COUNT is gone).
- **Non-breaking in Python / Ruby / Node** for every read pattern -- the result
  stays a list/array. The only Python break is the removed `with_count` tuple
  (2 in-repo call sites, migrated here).
- **PHP return type changes** `array` -> ModelCollection object. Contained by
  `ArrayAccess` + `Countable` + `IteratorAggregate` + `JsonSerializable` + a
  `toArray()` escape hatch, and by auditing every internal `is_array()` /
  `array_*` caller. This is the same pattern as `Job` (ADR-0024) and
  `DatabaseResult`.
- Docs: the four CLAUDE.md ORM sections and the `python/php/ruby` ORM doc pages
  gain `get_total_records()` / `getTotalRecords()` + `to_paginate()`; the
  `where() -> list` line becomes `where() -> ModelCollection`.

## Related

- **ADR-0043** -- `DatabaseResult.to_paginate()`, the seven-key envelope this
  mirrors.
- **ADR-0024** -- `Job` as an `ArrayAccess` object; the precedent for PHP
  returning an array-compatible object instead of a bare array.
- **ADR-0004** -- best implementation prevails; Python was the closest (it had
  `with_count`) and is reshaped into the uniform collection the others adopt.
