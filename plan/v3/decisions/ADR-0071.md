# ADR-0071: Mail encryption means what it says - `ssl` is TLS on any port, STARTTLS is required, certificates are verified

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release

## Context

`TINA4_MAIL_ENCRYPTION` (or the `encryption` argument) picks how the Messenger
talks to the SMTP server. The four frameworks read the same value in different
ways, and three of the readings can send mail in cleartext when the user asked
for encryption.

Measured at v3 on 2026-09-24:

| Setting | Python | PHP | Node | Ruby (tina4-ruby#49) |
| --- | --- | --- | --- | --- |
| `ssl`, port 465 | implicit TLS | implicit TLS | implicit TLS | implicit TLS |
| `ssl`, any other port | **cleartext** | **cleartext** | **cleartext** | implicit TLS |
| `tls` / `starttls`, server offers STARTTLS | STARTTLS | STARTTLS | STARTTLS | STARTTLS |
| `tls` / `starttls`, server does not offer it | error | varies | varies | error |
| an unknown value (a typo) | **cleartext** | **cleartext** | **cleartext** | **cleartext** |
| certificate checked | **no** (stdlib context) | **no** (`verify_peer => false`) | yes, unless `TINA4_MAIL_TLS_INSECURE` | yes |

A user who writes `encryption: "ssl"` with `port: 2465` gets no warning and no
encryption. Their password and the message go over the network in clear text.
A certificate that is not checked gives the same result against an active
attacker: the connection is encrypted, but to whoever answered.

## Decision

### 1. One transport table, for SMTP, in all four frameworks

| `encryption` | Port 465 | Any other port |
| --- | --- | --- |
| `ssl` | implicit TLS | implicit TLS |
| `tls` or `starttls` (default `tls`) | implicit TLS | plain connect, then STARTTLS. **Required**: if the server's `EHLO` reply does not offer `STARTTLS`, the send fails before `AUTH` or `MAIL FROM` is sent |
| `none` | implicit TLS | plaintext, never upgraded |

Port 465 is the implicit-TLS submission port (RFC 8314). A plaintext
connection to it can't work, and a STARTTLS attempt there can't work either,
so port 465 always means implicit TLS. That keeps every existing port-465
configuration working. `none` means "never upgrade with STARTTLS". It never
turns an encrypted port into a plaintext one.

The value is trimmed and compared without case (`"SSL"`, `" tls "` are valid).

### 2. An unknown value is refused

Any other value (`tsl`, `ssl3`, `yes`, an empty string after trimming) raises
when the Messenger is constructed. The message names the bad value and the
valid ones:

```
Unknown mail encryption '<value>'. Valid values: ssl, tls, starttls, none.
```

The IMAP setting (`TINA4_MAIL_IMAP_ENCRYPTION` or `imap_encryption`) follows
the same rule, with its own message:

```
Unknown IMAP encryption '<value>'. Valid values: ssl, tls, starttls, none.
```

`<value>` is the value as it was given. Python raises `ValueError`, PHP
`\InvalidArgumentException`, Ruby `ArgumentError`, Node `Error`. A typo must
never downgrade to cleartext.

### 3. Certificates are always verified

Every TLS connection the Messenger opens (SMTP implicit TLS, SMTP STARTTLS,
IMAP implicit TLS, IMAP STARTTLS) verifies the server certificate against the
runtime's trust store and checks that it matches the host name. There is no
Tina4 switch that turns this off. Node's `TINA4_MAIL_TLS_INSECURE` is
withdrawn.

To trust a private certificate authority (a lab mail server, a company relay),
use the runtime's own standard mechanism, the same one every other TLS client
in that process uses:

| Runtime | How to add a certificate authority |
| --- | --- |
| Python | `SSL_CERT_FILE=/path/ca.pem` |
| PHP | `openssl.cafile=/path/ca.pem` in php.ini (or the `SSL_CERT_FILE` the OpenSSL build reads) |
| Ruby | `SSL_CERT_FILE=/path/ca.pem` |
| Node | `NODE_EXTRA_CA_CERTS=/path/ca.pem` |

### 4. What is not changed

- The default is still `tls`. An app that sets nothing gets STARTTLS, now
  required and verified.
- IMAP keeps its own setting, `TINA4_MAIL_IMAP_ENCRYPTION` (`tls` and `ssl`
  are implicit TLS, `starttls` is STARTTLS and required, `none` is plaintext).
  Sections 2 and 3 apply to it.
- `TINA4_MAIL_CAPTURE` and `TINA4_MAIL_REDIRECT_TO` (MAIL-DEC-01) are checked
  before any connection is made, exactly as before.

## Consequences

- **Breaking, on purpose:** `ssl` on a port other than 465 now uses TLS. A
  server on that port that only speaks plaintext will now fail the send. Before,
  the send worked but in cleartext.
- **Breaking, on purpose:** a server that does not offer STARTTLS now fails a
  `tls`/`starttls` send. Set `none` to send in plaintext on purpose.
- **Breaking, on purpose:** a self-signed or wrong-host certificate now fails
  in Python and PHP, and in Node even with `TINA4_MAIL_TLS_INSECURE=true`. Trust
  the certificate authority as shown in section 3.
- **Breaking, on purpose:** an unknown `encryption` value now raises instead of
  sending in cleartext.

## Proof

Red-first regression tests in Python, PHP and Node against real mail servers
(no mocks). Ruby's `spec/support/mail-infra.sh` (tina4-ruby#49) runs GreenMail,
Mailpit and Dovecot in docker and is reused for the other three:

- `ssl` on a non-465 port against a real implicit-TLS listener delivers the
  message, and the server-side capture shows the session was TLS.
- `ssl` on a non-465 port against a plaintext-only listener fails. Before the
  fix it delivered the message in clear.
- `tls` against a server that does not offer STARTTLS fails, and the server
  never receives `AUTH` or `MAIL FROM`.
- `none` against a server that offers STARTTLS never sends `STARTTLS`.
- a certificate signed by an untrusted authority fails. The same server
  succeeds when its certificate authority is added as shown in section 3.
- an unknown value raises at construction.
