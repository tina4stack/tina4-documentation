# ADR-0095: Startup auto-migration holds a cross-process lock, so concurrent boots apply each migration exactly once

- Status: Accepted
- Date: 2026-10-08
- Deciders: maintainer
- Supersedes: none (first ADR governing migration-run concurrency)
- Related: ADR-0004 (best implementation prevails), the auto-migrate-on-startup
  hook (App.start / startServer / _bootstrap_application / auto_migrate_on_startup!)

## Context

`TINA4_AUTO_MIGRATE` (on by default) applies pending migrations at boot. The hook
was documented as running "at most once per process" and the race was described
only for "multi-instance production". Both were wrong in the same way, and
tina4-php#277 proved it against a real PostgreSQL:

- Under `php -S` (incl. `PHP_CLI_SERVER_WORKERS>1`), PHP-FPM and mod_php, **every
  request is a fresh process**, so the hook runs on every request and the
  per-process guard never carries over. Several first requests hit a fresh
  database at once.
- Nothing serialized the run. `migrate()` read the pending list once and applied
  each file; two overlapping runs **both** decided a migration was pending and
  **both** applied it. A data migration then inserted its rows more than once
  (observed 2–6 copies), concurrent `CREATE TABLE tina4_migration` collided on
  `pg_type`/`pg_class`, and `recordMigration()`'s delete-then-insert left the
  tracker showing one row — so the double-apply was **invisible in the ledger**.

This is not PHP-specific at the contract level: any framework that boots several
workers/instances against a fresh database at once has the same race. A
per-process guard cannot fix it (separate processes), so the fix belongs in the
migration runner, in all four frameworks.

## Decision

`migrate()` acquires **one run-wide lock before reading the pending list and
holds it for the whole run**, in Python, PHP, Ruby and Node. The winner migrates
while the rest block, then re-read the applied set and find nothing pending — each
migration applies exactly once however many boots arrive together, and no request
fails on a duplicate key.

The lock is per engine, and every backend **auto-releases on holder death** so a
crash mid-migration never deadlocks the next boot:

| Engine | Lock | Scope / crash-safety |
| --- | --- | --- |
| PostgreSQL | `pg_advisory_lock(k)` / `pg_advisory_unlock(k)` | session; released on disconnect |
| MySQL | `GET_LOCK(name, -1)` / `RELEASE_LOCK(name)` | connection; released on disconnect |
| MSSQL | `sp_getapplock @LockOwner='Session'` / `sp_releaseapplock` | session; released on disconnect |
| SQLite, Firebird, other | OS advisory file lock on a sidecar in the migrations dir | process; released on exit |

- `k` is a stable signed-64-bit key derived from the constant string
  `tina4_migration_lock` (SHA-256, first 8 bytes), so it cannot collide with an
  application's own advisory-lock keys. It is a constant, not user input.
- The file-lock fallback is `flock(LOCK_EX)` where the runtime has it (Python/PHP/
  Ruby) and an **atomic exclusive-create file** where it does not (Node core has
  no `flock`). The Node file records the holder's PID so a waiter can clear a lock
  left by a **crashed** holder — but only when it reads a **valid PID confirmed
  dead**; an empty/unparseable/missing PID is treated as NOT stale, because
  stealing the lock in the microsecond window between create and PID-write
  re-introduced the exact double-apply this ADR removes.
- A backend that cannot take the native lock degrades to the file lock, and
  finally to running unlocked (the pre-fix behaviour) rather than blocking boot.
- The tracking table is ensured **under the lock** (PHP/Python ensure it inside
  the locked run; Ruby/Node keep their single-boot eager ensure and re-ensure
  idempotently under the lock), so concurrent `CREATE TABLE` no longer collides.

### Scope boundary

The native advisory locks (PostgreSQL/MySQL/MSSQL) serialize across HOSTS. The
file-lock engines (SQLite/Firebird) serialize per HOST only. A cross-HOST fleet
on a file-lock engine that boots simultaneously must still set
`TINA4_AUTO_MIGRATE=false` and run one `<cli> migrate` per deploy — the docs say
so. The explicit CLI migrate stays fail-fast (non-zero exit) for CI.

## Consequences

- Each migration applies exactly once under concurrency; data migrations never
  double-insert; `/health` and DB-independent routes keep serving while a boot
  migrates.
- No executable contract fixture: concurrency is proven per framework by a
  **real multi-process test** (no mocks) — several OS processes run `migrate()`
  against one shared SQLite database with a slow data migration, asserting one
  row and one tracker row, each mutation-proved by removing the lock. The
  PostgreSQL/MySQL/MSSQL advisory paths and the Firebird file-lock path are
  exercised by the lab's real-service run. SQLite is the locally-runnable proof.
- `recordMigration()`'s delete-then-insert is unchanged: the lock makes it safe
  (only one run records at a time), and it still supersedes a leftover `passed=0`
  row cleanly.
