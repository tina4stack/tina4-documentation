# ADR-0081: Package/registry publishing runs only from a protected `release` environment, with per-job least privilege

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4 (the Rust CLI) and the four framework repos
  (tina4-python, tina4-php, tina4-ruby, tina4-nodejs) plus tina4-js — every
  workflow that publishes to a public registry or image repository
- **Decision owner:** Andre van Zuydam

## Context

A release tag triggers workflows that hold long-lived, high-value credentials:
crates.io (`CARGO_REGISTRY_TOKEN`), npm, PyPI, RubyGems, Packagist, and GHCR.
Those workflows also build, smoke-test and attest the artifacts. When one job
carries both the build work and the publish token, or when any push of a tag can
reach the publish step unattended, the blast radius of a compromised action or a
mistaken tag is the credential itself.

The build job in the CLI's `release.yml` additionally declared `contents: write`
that it never used — it uploads workflow artifacts and writes an attestation, and
a separate single-writer job touches the GitHub Release.

## Decision

1. **Publish jobs run in a protected `release` environment.** Every job that
   pushes to a registry or image repository declares `environment: release`. The
   environment carries the publishing secret (so no other workflow or job can
   read it) and its protection rules — required reviewer(s) and a tag-only
   deployment-branch rule — are configured in each repo's **Settings →
   Environments**. Adding the `environment:` key is the code half of this
   decision; the protection rules are the settings half and are owned by the
   `tina4stack` account.

2. **Tokens are scoped to the job that needs them.** GitHub grants `permissions`
   per **job**, not per step, so the finest available grain is to isolate the
   token-holding work in its own job. The build/attest job gets least privilege
   (`contents: read` for checkout; `id-token`/`attestations: write` only for the
   provenance step); it does not carry `contents: write`, because the release
   upload is a separate single-writer job.

3. **Trusted Publishing (OIDC) where the registry supports it.** Where PyPI / npm
   / RubyGems support OIDC Trusted Publishing, the publish uses it in place of a
   long-lived token; npm publishes with `--provenance`. Where a token is still
   required, it lives on the `release` environment, never at repo scope.

## Consequences

- A publish cannot run until the `release` environment's protection is satisfied,
  so an unattended or mistaken tag push cannot push to a public registry on its
  own.
- A compromised third-party action in the build matrix cannot read a publish
  token: the token is not present in the build job and the environment secret is
  gated behind the environment's protection.
- Until the `release` environment and its protection rules are created in a
  repo's settings, the `environment: release` key is inert (GitHub creates an
  unprotected environment on first use), so the change is safe to merge ahead of
  the settings work; the protection must then be configured for the gate to bind.

## Alternatives considered

- **Per-step permissions.** Not possible on GitHub Actions — permissions are
  job-scoped. Isolating the token in its own job is the realisable form.
- **Keep publish tokens at repo scope.** Rejected: a repo-scoped secret is
  readable by every workflow in the repo; an environment secret is gated behind
  the environment's protection.
- **Require the environment before merging the key.** Rejected as a blocker: the
  inert-until-configured behaviour lets the workflow change land first and the
  settings follow, without a window where publishing is broken.
