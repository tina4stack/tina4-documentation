# ADR-0094: `Crud.to_crud` is a frontend over AutoCrud, rendered from overridable Frond templates

- Status: Accepted
- Date: 2026-10-08
- Deciders: maintainer
- Supersedes: none (first ADR governing the HTML CRUD-page generator)
- Related: ADR-0004 (best implementation prevails), ADR-0069 (CRUD write allow-list),
  ADR-0088 (strict default CSP + nonce)

## Context

Ruby grew `Tina4::Crud.to_crud` — a one-call server-rendered HTML CRUD admin
(searchable, sortable, paginated table + create/edit/delete modals). The other
three frameworks never had it. Before porting it to Python/PHP/Node two problems
surfaced:

1. **Backend duplication + a bug.** `AutoCrud` already generates the full REST
   backend in all four frameworks — GET list, GET `/{id}`, POST, PUT, DELETE,
   secure-by-default. But `to_crud`'s `sql:` mode registered its OWN bespoke
   POST/PUT/DELETE and NO GET, so the edit modal's `GET /api/{table}/{id}` 404'd
   in sql mode. Two implementations of the same backend, one of them broken.
2. **It violated Tina4's own DX rules.** It emitted a standalone HTML document
   built by string concatenation, with an inline `<style>` block and a `style=`
   attribute (the latter CSP-dead under `default-src 'self'`) — against the
   framework's "template inheritance, shared CSS, no inline styles" principles.

## Decision

`to_crud` is a **frontend only**. It renders an admin UI; it owns **no backend
routes**.

1. **The backend delegates entirely to `AutoCrud`.** `to_crud` requires a `model:`
   (an ORM class); it calls the framework's `AutoCrud` to register the five REST
   routes and the UI's JavaScript talks to those. `to_crud` registers no
   POST/PUT/DELETE/GET of its own. The old bespoke sql-mode write handlers are
   removed.
2. **`model:` is required; `sql:` is an optional listing query inferred from the
   model when omitted.** Pass a model for the backend; optionally pass a custom
   `sql:` SELECT to shape the displayed grid (a filter/join/projection). When
   `sql:` is absent it is derived from the model (`SELECT <columns> FROM <table>`).
   Writes, GET-list and GET-by-id always go through AutoCrud via the model, so a
   custom `sql:` never creates an unauthenticated or divergent write path.
3. **The UI renders from overridable Frond templates**, not inline HTML strings.
   The framework ships `crud/` templates (page shell, table/rows, create+edit
   form, modals); an app overrides any of them by placing the same path under its
   own `templates/` dir (the existing app-first-then-gem resolution — same
   convention as the error pages). No inline `style=`, no inline `on*=`; the only
   inline block is a single nonce'd `<script>` (ADR-0088) wiring actions via
   `data-crud-action` + delegated `addEventListener`. Styling uses tina4-css
   classes (Bootstrap-compatible names; no Bootstrap dependency). The templates
   are a first-class editing surface — clean, commented, minimal logic — so a
   developer restyles the grid or form by editing one `crud/*.twig`.

4. **Column alignment is derived from the model's field types.** Numeric columns
   (integer/numeric/float) are right-aligned (cell AND header); text columns are
   left-aligned (cell AND header); the Actions column is right-aligned. Via
   tina4-css alignment utility classes, never inline styles.

5. **The grid is live/AJAX, driven by the AutoCrud list endpoint.** The initial
   page server-renders the first page of rows; thereafter the nonce'd script
   holds `{search, sort, sort_dir, page}` and on any change (debounced
   as-you-type input, a sort-header click, a pagination click) GETs
   `{prefix}/{table}?search=&sort=&sort_dir=&page=` and re-renders the tbody +
   pager. **Search is live — there is no Search button** — debounced (~300ms),
   and each new request **aborts the previous in-flight one** (`AbortController`),
   so a fast typist never races stale results. The search term is preserved
   across sort and pagination because the script owns the state.

   This requires the **AutoCrud list endpoint to support `search` and
   `sort`/`sort_dir`** (today it supports only page/per_page/limit/offset).
   `search` is `LIKE %term%` OR'd across the model's string/text columns, applied
   before limit/offset with the total reflecting the filtered count; `sort` is
   ADR-0069 safe-sort (a real model column else the pk) with `sort_dir` asc/desc.
   This is an AutoCrud enhancement shipped in all four frameworks (Ruby master →
   Python/PHP/Node), each with a real no-mock test. `to_crud` still registers no
   routes of its own; it consumes the now-searchable/sortable AutoCrud list.

6. **A failed save shows its errors inline — never a false success.** AutoCrud
   answers a failed create/update with a non-2xx status and `{errors:[...]}` (or
   `{error:...}`). The save path checks the HTTP status (not just a `result.error`
   key), and on failure keeps the modal OPEN and renders the messages in a
   per-modal `data-crud-errors` box; on success it closes and refreshes. (The
   original Ruby code only checked `result.error`, so a 422 validation failure
   closed the modal reporting "saved successfully" — a real bug this fixes.)

7. **The scaffolded admin page is secured by default.** `generate crud <Model>`
   writes the `GET /admin/<table>` page with the framework's secure-GET
   (secure_get / @secured / equivalent); `--public` opens the page AND the writes
   together. The AutoCrud READ API (GET list, GET/{id}) stays public by AutoCrud's
   own default; the generated route documents this and that a browser needs a
   token/session to open a secured page.

## Contract (identical across all four; idiomatic names per language)

- Entry: `to_crud(request, options)` (py/rb) · `toCrud` (php/node). Node returns
  `Promise<string>` (async DB adapters); the others return a string.
- Options: `model:` (required), `sql:` (optional, inferred from model),
  `title:`, `prefix:` (default `/api`), `limit:` (default 10). Multi-word option
  keys idiomatic (`primary_key`→none now; `prefix`/`limit`/`title`/`model`/`sql`
  are single-word and identical).
- Side effect: registers the AutoCrud routes for `model` at `prefix` (idempotent).
- Output: the rendered `crud/page` template.
- Templates (overridable): `crud/page`, `crud/table`, `crud/form`, `crud/modals`
  (exact split is the Ruby master's to set; the other three mirror the same set
  and the same override paths).

## Consequences

- One backend, four frontends — no duplicated or divergent CRUD write path; the
  edit-404 is gone (GET comes from AutoCrud).
- Apps can restyle/rework the admin by overriding a template, no framework fork.
- Breaking vs the old Ruby `to_crud`: `sql:`-only (no model) is no longer a full
  CRUD surface — a model is required for writes. Specs that drove sql-only CRUD
  are updated.
- The generator stops violating the framework's own inline-style/template rules.

## Guard

Each framework ships a real no-mock test: a live DB + real request + the real
generator asserts the page renders, the AutoCrud routes are registered, and the
output carries zero inline `on*=` / `style=` attributes (mutation-proven).
