# ADR-0070: A framework opens a browser only in development, never when TINA4_NO_BROWSER is truthy (true/1/yes/on), never when --no-browser is passed, never under CI

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release

## Context

Running a test suite or `tina4 serve` kept opening tabs in the developer's
browser. Nobody decided when a browser should open, so each of the five
launchers grew its own answer, and none of them agreed:

- **The Rust CLI** opened two tabs on every `tina4 serve`: the app at
  `src/main.rs:830`, then `/__dev` 400ms later at `src/main.rs:838`. It opened
  the app tab under `--production` too, never looked at `CI`, and read
  `TINA4_NO_BROWSER` as `true`/`1`/`yes` only (`src/main.rs:580-584`,
  `:993`). It already silenced the framework it spawns
  (`std::env::set_var("TINA4_NO_BROWSER", "true")`, `src/main.rs:587`), so
  both tabs were its own.
- **Python** opens from `run()` whenever `TINA4_NO_BROWSER` isn't
  `true`/`1`/`yes` (`tina4_python/core/server.py:3924-3926`). `on` doesn't
  count, surrounding whitespace isn't trimmed, and it opens in production.
  Its own CLI adds a second variable, `TINA4_OPEN_BROWSER=false`
  (`tina4_python/cli/__init__.py:734`).
- **PHP** has two paths. `App::run()` opened unless `TINA4_SUPPRESS` was
  truthy and never read `TINA4_NO_BROWSER` (`Tina4/App.php:1437`,
  `:1476-1477`). tina4-php#216 fixed that path on 2026-09-24 (see section 4).
  `bin/tina4php serve` is the only launcher anywhere that requires debug mode
  (`bin/tina4php:2210-2211`), but it doesn't check CI or accept `on`.
- **Ruby** opens unconditionally from both server paths in `Tina4.run!`
  (`lib/tina4.rb:608` for Puma, `:614` for WEBrick), in production included.
  `cmd_start` parses `--no-browser` and `TINA4_NO_BROWSER` into an option
  nothing reads (`lib/tina4/cli.rb:680`, `:687-689`).
- **Node** opens unless `TINA4_NO_BROWSER` is truthy
  (`packages/core/src/server.ts:2355-2358`), with no debug or CI check. Under
  `TINA4_PRODUCTION=true` every cluster worker reaches that line, so one start
  opens one tab per CPU core. The CLI parses `--no-browser`
  (`packages/cli/src/bin.ts:332`) and `serve.ts` drops it.

Citations are against tina4 `origin/main` 6030c77, tina4-python `origin/v3`
001cf91, tina4-php 94e493ca, tina4-ruby 26798e2 and tina4-nodejs c296cdc.

A browser tab is a side effect on the developer's desktop. It helps in exactly
one situation: a person just started a development server and wants to look at
it. Anywhere else (a test run, a CI job, a production boot, a container, a
second worker) it's noise at best, and at worst it's a tab pointing at a
production process on someone's laptop.

## Decision

A launcher opens a browser only when **all four** rules below allow it. Each
rule is a veto. No flag, argument or variable can force a browser open past a
veto, so there's no precedence to learn: any one of them is enough to stop it.

### 1. Development only

A launcher opens a browser only when the server it started is in development.

**A framework server is in development when its resolved debug mode is on**,
which is how all four already decide it. `TINA4_DEBUG` is read with the
framework's own truthy helper, and unset means off:

| Framework | Debug decision | Truthy helper |
| --- | --- | --- |
| Python | `is_debug = is_truthy(os.environ.get("TINA4_DEBUG", ""))`, `tina4_python/core/server.py:3885` | `is_truthy`, `tina4_python/dotenv/__init__.py:282` |
| PHP | `App::isDevelopment()`, `Tina4/App.php:736-738` (`$this->development` or truthy `TINA4_DEBUG`, default `'false'`) | `DotEnv::isTruthy`, `Tina4/DotEnv.php:417-420` |
| Ruby | `is_debug = Tina4::Env.is_truthy(ENV["TINA4_DEBUG"])`, `lib/tina4.rb:604` | `Tina4::Env.is_truthy`, `lib/tina4/env.rb:110-118` |
| Node | `const isDebug = isTruthy(process.env.TINA4_DEBUG)`, `packages/core/src/server.ts:2255` | `isTruthy`, `packages/core/src/dotenv.ts:316-319` |

An explicit argument that turns debug on (PHP's `development` property, Ruby's
`run!(debug:)`) counts, per ADR-0041. `TINA4_PRODUCTION=true` never counts as
development.

**The `tina4` CLI decides the mode of `tina4 serve` before it spawns anything:**

1. `--production` means production, whatever else is set.
2. Otherwise `--dev` means development.
3. Otherwise a tina4-js project is development. It has no `TINA4_DEBUG`
   switch, and without `--production` it runs the Vite dev server.
4. Otherwise a backend project is in development only when `TINA4_DEBUG` is
   truthy, which is the same switch the framework will read.

Every backend project `tina4 init` scaffolds writes `TINA4_DEBUG=true` to
`.env`, so a fresh project still opens its tab. A project with no
`TINA4_DEBUG` at all is served in production mode by its framework, and gets
no tab.

### 2. Never when `TINA4_NO_BROWSER` is truthy

**The truthy set is `true`, `1`, `yes`, `on`**, compared after trimming
surrounding whitespace and ignoring case. That's the set every framework's
`is_truthy` helper already uses. Anything else is not truthy, including an
empty value, `y`, `t` and `enabled`. `TINA4_NO_BROWSER=false` doesn't veto,
and it doesn't force a browser open either.

A variable resolves from the process environment first, then the project's
`.env`, which is the precedence every framework's dotenv loader applies. So
`TINA4_NO_BROWSER=on` in `.env` is honoured.

`TINA4_NO_BROWSER` is the one variable. No framework adds a second one.
Python's `TINA4_OPEN_BROWSER=false` may stay as an extra veto until 3.14.0,
but it can't open a browser any of these rules have vetoed.

### 3. Never when `--no-browser` is passed

Every launcher that accepts `--no-browser` honours it: `tina4 serve`,
`tina4python serve`, `tina4php serve`, `tina4ruby start` (and its `serve`
alias) and `tina4nodejs serve`. A programmatic equivalent, such as Python's
`run(no_browser=True)`, has the same effect. These arguments can only veto. `no_browser=False` means
"this argument doesn't veto". It doesn't mean "open one", so ADR-0041 (an
explicit argument beats the environment) never lets an argument override a
truthy `TINA4_NO_BROWSER`.

### 4. Never under CI

**Under CI means any one of these eight variables is set:**

```
CI  CONTINUOUS_INTEGRATION  GITHUB_ACTIONS  GITLAB_CI
BUILDKITE  JENKINS_URL  TF_BUILD  TEAMCITY_VERSION
```

That's the union of the two lists that already shipped:
`App::CI_ENVIRONMENT_VARIABLES` in tina4-php (`Tina4/App.php:1760` on
`origin/v3` a8525acd, from tina4-php#216) and `Tina4::CI_ENV_VARS` in
tina4-ruby (`lib/tina4.rb:535` on `fix/zero-dep-builtin-server` d04338e).
PHP's list has everything except `TEAMCITY_VERSION`. Ruby's has everything
except `TF_BUILD`. Every launcher uses exactly this list, in this order, and
its suite asserts the list against the fixture's `ci_env_vars` array element
for element.

**The per-variable rule (maintainer decision, 2026-09-24).** A variable
counts as set when its value, trimmed and lower-cased, is non-empty and is
none of `false`, `0`, `no`, `off`. Any one variable that counts is enough.

- These count: `CI=true`, `CI=1`, `CI=yes`, `CI=woodpecker`,
  `GITHUB_ACTIONS=true`, `JENKINS_URL=http://jenkins.example:8080/`,
  `TF_BUILD=True` and `TEAMCITY_VERSION=2024.12`.
- These don't: an unset variable, an empty value, a value of only whitespace,
  and `false`, `0`, `no` or `off` in any case with any surrounding whitespace.

The fixture carries the not-set values as `ci_not_set_values`. tina4-php#216
shipped a narrower not-set list (`false`, `0` only), so `CI=no` and `CI=off`
counted as CI there; PHP moves to this rule. A false "this is CI" only costs
a tab, but `no` and `off` read as "not CI" to anyone who types them, so they
mean not CI everywhere.

The Ruby branch counts any non-empty value, so `CI=false` counts as CI there.
It moves to this rule too. The four auth modules still use `is_truthy(CI)` to skip
minting a dev secret (`tina4_python/auth/__init__.py:73`,
`Tina4/Auth.php:292`, `lib/tina4/auth.rb:522`,
`packages/core/src/auth.ts:39`), and this ADR doesn't change that.

### 5. At most one tab, and one decider

- A start opens at most one tab, pointing at the app's own URL. The dev
  dashboard (`/__dev`) is printed, not opened.
- When the `tina4` CLI spawns a framework server, the CLI decides. It computes
  its answer first, then sets `TINA4_NO_BROWSER=true` in the child's
  environment, so the child can't open a second tab.
- In a multi-process server, only the primary process may open the tab. No
  worker ever does (this is Node's cluster mode).

A framework may add a veto of its own (PHP's CLI never opens on Windows), as
long as it's documented. It may not add a way to open.

## Test contract

The shared fixture is `plan/v3/fixtures/browser_open_contract.json`. Its
`decision_table` lists every case as environment + flags + mode, with the
expected `opens`. Its `mode_table` lists how the CLI resolves the mode. Each
launcher's suite runs every row against its real gate, with the environment
set for real and no mocks. It tests both directions: every rule vetoes on its
own, and nothing else vetoes.

The fixture's `ci_env_vars` is the list itself, so each runner asserts it
element for element as well as running the cases. The cases set each of the
eight variables on its own, then clear each one with `false`, `0` and an
empty value.

Mutation-prove each rule. Remove the development check, ignore the flag,
ignore the variable, drop `on`, make the comparison case-sensitive, ignore CI,
read only `CI`, drop a variable from the list, or count `false`, `0`, `no` or `off` as set.
Each of those has to turn at least one named case red.

The CLI proves the gate in `src/main.rs`: `should_open_browser`,
`resolve_serve_mode`, `CI_ENV_VARS` and thirteen named tests. The frameworks' invariants stay
owed until their fixes land.

## Consequences

- `tina4 serve` opens one tab, not two, and only for a development server.
  `tina4 serve --production`, a CI job, and a project with `TINA4_DEBUG` unset
  or false open nothing.
- Test runs stop opening tabs. A suite that boots a real server runs under CI
  in the pipeline, and locally it's covered by development-only for a
  production-mode fixture and by `TINA4_NO_BROWSER`, which every test harness
  should export anyway.
- `TINA4_NO_BROWSER=on` starts working in Python, PHP and the CLI, where it was
  silently ignored.
- A project with no `TINA4_DEBUG` that relied on `tina4 serve` opening a tab
  loses it. Add `TINA4_DEBUG=true` to `.env` (the scaffold already does), or
  pass `--dev`.
- The `/__dev` dashboard no longer opens itself. Its URL is printed at start.

## Related

- **ADR-0041**: an explicit argument beats the environment. Arguments here can
  only veto, so the two never conflict.
- **ADR-0038**: one canonical `TINA4_TEST_*` set. A harness that boots a real
  server should export `TINA4_NO_BROWSER=true` alongside it.
- **ADR-0004**: best implementation prevails. PHP's `tina4php serve` was the
  only launcher that required debug mode. Node's truthy set was the only
  complete one.
