# ADR-0098: Spec-Driven Development — a per-feature spec is the source of truth, mapped 1:1 to its contract fixture

- Status: Accepted
- Date: 2026-10-18
- Deciders: maintainer
- Supersedes: none
- Related: ADR-0099 (Tina4-Driven Development, T4DD - the plan-driven umbrella this spec layer sits under), ADR-0004 (best implementation prevails), ADR-0024 (one shared fixture + one checker per pluggable subsystem), ADR-0043 (a documented contract cites its ADR); the contract backbone in `CONTRACT-MAP.md` + `scripts/audit-contract-fixtures.py`; the `tina4-maintainer` and `tina4-developer-*` skills

## Context

Tina4 was already most of the way to Spec-Driven Development (SDD) without naming
it: an ADR records WHY a cross-framework behaviour is what it is, a contract
fixture (`fixtures/*_contract.json`) is that decision made EXECUTABLE, and
`audit-contract-fixtures.py` proves all four frameworks obey it. What was missing
was a single, canonical, human-readable spec per feature - the intent and the
acceptance criteria a person (or an agent) reads first and builds from.

Without it the "spec" was scattered: `MASTER-SPEC.md` (prose, with stale numbers),
the per-feature `features/NNN-*.md` plans, and the fixtures each held a piece, and
none of them tied a human-readable acceptance criterion to the executable case that
proves it. So "proven/owed" was tracked per feature, not per behaviour, and a
reader could not see which criterion a given test defended.

## Decision

Every feature gets a canonical spec at `plan/v3/specs/NNN-<feature>.md`, and it is
the source of truth from which the code is derived - not the other way round.

1. **A spec carries intent, acceptance criteria, non-goals and tasks.** Each
   acceptance criterion is a numbered `AC-N` given/when/then line - one behaviour a
   single test can turn red or green.

2. **Each `AC-N` maps to cases in the feature's contract fixture, and every fixture
   case is claimed by an `AC-N`.** The AC is the human form; the fixture case is the
   executable form. One AC per case is the goal; an AC may cite several cases when a
   behaviour genuinely needs them. `scripts/audit-spec-coverage.py` gates this both
   ways and fails the build on any gap (an AC with no case, a case named that the
   fixture lacks, or a fixture case no AC claims).

3. **The spec is the source of truth.** To change behaviour, change the spec first
   (add or amend an `AC-N`), supersede the ADR if a decision moves, update the
   fixture, then bring the four frameworks to the new criterion. A spec that
   disagrees with the code is the bug, exactly like a doc that disagrees with the
   code (the First Principle).

4. **Adoption is per feature and additive.** A feature with no spec yet is simply
   not gated; existing fixtures keep working unchanged. The gate passes when no
   feature spec exists at all. `MASTER-SPEC.md` retires into per-feature specs over
   time; its stale numbers were the drift this closes.

5. **This sits on top of the existing backbone, it does not replace it.** The
   fixture + `audit-contract-fixtures.py` still prove the four frameworks obey the
   contract. SDD adds the acceptance-criteria front-end and the spec↔fixture gate.

The skills carry the working discipline: `tina4-maintainer` (the feature update
loop now begins "write/confirm the spec") and `tina4-developer-*` (app features are
driven by `AC-N` → one real, no-mock test each).

## Consequences

- `plan/v3/specs/` holds one spec per adopted feature, from `specs/TEMPLATE.md`.
- `audit-spec-coverage.py` runs in `audit-truth.yml` and blocks spec↔fixture drift.
- "Proven/owed" can be reasoned per criterion: an `AC-N` can be proven in Ruby and
  owed in Node, because it maps to a fixture case the per-language runners execute.
- Writing a spec for a large existing fixture means one AC per case (e.g. the
  adapter fixture's 40 cases → 40 ACs). That is the honest cost of making every
  behaviour a named, human-readable criterion; it is paid per feature, when adopted.

## Alternatives rejected

- **Adopt an external SDD toolchain (Spec Kit, Kiro).** Rejected: a spec is a
  markdown file plus a gate, not a dependency. Tina4 is zero-dependency and
  convention-over-configuration by design (the `tina4-maintainer` reuse ladder).
- **Carry acceptance criteria as prose inside the fixture JSON.** Rejected: the
  fixture is machine-first; a human-readable spec beside it, mapped by case id,
  reads better and keeps the fixture clean. Drift is prevented by the gate, not by
  co-location.
- **Keep `MASTER-SPEC.md` as the single spec.** Rejected: one monolith with stale
  numbers is the drift SDD is meant to kill; per-feature specs gated against the
  fixtures replace it.
