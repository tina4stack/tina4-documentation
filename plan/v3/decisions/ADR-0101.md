# ADR-0101: the RTC config route and signalling socket require auth by default

- Status: accepted
- Date: 2026-10-23
- Context: the realtime subsystem (`calls` feature), ADR-0019 (write-secure-by-
  default routing), the realtime guide §4; tina4-python#252
- **Breaking change** (security hardening): see Consequences.

## Context

With TURN configured (`TINA4_RTC_TURN_URL` + `TINA4_RTC_TURN_SECRET`), the
`calls` feature serves `GET {prefix}/api/rtc/config`, and every response mints a
fresh, valid coturn credential. It was registered public, and so was the
`{prefix}/ws/rtc/{room}` signalling socket. Anyone on the internet could
therefore fetch a credential and use the operator's TURN server as a relay:
unbounded bandwidth on the operator's bill, and arbitrary UDP sent from the TURN
server's IP (tina4-python#252).

This was documented as intentional - the browser needs ICE servers before it can
authenticate anywhere, which is true for anonymous calling. But it held for every
app, including the many that only ever call between signed-in users. For those,
the public route was pure exposure, and there was no way to close it: the route
is registered inline by the feature, so an app could not wrap it with a guard.
The short credential TTL does not bound the abuse either - nothing has to leak, a
script just fetches a fresh credential on a loop.

The framework's own rule for ambiguous auth is already secure-by-default
(ADR-0019: a write route requires auth unless it opts out with `@noauth`). The
RTC surface was the drift.

## Decision

Both endpoints require a valid token by default. An app opts out with
`TINA4_RTC_REQUIRE_AUTH=false`:

- unset, or any value other than a recognised opt-out, secures both the config
  route and the signalling socket (a valid JWT is required - the config route on
  the request, the signalling socket on the upgrade handshake);
- `TINA4_RTC_REQUIRE_AUTH` set to `false`, `0`, `no` or `off` (case-insensitive,
  trimmed) restores the open behaviour, for an app that genuinely wants anonymous
  calling.

The opt-out is a **blacklist of falsey values**, not a whitelist of truthy ones:
only a recognised opt-out opens the relay, so a typo (`TINA4_RTC_REQUIRE_AUTH=ture`)
keeps it secured rather than silently opening it. Each framework secures the two
routes through its own existing mechanism - Python's `handler._secured`, PHP's
`->secure()` / `secure:` argument, Ruby's `.secure`, Node's `.secure()` - so the
upgrade/dispatch path enforces it exactly as any other secured route.

## Consequences

- **Breaking for anonymous-calling apps.** An app that relied on the open config
  route or signalling socket and does NOT set `TINA4_RTC_REQUIRE_AUTH=false` will
  see those endpoints start returning 401 after the upgrade. The fix is one env
  var; the CHANGELOG calls this out under a BREAKING heading.
- **Safe for everyone else.** An app that calls between signed-in users gets the
  correct posture with no change, and the TURN relay stops being an open resource.
- Identical across all four frameworks, pinned by `rtc_auth_contract.json`
  (three invariants: secured-by-default, explicit-opt-out-opens, only-explicit-
  falsey-opens) and proven on the real route tables after a real registration, no
  mocks, each mutation-proved.
- The realtime guide §4 is updated: the open route is now the opt-in, not the
  default.
