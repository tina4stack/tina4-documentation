# ADR-0096: The dev-admin peer gate exempts the static toolbar assets, gains a raw-peer opt-in, and never injects a toolbar it would refuse

- Status: Accepted
- Date: 2026-10-08
- Deciders: maintainer
- Supersedes: none (refines the DEVADMIN-DEC-02 / ADR-0078 peer gate; does not relax it)
- Related: ADR-0078 (dev-surface peer/host/origin gate), ADR-0082 (one gate for every /__dev request)

## Context

With `TINA4_DEBUG=true`, every `/__dev` request from a non-loopback socket peer
is refused `403 (non-loopback peer)` - the right default for a network-exposed
debug box. But in a Docker dev box the port is published, so the browser's
requests arrive from the container-network gateway (e.g. `172.22.0.1`), never
loopback. tina4-php#279 showed three consequences:

1. The toolbar's own `/__dev/toolbar.css` and `/__dev/toolbar.js` - static
   framework files with no secrets - were refused, so every page carried a
   broken toolbar whose stylesheet and script 403'd.
2. No setting admitted a browser in that position. `TINA4_HOST` only widens the
   Host allow-list; `TINA4_MCP_TOKEN` is read from an `Authorization`/`X-MCP-Token`
   header a page's `<link>`/`<script>` cannot send; `TINA4_TRUSTED_PROXIES` is
   deliberately not consulted (the gate reads the raw peer).
3. The toolbar markup was injected regardless of whether the viewer's peer would
   be admitted, so a refused viewer always got the broken markup.

## Decision

Three changes, identical across Python, PHP, Ruby and Node. The peer gate itself
is NOT relaxed: a non-loopback peer still cannot reach the dashboard or any
action endpoint by default.

1. **The static toolbar assets are exempt from the peer gate.** `/__dev/toolbar.css`
   and `/__dev/toolbar.js` are served to any peer (the Host allow-list and the
   same-origin check still apply). They carry no secrets and expose no actions,
   and the injected toolbar needs them wherever it appears. This restores the
   3.13.136 behaviour for these two paths only - every other `/__dev` path,
   including the dashboard and the file/DB/metrics tools, stays behind the peer
   gate.

2. **`TINA4_DEV_ALLOWED_PEERS` is a raw-peer opt-in.** A comma-separated allow-list
   of IPs or CIDRs (IPv4 and IPv6; an IPv4-mapped IPv6 peer is matched as IPv4).
   A peer in the list reaches the full `/__dev` surface. It is matched against the
   REAL socket peer ONLY, never a forwarded header, so `X-Forwarded-For` cannot
   spoof it. Default unset = the strict pre-#279 behaviour. This is the documented
   way to use the dashboard from a Docker dev box (`TINA4_DEV_ALLOWED_PEERS=172.16.0.0/12`).
   It sits beside `TINA4_HOST` and `TINA4_MCP_TOKEN` as an explicit, operator-set
   widening of a deny-by-default boundary.

3. **The toolbar is not injected for a viewer the gate would refuse.** Injection
   now checks the same Host + raw-peer gate: a refused viewer gets a clean page
   with no toolbar markup (so nothing 403s), and an admitted viewer (loopback, or
   a `TINA4_DEV_ALLOWED_PEERS` peer) gets the toolbar whose assets then load.

### Scope boundary (unchanged security posture)

`TINA4_DEV_ALLOWED_PEERS` only ever ADMITS a raw peer; it never consults a
forwarded header and never lifts the Host or same-origin checks. With it unset,
#279's behaviour is exactly the prior strict gate minus the two static-asset 403s.
The dashboard runs DB queries and sandboxed file tools, so admitting a peer is a
deliberate operator choice for a trusted dev network, not a default.

## Consequences

- A Docker dev box loads the toolbar out of the box and reaches the dashboard
  with one env var; a plain network-exposed box still refuses both by default.
- No executable fixture: the gate is proven per framework by a real test with a
  genuine non-loopback peer (a real `php -S`/Node server reached over the host's
  own non-loopback IPv4; the Python ASGI front controller driven with a real
  `scope["client"]`; the Ruby handler driven with a real `REMOTE_ADDR`), each
  asserting assets-200 / dashboard-403 / opt-in-200 / no-inject, and the CIDR
  matcher covered by a pure v4/v6/mapped/boundary matrix. Mutation-proved.
- Implemented via one helper trio per framework - `ip_in_cidr` / `dev_peer_allowed`
  / `dev_toolbar_allowed` (PHP `ipInCidr`/`devPeerAllowed`/`toolbarAllowed`, Node
  `ipInCidr`/`devPeerAllowed`/`devToolbarAllowed`) - using the language's own IP
  library (Python `ipaddress`, PHP `inet_pton`, Ruby `IPAddr`, Node `net.BlockList`).
