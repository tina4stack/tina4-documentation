# ADR-0028: the database session backend follows the configured connection on every engine

- Status: accepted
- Date: 2026-08-04
- Context: ADR-0024 (a pluggable subsystem's contract), ADR-0021 (log-loud-and-degrade),
  session contract fixture invariant `every-backend-works-on-every-engine-it-claims`

## Context

Node's database session backend was SQLite-only. `resolveDbPath()` threw on any
non-sqlite `TINA4_DATABASE_URL`, and two assertions in
`test/sessionExpiryContract.test.ts` pinned that throw as the contract.

The operator-visible consequence is ADR-0024's founding scenario, landing in the
one subsystem that decides whether anyone is logged in: develop on sqlite, deploy
on postgres, and the app does not start. The same `.env` that worked in Python,
PHP and Ruby raised in Node.

The throw itself was not the original defect. It was a fix for a worse one:
`resolveDbPath()` used to strip a `sqlite://` prefix and otherwise return the
literal `"data/tina4_sessions.db"`, so a postgres URL round-tripped happily while
writing SQLite files into the process working directory. Measured from a clean
temp cwd: round-trip true, and `data/` contained `tina4_sessions.db`, `-shm` and
`-wal`. Every horizontally-scaled instance then had its own private session store
and a user was logged out on every request that landed elsewhere - an outage that
looks exactly like success. Refusing loudly was the right call at the time.

## The wrong premise, recorded because it is the point of this ADR

The first assessment of this invariant concluded that multi-engine support was
too expensive to build, on this reasoning:

> Node's session API is SYNCHRONOUS, so a multi-engine backend would require a
> synchronous Postgres bridge, and that price is not worth paying for this
> backend.

**That premise was false.** The sync-over-async bridge already existed:
`packages/core/src/sessionHandlers/syncBridge.ts` and `syncSocket.ts`, with four
consumers already shipping on it - the RESP client (redis and valkey), the
memcached handler, and the MongoDB client. The cost that was described as
prohibitive had already been paid, and paid four times over.

The consequence was not academic. On that premise the decision was made to keep
Node SQLite-only and to close the invariant by documenting the limitation instead
of removing it, and an instruction to that effect was relayed to the implementer.
The premise went unchallenged because it sounded like an architectural constraint
rather than a checkable claim. It is recorded here in full, including that the
coordinator relayed it, because an ADR that records only the conclusion would let
exactly this recur: the next person to ask "can the session backend speak
postgres?" would find a decision that says no and a rationale that is wrong.

The check that would have caught it costs one command:

```
grep -rln "syncBridge\|syncSocket" packages/core/src/
```

**Rule this leaves behind: before accepting "we would have to build X" as a
reason not to do something, grep for X.** A cost that is asserted rather than
measured is not a cost.

## Decision

**The database session backend follows the configured connection, on every engine
the ORM layer supports** - sqlite, postgres, mysql, mssql and firebird. The async
drivers ride the existing `syncBridge`; no second bridge was built. SQLite stays
on `node:sqlite`, which is already synchronous, because routing it through the
bridge would only make it slower.

Two properties are preserved, both load-bearing:

1. **The anti-demotion guard stays.** An unrecognised scheme still RAISES, naming
   the scheme it got, and a session on a remote engine still leaves nothing on
   local disk. The two assertions that pinned the old throw were re-expressed to
   assert the new contract, not deleted - the failure they were protecting against
   is unchanged.
2. **No I/O in the constructor (ADR-0021).** The constructor resolves only the
   path; the connection opens on first use. A multi-engine rewrite is the single
   most likely change to reintroduce constructor-time I/O, so the invariant-4 gate
   was re-run after every change rather than at the end.

## Consequences

- Node's database session backend works on sqlite, PostgreSQL and MySQL, proved by
  a real round trip through a fresh handler on each. MSSQL and Firebird are wired
  through the same path but are not yet exercised by a live test.
- The "same .env raises in Node only" asymmetry is gone. ADR-0024's one-env-var
  promise now holds for this backend in all four frameworks.
- `test/sessionExpiryContract.test.ts` changed two assertions. That file is a
  contract suite, so the change is deliberate and is described in the commit
  rather than being silent.

## Alternatives rejected

- **Keep Node SQLite-only and document the limitation.** This was briefly the
  accepted decision, on the false premise above. Rejected once the premise was
  checked: it made a documented exception out of a problem that did not exist.
- **Build a second, session-specific synchronous bridge.** Rejected: the existing
  one already had four consumers. A second bridge would have been a new mechanism
  to maintain, test and reason about, for a capability already in the tree.
- **Make the session API asynchronous.** Rejected as out of proportion: the
  session is read and written inside a monkey-patched `res.end`, so making it
  async would change the shape of the request pipeline for every user of the
  framework, to solve a problem the bridge already solves.
