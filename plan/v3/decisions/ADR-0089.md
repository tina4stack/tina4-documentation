# ADR-0089: tina4-go serve/DevReload is watch -> go build -> bounce the child, not in-process re-import

Status: Accepted (2026-10-01; the biggest fork a Go port introduces)
Date: 2026-10-01
Context: scoping spike, `plan/go/ARCHITECTURE.md`
Relates to: ADR-0017 (graceful shutdown), ADR-0047 (shutdown clauses), the Rust CLI `tina4 serve`

## Context

The four frameworks are interpreted. When `tina4 serve` sees a file change it does
not restart anything: it POSTs `/__dev/api/reload`, the framework re-imports the
changed modules inside the running process, and then pushes a browser reload over
the `/__dev_reload` WebSocket. The child process lives; only its module table
moves. (`tina4/src/main.rs` `handle_serve`, the watcher at `watcher::watch_and_reload`.)

Go is compiled. A running Go binary cannot re-import a changed `.go` file into
itself, so the in-process reload path simply has no meaning for a Go target. The
edit has to travel a different road: the watcher must rebuild the binary and then
swap the running child for the fresh one, without the developer losing the port
or the browser tab they are watching.

The CLI already has every piece this needs. The nodejs arm of
`start_language_server` prefers a built `dist/app.js` over the transpile-at-runtime
dev path, so "run the compiled artifact" is not a new idea. The respawn loop in
`handle_serve` (currently dormant, kept for crash detection) is exactly a
kill-group-then-start-again machine. And child supervision already makes every
child its own process-group leader (`setpgid`) and kills the whole tree with
`killpg` on SIGTERM, so a Go `main` that itself spawns nothing still bounces
cleanly.

## Decision

For a Go project `tina4 serve` runs a compile-and-bounce loop, NOT the reload POST:

1. On a meaningful source change, run `go build` into a temp output.
2. If the build fails, keep the old child serving and surface the compiler error
   to the terminal and the browser overlay. A red build never takes the site down.
3. If the build succeeds, bounce the child: `killpg` the old group, start the new
   binary with the same `PORT`/`HOST`, wait for it to bind, then push the browser
   reload over the existing `/__dev_reload` WebSocket.
4. Preserve the socket where the runtime allows a graceful handoff (pass the
   listening fd to the child, or bind-retry with `SO_REUSEADDR` during the
   sub-second gap); otherwise accept a brief connection refusal during the swap
   and let the browser's reload retry cover it.

The developer SEES the same thing they see today: save a file, the browser
refreshes. Only the mechanism under it changes from re-import to rebuild-and-bounce.

## Resolved (2026-10-01)

- **Socket handoff: accept the sub-second refusal, lean on the browser retry.** No
  listener-fd inheritance. On a passing build the loop `killpg`s the old child,
  starts the fresh binary on the same port, waits for it to bind, and pushes the
  browser reload; a <1s connection refusal on localhost during the swap is covered
  by the browser's reload retry. Chosen for far less code and no platform-specific
  fd-passing plumbing on a localhost dev loop; fd inheritance can be revisited later
  behind this same contract if a zero-drop swap is ever wanted.
- **Build cadence: debounce.** Coalesce saves over a short debounce window and run
  one `go build` per quiet point, so a noisy editor cannot trigger many builds a
  second. (Same debounce the watcher already applies before a reload POST.)
- **`tina4 serve` owns the `go build`.** The Go arm of `start_language_server` runs
  the build and the bounce directly, keeping the toolchain in the CLI where the
  other language arms already live; no separate `--managed` Go wrapper.

## Consequences

- A new `start_language_server` arm for Go, and the dormant respawn loop is
  re-activated for this one target.
- `tina4 serve` gains a Go branch; the reload-POST path is skipped for Go.
- No change to the interpreted frameworks.
