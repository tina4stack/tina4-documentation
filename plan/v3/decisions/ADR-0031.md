# ADR-0031: memcached invalidates by NAMESPACE GENERATION, and redis clears by SCAN

- **Date:** 2026-08-04
- **Status:** Accepted
- **Scope:** `clear()` on the cache backends in all four frameworks.
- **Relates to:** [ADR-0024](ADR-0024.md) (the swap must work, and rule 4: the
  zero-dependency default counts), [ADR-0012](ADR-0012.md) (settle a contract
  against real-world frameworks).

## The decision

> **`clear()` removes every entry THIS cache can serve, on every provider, and
> nothing that belongs to anyone else.**
>
> - redis / valkey: a `SCAN ... MATCH <prefix>*` cursor loop plus `DEL`, on both
>   the driver transport and the raw RESP transport. Never `KEYS`, never
>   `FLUSHALL`, never `FLUSHDB`.
> - memcached: bump a shared NAMESPACE GENERATION counter that every real key
>   carries. Never `flush_all`, and never a local write log.

## The defects this closes

Measured 2026-08-01, re-measured at `v3` HEAD 2026-08-04.

**redis/valkey, raw RESP transport: `clear()` was a literal no-op** in Python,
PHP and Ruby. The comment said "no easy pattern delete, let the TTL handle it".
That is the ZERO-DEPENDENCY default install, so a write never invalidated the
persistent DB query cache and every instance kept serving pre-write rows until
the TTL ran out.

It survived because the test environments install the redis client library, so
every existing redis test took the DRIVER path. **The default transport had no
coverage at all.** That is the ADR-0024 rule 4 failure in its purest form, and
the lesson generalises: if a subsystem ships two transports, the tests must pin
which one they are on, or they will silently all take the same one.

**memcached: `clear()` deleted only the keys THIS process had written**, so a
second instance kept serving rows the first had just invalidated. The version
before that sent `flush_all`, which wipes every key on the instance including
every other application's - and `cache_clear()` is public API, so calling it
destroyed other tenants' data.

## Why the namespace generation

memcached has no `KEYS`, no prefix scan and no prefix delete. So there are
exactly three candidate answers, and the first two are the two that shipped:

| approach | invalidates globally | leaves other tenants alone |
| -------- | -------------------- | -------------------------- |
| `flush_all` | yes | **no - destroys their data** |
| delete the local write log | **no - a second instance serves stale rows** | yes |
| namespace generation | yes | yes |

The generation is the documented memcached idiom: a counter at a well-known key,
folded into every real key, bumped on clear. One `incr` orphans every
previously-written entry for every instance at once. The orphans are reclaimed
by memcached's own TTL and LRU - **unreachable is what "removed" means for a
cache**, and it is what `flush_all` achieves too, just without the collateral.

`incr` is atomic, so two instances clearing concurrently both advance rather
than racing to write the same value.

### The generation is read from the server on EVERY operation

Deliberately, and it costs one extra round trip. Caching it in-process
reintroduces exactly the bug being fixed: an instance holding a stale generation
keeps computing the OLD key, the old key still holds the old value, and it
serves a stale hit after another instance cleared. A cache that is wrong only
sometimes, only under concurrency, is worse than one that is wrong always.

This is pinned by a negative test (`memcached entries written before a clear
stay invalid`), and the memoise-the-generation mutation is one of the proofs.

## Why SCAN and not KEYS

`clear()` runs on EVERY WRITE in persistent DB-cache mode. `KEYS` is O(N) over
the whole keyspace and blocks the entire Redis server for its duration; Redis's
own documentation says to prefer `SCAN` in production. A blocking O(N) command
on every write is a production hazard, not a style preference.

Per ADR-0012 the upstream guidance outranks internal precedent, so Node's
already-working `KEYS` implementation moved to `SCAN` too rather than the other
three copying it.

**The page count in the test is load-bearing and was MEASURED.** At 250 keys a
`SCAN ... COUNT 500` returns everything on the first page with cursor 0, so a
cursor loop that stops after one page still clears everything and the test goes
green while gating nothing. That is not hypothetical: the first version of the
test used 250 and stayed GREEN under a mutation that broke the loop, in three
frameworks independently. The suites now use 1500-2000 keys, and the same
mutation fails.

## The RESP reader had to be rewritten first

The zero-dependency reader did a single `recv(65536)` and string-split the
result. That truncated any reply larger than the buffer, which meant:

- a large cached VALUE came back corrupt - a latent data bug, not just a
  blocker for the scan;
- a page of scanned keys came back short, so a `clear()` built on it would have
  cleared only some of them and still looked green on a small test.

It now reads one complete reply through a buffered stream and parses multi-bulk
arrays recursively. Fixing `clear()` on the default transport was not possible
without this, which is a fair summary of how long the default transport had gone
unexercised.

## How it is held

`plan/v3/fixtures/cache_contract.json`, invariant
`clear-really-invalidates-on-every-provider`, with the four suites it names.
Both halves are pinned: a clear must remove what it owns, and a clear must NOT
touch a key outside the prefix.

One honest gap, recorded rather than papered over: the "another tenant's keys
survive" case for memcached is asserted but has no mutation proof, because the
only change that would break it is sending `flush_all` at a shared service,
which the working rules forbid. The assertion is right; it is not a
mutation-proved gate.
