# ADR-0080: The release is signed only over CI-verified bytes, and every install path verifies the published checksum

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4 (the Rust CLI) — the release-signing pipeline, the one-line
  installers, and `tina4 update`
- **Decision owner:** Andre van Zuydam

## Context

The tina4 CLI ships prebuilt binaries on each GitHub Release. Windows code
signing is a deliberate, local, human-in-the-loop step: CI builds and publishes
a **draft** release (binaries, `SHA256SUMS`, SBOM and licence assets), and a
maintainer later EV-signs the Windows `.exe` on their own machine (the SimplySign
2FA is never stored in CI) and publishes.

That split created three trust gaps:

1. **The local signer signed whatever was on the draft.** The signing scripts
   downloaded the draft assets and signed the `.exe` with no check that those
   bytes were the ones CI built. A tampered draft asset could be EV-signed.
2. **The signer rebuilt the whole `SHA256SUMS`.** After signing it regenerated
   the entire checksum manifest locally, re-deriving every line — including the
   lines for assets it never changed — from local tooling, reopening the very
   gap a verification would close.
3. **The installers and self-update trusted the download.** `install.sh` /
   `install.ps1` skipped the checksum when `SHA256SUMS` was absent, and
   `tina4 update` replaced the running binary with no integrity check and no
   protection against being rolled back to an older build.

## Decision

1. **Verify CI provenance before signing.** Before the local signer touches the
   `.exe`, `scripts/verify-release-inputs.py` confirms that (a) `SHA256SUMS`
   exactly covers the downloaded assets, (b) every asset's SHA-256 matches its
   entry, and (c) every asset carries a build-provenance attestation bound to
   this repo's `release.yml` workflow **at this release tag**
   (`gh attestation verify --cert-identity …@refs/tags/<tag>`). CI attests every
   CI-built binary, **including the unsigned Windows `.exe`**, so its
   pre-signing bytes are covered. Signing aborts on any mismatch.

2. **Signing changes only the one line whose bytes changed.** After EV-signing,
   the signer updates **only the `.exe`'s line** in the CI-produced
   `SHA256SUMS`; every other line keeps its exact CI bytes. The manifest is never
   rebuilt from local tooling.

3. **The installers fail closed.** `install.sh` and `install.ps1` refuse to
   install when `SHA256SUMS` is missing, download to a temporary path, and write
   the binary to its final location **only after** the checksum passes — and, on
   Windows, only after the Authenticode signature is `Valid` and the signer is
   Code Infinity.

4. **Self-update verifies and never downgrades.** `tina4 update` verifies the
   downloaded binary against the release `SHA256SUMS` before overwriting the
   running CLI (fail closed on a missing or mismatched sum), and refuses to move
   to a version older than the installed one.

SHA-256 is computed by shelling out to the platform tool
(`sha256sum` / `shasum` / `Get-FileHash`) in both the installers and the CLI, so
no cryptographic runtime dependency is added.

## Consequences

- A draft asset that does not match CI's checksums **and** tag-bound provenance
  can no longer be EV-signed and published.
- The published `SHA256SUMS` differs from CI's only on the signed `.exe`'s line;
  the bytes the installers verify are exactly the bytes CI produced for every
  other asset.
- An install or self-update that cannot prove the download is the published,
  signed binary stops with a clear error rather than installing it.
- A release must publish `SHA256SUMS` (every release since 3.8.53 does). A build
  old enough to lack it is installed by pinning an explicit asset by hand.

## Alternatives considered

- **Sign in CI.** Rejected: it would require the EV key / SimplySign OTP seed to
  live in CI, so an automated job could sign as Code Infinity. The human-gated
  local step is the whole point.
- **Add a Rust crypto crate for the self-update hash.** Rejected: shelling out to
  the platform SHA-256 tool matches the installers and keeps the CLI's
  zero-crypto-dependency posture.
- **Keep rebuilding the whole `SHA256SUMS` after signing.** Rejected (clause 2):
  re-deriving lines the verification already trusted reopens the gap.
