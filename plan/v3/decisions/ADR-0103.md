# ADR-0103: the Frond `date` filter accepts both strftime and Twig/PHP `date()` letters, with identical English output across the four frameworks

- Status: Accepted
- Date: 2026-11-05
- Context: tina4-python#292 (found in an AI-agent eval; a board template wrote
  `{{ c.timestamp|date("Y-m-d") }}` and every card showed the literal `Y-m-d`),
  ADR-0004 (best implementation prevails), the Twig-compatibility promise Frond
  advertises. Cross-framework contract change.

## Context

Frond markets itself as Twig-compatible, and in Twig the `date` filter takes
**PHP `date()` format letters** (`date("Y-m-d")`). The four implementations had
silently drifted into two incompatible conventions:

- **Python / Ruby / Node** passed the format straight to **strftime**
  (`%Y-%m-%d`). A Twig-idiomatic `date("Y-m-d")` has no `%`, so strftime emitted
  the letters verbatim: the page showed `Y-m-d` for every date, with no error.
- **PHP** used native `date()` (PHP letters), so `date("Y-m-d")` worked but the
  strftime spelling `date("%Y-%m-%d")` produced `%2026-03-29` (the inverse bug).

So the identical template produced three different wrong answers and one right
one, depending on the backend: a parity break, and the worst failure mode of the
three the issue named, printing the format back with no error.

## Decision

The `date` filter accepts **both** conventions and produces **identical** output:

- A format containing `%` is treated as **strftime** (back-compatible with every
  existing template and test). PHP, whose native `date()` cannot read strftime
  and whose `strftime()` is deprecated/removed (8.1+/8.3), translates the `%X`
  codes to `date()` letters first, escaping literal alphabetic characters so
  `date()` never reinterprets them.
- Any other format is treated as **Twig/PHP `date()` letters**. The supported set
  is `Y y m n d j H G h g i s A a D l M F N w`; a backslash escapes the next
  character; an unmapped character is emitted literally (PHP's own rule).
- Month and weekday **names are hardcoded English** (`January...`, `Monday...`),
  not taken from a locale-sensitive `strftime`/`toLocaleString`, so `date("l, F
  j")` returns the same bytes on every host and in every framework.
- Each framework keeps its existing default format; the **output** of the default
  is unchanged (`YYYY-MM-DD`).

Invariant: `date("Y-m-d")` == `date("%Y-%m-%d")` == `2026-03-29` in all four.

## Consequences

- Purely additive for existing templates: a `%`-format behaves exactly as before.
- A template written from Twig docs, or by an AI coder, now renders correctly on
  every backend instead of printing the format letters.
- Helpers added: Python `_php_date`, Ruby `Frond.php_date`, Node `phpDate`, PHP
  `Frond::strftimeToPhpDate` (the inverse translator). No new dependency.
- Covered by the existing per-framework Frond date-filter tests, each
  mutation-proved (forcing the strftime branch turns the PHP-letter cases red). A
  shared `frond_date_filter_contract.json` is owed if the date filter is later
  pulled into the executable contract set.
