# ADR-0079: Auth-token rules - token purpose, secret strength, explicit debug, peer identity

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** tina4-python, tina4-php, tina4-ruby, tina4-nodejs (all four, at parity)
- **Decision owner:** Andre van Zuydam
- **Fixture:** `plan/v3/fixtures/auth_token_contract.json`
- **Related:** ADR-0019 (auth gate is independent of middleware), ADR-0041 (an explicit
  argument beats the environment), ADR-0058 (RBAC reads the verified payload),
  ADR-0073 (vulnerability handling and security tests)

## Context

Every Tina4 framework signs two kinds of JWT with the same `TINA4_SECRET`:

- **auth tokens**, minted by the application (`get_token` / `getToken`) to say who a
  caller is, and
- **form tokens**, minted by Frond's `form_token()` to prove that a write came from a
  form the application rendered. A form token carries `"type": "form"` and a nonce.

The route auth gate, the WebSocket upgrade gate, `authenticate_request` and the
Bearer middleware helpers checked only that a token was validly signed and unexpired.
They did not check what the token was for. The CSRF middleware already checked
`type == "form"`, so the rule existed in one direction only.

The September 2026 security audit also found that a blank or short `TINA4_SECRET`
was accepted for signing and verifying, that debug mode could be switched on by an
implicit default rather than by the operator, that an empty peer address was treated
as a loopback caller, that PHP's native `$_SESSION` outlived a request in long-running
workers, that a stored SSO identity was trusted past its expiry, and that Ruby's form
token lived sixty times longer than configured. These are one topic: what the
framework accepts as proof of identity. They are decided together here.

## Decision

### 1. A token's purpose is part of its validity

1. A JWT whose `type` claim is `"form"` is a form token. It proves where a write came
   from. It never proves who the caller is.
2. Every identity gate refuses a form token: the route auth gate (all three token
   slots: `Authorization: Bearer`, the body `formToken` field and the session `token`),
   the WebSocket upgrade gate (header, `bearer` subprotocol and `?token=`),
   `authenticate_request` / `authenticateRequest`, and the Bearer middleware helpers
   (`Auth::middleware()` in PHP, `authMiddleware()` in Node, `bearer_auth` in Ruby).
3. A form token in one slot does not end the search. The gate skips it and keeps
   looking, so a logged-in user who submits a rendered form (form token in the body,
   auth token in the session) is still authenticated by the session.
4. The gate issues a `FreshToken` header only after an identity token authenticated
   the request, so it never issues one from a form token. `refresh_token` /
   `refreshToken` preserves purpose: refreshing a form token returns a form token
   (the existing CSRF token rotation), which every identity gate still refuses.
5. `valid_token` / `validToken` stays purpose-neutral: it checks the signature, the
   algorithm pin, `exp` and `nbf`. The CSRF middleware keeps accepting only form
   tokens, exactly as before.
6. The reserved purpose values are held in one constant per framework
   (`NON_IDENTITY_TOKEN_TYPES = ["form"]`). Application payloads are otherwise free:
   an application that puts `"type": "admin"` in its own auth token is unaffected.

Consequence: a write route that must accept anonymous form posts is marked
`@noauth()` / `->noAuth()` / `auth: false`. That was always the documented way to
open a write route (ADR-0019); a form token no longer opens it implicitly.

### 2. The HMAC secret is at least 32 bytes, and there is no blank key

1. HMAC signing (HS256, HS384, HS512) raises an error when the key is shorter than
   32 bytes. A blank key is the shortest case. The error names `TINA4_SECRET` and
   says how to make one: `openssl rand -hex 32`. 32 bytes is the HS256 output size,
   the minimum RFC 7518 section 3.2 requires for HS256.
2. HMAC verification with a key shorter than 32 bytes rejects the token (returns
   null) and logs the same message. It does not throw, so every gate fails closed
   with a 401 and never with a 500.
3. The rule applies to an explicit `secret` argument as well as to the environment.
   The key is the key, whichever way it arrives.
4. RS256 is unaffected: its key is a PEM, and the existing RS256 rules stand.
5. A server refuses to start outside dev (`TINA4_DEBUG` not truthy) when
   `TINA4_SECRET` is blank, and refuses to start in any mode when it is set but
   shorter than 32 bytes. In dev, a blank secret is still generated into the
   gitignored `.env.local`, as before. Ruby also accepts operator-provisioned RS256
   keys in `.keys/` in place of `TINA4_SECRET`.
6. Ruby no longer generates an RSA key pair implicitly when the secret is blank.
   Keys that already exist in `.keys/` keep working. Generating keys is an explicit
   action (`Tina4::Auth.setup`), and a generated private key is written `0600`.
7. Project scaffolds (`init`) write a random `TINA4_SECRET`, never a fixed
   placeholder.

### 3. Debug mode is explicit

1. An unset `TINA4_DEBUG` means debug is off, in every framework and every entry
   point.
2. No framework writes `TINA4_DEBUG=true` or an API key into a `.env` file as a side
   effect of booting. A scaffold (`init`) is an explicit developer action and may
   write `TINA4_DEBUG=true` into the project it creates.
3. The `serve` command loads `.env` before it reads `TINA4_DEBUG`, so the file's value
   is honoured. `--production` sets debug off; the explicit flag beats the
   environment (ADR-0041).

### 4. An unknown peer is not a local peer

1. `is_loopback("")` is false in all four frameworks. An empty or unknown peer
   address is a remote caller for every loopback-gated surface (MCP, dev-admin
   writes).
2. Every runtime path passes the real socket peer into the request: the built-in
   servers, PHP's Swoole, PSR-7 (RoadRunner, FrankenPHP) and array entry points, and
   the Rack, ASGI and Node servers. A synthetic in-process request that needs local
   access says so explicitly with a loopback address.

### 5. Request-scoped identity state does not outlive the request

1. In a long-running PHP process (the CLI SAPI: the built-in server, Swoole,
   RoadRunner), the native `$_SESSION` the router started for one request is written
   and closed at the end of that request, and `$_SESSION` is emptied before the next
   request starts its own session from its own cookie. A session the host
   application started itself before dispatch is left alone.
2. A stored SSO identity is accepted only while its `expires_at` is in the future. An
   `expires_at` of `0` means the provider gave no lifetime, and the identity then
   lives as long as the session. The callback and refresh store `0` when the provider
   omits `expires_in`, instead of an instant that is already in the past.
3. A form token lives `TINA4_TOKEN_LIMIT` minutes (default 60) in every framework.

## Consequences

- Applications that relied on an anonymous form post passing a default-secured write
  route must mark that route `@noauth()`. Authenticated users are unaffected: the
  session token and the frond.js `FreshToken` flow still authenticate them.
- Deployments with a blank or short `TINA4_SECRET` stop at boot with an actionable
  message instead of running with forgeable tokens. Tests that used short literal
  secrets move to 32-byte secrets.
- Ruby applications that were signing with an implicitly generated RSA key keep
  working while the key files exist; new deployments sign with HMAC and
  `TINA4_SECRET`, like the other three frameworks.
- Tools that call the MCP or dev-admin endpoints in-process must pass a loopback peer.

## Alternatives considered

- **Require `type: "auth"` on every auth token.** Rejected. Every token an
  application already minted would stop working, and application payloads already use
  `type` for their own meaning. Refusing the reserved purpose is enough and breaks
  nothing that is not the defect.
- **Treat a form token as an identity only on routes that are secured by default.**
  Rejected. A form token is issued to whoever renders the form, so it carries no
  identity on any route.
- **Warn instead of refusing to boot with a weak secret.** Rejected. The warning has
  existed for several releases and the insecure deployments still ran. A key that
  anyone can reproduce is not a configuration choice.
- **Disable the PHP native session under every CLI SAPI.** Rejected. The built-in dev
  server and existing applications use `$_SESSION`; closing and reopening it per
  request keeps them working and removes the sharing.
