# ADR-0046: Health owns a system-route tier, monotonic uptime and readiness

Date: 2026-08-10
Status: Proposed
Supersedes: the system-route, uptime, readiness-body, path-validation and
response-header clauses of ADR-0016. ADR-0016's liveness/readiness SPLIT remains
in force. Full contract: `features/037-health-check.md`.

## Context

ADR-0016 established that liveness is process-only and readiness is a separate
endpoint, but left the mechanism to each port. The re-audit (feature 37) found
liveness turned into a 503 by application middleware in all four, `/health`
shadowable by an application route, readiness absent, wall-clock uptime, and no
`Cache-Control: no-store`.

## Decision

- Health and readiness are reserved SYSTEM routes dispatched before application
  route matching and before the Feature 32 middleware pipeline; they are
  unshadowable, and an exact application conflict fails startup.
- `/__health` (plus permanent `/health`) and `/__ready` (plus permanent
  `/ready`); strict literal path validation, invalid values fail startup.
- Uptime is monotonic and never decreases for a server instance.
- GET/HEAD responses carry `Cache-Control: no-store` and no validators.
- Readiness has a check registry; a dependency is "required" when ACTIVATED
  (connection configured), auto-registers, and can be downgraded via
  `unregister`. The readiness timeout is enforced by bounding each adapter
  probe's own driver connect/statement timeout, so it holds in synchronous
  runtimes too.
- A runtime-native Docker `HEALTHCHECK` on `/health` and separate Kubernetes
  startup/liveness/readiness probes.

## Consequences

- Applications that declared their own `/health` route must move it.
- The behavior is gated by `health_contract.json` version 2, four runners and a
  real image plus dependency lab matrix in the build phase.
