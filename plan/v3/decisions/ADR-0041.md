# ADR-0041: An explicit argument always beats the environment

Date: 2026-08-06
Status: Accepted
Supersedes: none

## Context

`Log.configure("/srv/myapp/logs")` is one line that means one thing. Measured on
2026-08-06 against all four frameworks, it did three different things.

The probe controlled both coordinates and read the FILESYSTEM for the answer -
it set `TINA4_LOG_DIR` to one directory, passed a DIFFERENT directory to
`configure()`, then looked at which directory the log file actually appeared in.
Asking the framework which directory it had chosen would have been delegating
the very property under test.

| Framework | Log file landed in | `TINA4_LOG_DIR` afterwards |
|---|---|---|
| Python | the ENV directory | unchanged |
| PHP | the ENV directory | unchanged |
| Ruby | the ARGUMENT directory | unchanged |
| Node | the ARGUMENT directory | REWRITTEN to the argument |

Three behaviours, four frameworks:

- **Python** (`tina4_python/debug/__init__.py`) resolved the directory with
  `os.environ.get("TINA4_LOG_DIR", log_dir)`. That idiom reads naturally but
  says the opposite of what it looks like: the caller's argument is demoted to
  the *fallback default*, used only when the operator set nothing.
- **PHP** (`Tina4/Log.php`) did the same, and its own docblock stated it as the
  intent: `Directory: env override > caller arg`.
- **Ruby** (`lib/tina4/log.rb`) resolved `target || log_dir_env || "logs"`,
  which is the rule this ADR adopts.
- **Node** (`packages/core/src/logger.ts`) reached the right answer through a
  mechanism no other framework has: `configure()` ASSIGNED to
  `process.env.TINA4_LOG_DIR`. The argument wins, but by destroying the
  operator's value for the remaining life of the process and for every child
  process spawned afterwards.

This is the fifth instance in one working period of a single defect shape: **the
value in force is not the value anyone chose.** The others were PHP's
`Queue::resolveMongoConfig` (env `TINA4_QUEUE_URL` beat an explicit `uri`),
Node's `MongoSessionHandler.target()` (env URI beat explicit host/port), and two
manifest/lockfile divergences. Each was found by measurement and none was
visible by reading the calling code, which is what makes the shape dangerous:
the call site looks correct in every one of them.

### The second finding: a default sent through the explicit channel

Fixing precedence alone would have broken more than it fixed, which only showed
up on measuring the BOOT path rather than a direct `configure()` call.

Two bootstraps pass the framework's own default location as if it were a
caller's instruction. `Tina4::App::initialize!` calls
`Tina4::Log.configure(root_dir)`, and PHP's `App::start()` calls
`Log::configure(logDir: $basePath . '/logs')`. Python's `run()` and Node's
bootstrap pass no directory at all.

Ruby already applies the correct precedence, so measuring a booted Ruby app
shows what the argument channel does to the environment variable:

    project_root files : ["error.log", "tina4.log"]
    project_root/logs  : []
    TINA4_LOG_DIR dir  : []

Two defects in one line. `TINA4_LOG_DIR` is **entirely dead** in a booted Ruby
application - the documented variable cannot move the logs anywhere. And the
files land in the PROJECT ROOT rather than the documented `logs/`, because
`root_dir` is an existing directory and is taken as the log directory itself.
Every booted Ruby app has been dropping `tina4.log` and `error.log` beside its
`Gemfile`.

The trap this sets for PHP is the important part: PHP's booted app honours
`TINA4_LOG_DIR` **only because of the precedence bug**. The environment beats
the caller, and the bootstrap is a caller, so the operator's value wins by
accident. Correct the precedence and leave the bootstrap alone, and PHP becomes
Ruby - a dead environment variable in every booted app. The two halves have to
land together.

The rule underneath: **a framework default is not a caller instruction, and must
not travel through the argument channel.** `basePath/logs` is what the framework
falls back to, so it belongs below the environment, not above it. The fix is to
delete the argument from both bootstraps and let resolution run
env -> default, which is what Python and Node already do.

## Decision

**Precedence is explicit argument, then environment, then built-in default. In
every framework, for every configuration entry point.**

**A bootstrap passes no configuration value it did not receive from the user.**
The framework's own default goes in the default slot, never the argument slot.

Three rules follow from it, and all three are load-bearing:

1. **An argument the caller actually passed always wins.** The environment
   supplies a value for callers who passed nothing; it never overrides one who
   did.

2. **A configuration API must be able to tell "not passed" from "passed the
   default value".** A parameter defaulting to a real value cannot express the
   three-way precedence: `configure(log_dir="logs")` makes "the caller asked for
   `logs`" and "the caller said nothing" the same input. Configuration
   parameters therefore default to the null value of the language (`None`,
   `null`, `nil`, `undefined`) and resolve the real default inside the function.

3. **Reading configuration must not write it.** Resolution is a pure read of the
   environment into local state. A `configure()` that assigns to
   `process.env` / `putenv` / `ENV[]` mutates global state that other
   subsystems, later `configure()` calls, and child processes all read - so the
   operator's own value is silently gone, and the framework cannot report what
   the operator actually set.

## Why this way

The authority order is STANDARD, then real frameworks, then libraries, then our
own precedent. The standard here is unanimous, which is why this needed no
invention:

- Python's own `logging.basicConfig(filename=...)` uses the argument; there is
  no environment override at any precedence.
- Ruby's `Logger.new(path)`, Node's winston/pino destinations, and PHP's
  Monolog handlers all take the explicit path.
- Log4j and logback resolve programmatic configuration ABOVE the properties
  file, which sits above the compiled defaults.
- Twelve-factor says configuration comes from the environment. That is about
  where an application's *defaults* come from, not about an argument the
  programmer wrote at the call site being overridden by one.

Every one of them puts the more specific instruction on top, and an argument at
the call site is more specific than a process-wide variable. The inverted form
also has no way to express "put the logs exactly here" at all: with the
environment on top, an operator's `TINA4_LOG_DIR` makes the argument
unreachable, and code that must control its own log destination (a test, a
migration runner writing an audit trail, a worker isolating its output) cannot.

Ruby is the reference implementation, not Python. This is the case
`feedback_python_master_governance` exists for: Python is the master on internal
API design, but where Python is the broken one it gets FIXED rather than
mirrored into the other three.

## Consequences

**This is a breaking change, and it is the right kind.** An operator who set
`TINA4_LOG_DIR` to steer an application that also calls `configure()` with an
explicit directory will see logs move to the directory the application names.
That deployment was previously relying on the environment beating the code -
which is exactly the behaviour being removed, so there is no way to fix the bug
and keep it. The migration is one line: drop the explicit argument, or point it
where the environment pointed.

The blast radius is narrow. It changes nothing for the common cases: an
application that calls `configure()` and sets no environment variable, or sets
the environment variable and never calls `configure()`, behaves identically
before and after. Only the conflict case moves, and only in Python and PHP.

Node changes behaviour for nobody - the directory it selects is already the
argument. What it loses is the side effect: after `configure()`,
`process.env.TINA4_LOG_DIR` still reads what the operator set, and a child
process inherits the operator's value rather than the parent's argument.

**The bootstrap change is a fix in both frameworks it touches, not a
regression.** Ruby gains a working `TINA4_LOG_DIR` and stops writing
`tina4.log` / `error.log` into the project root; its logs move to `logs/`, which
is where every version of the documentation has said they are. Existing Ruby
deployments that scrape the root for `tina4.log` must look in `logs/`, and the
root-level files left behind by earlier versions can be deleted. PHP keeps the
behaviour it has today for every deployment that sets `TINA4_LOG_DIR` - it just
reaches it by the rule instead of by the bug. The one PHP case that moves is an
application whose `basePath` differs from its working directory: it logs to
`./logs` rather than `basePath/logs`. That is the documented default, and the
fix for an app that needs otherwise is to set `TINA4_LOG_DIR`, which now works.

**The rule is general, and the audit is owed.** `Log.configure` is where it was
measured, not where it stops. Every `configure`-shaped entry point that reads a
`TINA4_*` variable is subject to this ADR, and the ones already found and fixed
in this family (`Queue::resolveMongoConfig`, `MongoSessionHandler.target()`) are
the same decision applied ahead of it being written down.

Locked in by named regression tests in all four frameworks, positive and
negative: that the argument wins over a conflicting environment variable, and
that the environment still applies when no argument is passed. Both directions
are needed - a test for the first alone passes on an implementation that ignores
the environment entirely.
