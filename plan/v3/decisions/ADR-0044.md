# ADR-0044: Batch and first-row execution are adapter primitives

Date: 2026-08-10
Status: Accepted
Supersedes: the execution boundary in `features/003-database-adapter-interface.md`
and the original `adapter_contract.json`

## Context

The first Feature 3 redesign reduced the adapter to fourteen methods and placed
`executeMany` and `fetchOne` above it. Its reasoning was that a batch is a loop
over `execute` inside a transaction and a first-row read is `fetch` limited to
one.

The implementation and live evidence contradict that simplification.

- A batch must own one physical connection, native transaction state, rollback,
  affected-row accounting and generated identifiers. Tina4 has already fixed
  partial-write and premature-commit bugs in Python and Node when those details
  were reconstructed at the wrong layer.
- Collapsing 500 inserts into native/chunked batches measured 625x faster on
  PostgreSQL, 216x on MySQL and 121x on MSSQL than a facade row loop.
- The Node public facade previously committed a caller's outer transaction from
  inside `executeMany`; a real PostgreSQL regression test was required to prove
  the fix.
- A first-row read has a native cursor operation. Routing it through paginated
  `fetch` can run a true-total count probe and build a result envelope that the
  caller immediately discards.
- Python, PHP and Node already declare both methods on their adapter interfaces,
  while the shared fixture asserts they must be absent. The fixture runner
  passes because it checks the fixture against itself rather than against the
  declared boundary.

The old contract also required `lastInsertId` and `error`. Those are duplicate
channels: generated ids already belong to the write result, and failures throw
through the facade while its `getError` state records the cause.

## Decision

`executeMany` and `fetchOne` are required adapter primitives and required public
`Database` facade methods in every language.

The required adapter capabilities are:

- connection: `connect`, `close`, `getDatabaseType`;
- execution: `execute`, `executeMany`, `fetch`, `fetchOne`;
- transaction: `startTransaction`, `commit`, `rollback`, `autocommit`;
- introspection: `getTables`, `getColumns`, `tableExists`.

Every capability is required. Host-language casing and async syntax are
idiomatic, but the observable contract is shared. Node uses one asynchronous
adapter interface; synchronous methods whose implementation only throws "Use
...Async" are not valid capabilities.

`connect` is the canonical lifecycle name. `autocommit` is a readable and
writable native boolean capability; a host language may implement it as a
property or through idiomatic accessors rather than as a callable method.

`executeMany` returns one aggregate `DatabaseResult`, owns a transaction only
when it is standalone under autocommit, joins an existing explicit transaction,
and never scatters a batch across pooled connections. `fetchOne` returns one
native record or null and does not run a pagination count probe.

Adapter `fetch` returns a native list of records. The public `Database` facade
wraps those records in the shared `DatabaseResult` and owns pagination, the
true-total count and cache behavior.

`lastInsertId` and `error` leave the required adapter interface. Generated ids
come from `DatabaseResult.last_id` / `lastId`; failures throw and the facade
records the cause before rethrowing.

## Consequences

- The method count remains fourteen, but the execution and diagnostics groups
  change.
- The existing shared fixture and all four structural runners are superseded.
- Python, PHP and Node retain useful existing adapter primitives but must clean
  their fat/stale declarations and normalize result types.
- Ruby must promote its working facade batch and first-row behavior into required
  driver primitives without reintroducing optional feature detection.
- Node changes `executeMany` from a per-row facade array and adapter
  `{totalAffected}` object to the shared aggregate `DatabaseResult`, and removes
  the unusable sync/async split.
- Third-party adapters face a breaking pre-3.14 migration. Registration must
  fail loudly when any required capability is absent.
- The contract is gated by the behavioral `adapter_contract.json`, real-engine
  witnesses and negative mutations, not by method-count floors alone.
