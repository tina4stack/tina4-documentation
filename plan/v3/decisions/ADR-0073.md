# ADR-0073: Every change follows the ISO/IEC 18974 and ISO/IEC 5230 controls

- **Status:** Accepted
- **Date:** 2026-09-24
- **Scope:** All Tina4 repositories: tina4 (CLI), tina4-python, tina4-php, tina4-ruby,
  tina4-nodejs, tina4-js, tina4-documentation
- **Decision owner:** Andre van Zuydam
- **Plan:** `plan/iso/ISO-ALIGNMENT-PLAN.md`

## Context

Developers who work inside an ISO/IEC 27001 programme have to show an auditor that the
tools they build with are developed and shipped securely. Tina4 is working towards
OpenChain conformance: ISO/IEC 18974 (open source security assurance) and ISO/IEC 5230
(open source licence compliance). Those standards certify a process, not a snapshot.
A process that holds only while someone remembers it is not a process an assessor can
accept, so the controls have to be a standing rule that every change, every worker and
every release follows by default.

## Decision

From 2026-09-24 every change to an in-scope repository follows these controls. A change
that cannot meet one of them is not merged until it does, or until a new ADR records the
exception.

1. **Traceable change.** Every change to a release line (`v3`, `main`, `master`, `v2`)
   lands through a pull request with the required CI checks green. No direct pushes, no
   force pushes, no deleted or moved release tags. The repository rulesets that enforce
   this are declared in `scripts/governance/github-controls.json` and verified with
   `scripts/governance/github_controls.py --check`.
2. **Zero third-party runtime dependencies.** A framework declares no runtime dependency.
   Database drivers and optional servers are application dependencies (ADR-0067). A new
   development dependency needs a stated reason in the pull request.
3. **Vulnerability handling (ISO/IEC 29147 / 30111).** A security report arrives through
   GitHub private vulnerability reporting or the address in `SECURITY.md`, is triaged with
   CVSS v3.1, and is fixed in every affected framework in the same release (the parity
   rule). Until the fix ships, commits, pull requests and public plan documents describe
   the change factually and carry no exploit detail. The fix ships with a GitHub Security
   Advisory, a CVE where one applies, and a release-note entry.
4. **Security tests.** Every fixed vulnerability gets a named regression test in every
   affected framework, run against the real dependency (no mocks), proven by mutation, and
   kept permanently. A cross-framework rule also gets a contract fixture.
5. **Release integrity.** Every release ships checksums, a software bill of materials
   (SPDX, ISO/IEC 5962 lineage) and build provenance. Signing verifies what CI built
   before it signs. Actions in release workflows are pinned by commit SHA.
6. **Licence compliance (ISO/IEC 5230).** Inbound licences are checked on every pull
   request against the licence policy, and third-party notices ship with any artefact that
   bundles third-party code.
7. **Evidence.** The evidence register in the plan says where each control's proof lives.
   `github_controls.py --check` output, advisories, SBOMs and CI runs are kept so an
   assessor can reproduce the claim.
8. **No claim without evidence.** No page, README or release note says Tina4 is ISO
   certified, conformant or aligned until the matching evidence exists. The first public
   statement is the OpenChain conformance declaration.

## Consequences

- Maintainers and automated workers stop pushing directly to release lines once the
  rulesets are applied. Hotfixes go through a pull request too.
- The maintainer skills carry these controls, so every worker follows them without being
  told.
- Some existing gaps stay open until the plan closes them, including SBOM generation, SHA
  pinning in framework publish workflows and trusted publishing. They are tracked as plan
  items and are not exceptions to this ADR.

## Alternatives considered

- **Treat ISO work as a one-off project.** Rejected. Conformance is re-certified, and a
  control nobody enforces between audits fails the next one.
- **Record the controls only in the plan.** Rejected. The plan describes work; this log
  records the rules the code and the process must obey. Keeping the rule here means a
  change that breaks it has to supersede an ADR in the open.
