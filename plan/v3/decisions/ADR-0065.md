# ADR-0065: Database statement semantics - what a write is, what fetch and execute do with it, and which ? is a placeholder

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release
Issues: tina4-python #133, #138 (fixed at parity in all four frameworks)
Fixture: `fixtures/statement_semantics_contract.json`

## Context

Two bug reports against the Python reference turned out to be one question the
four frameworks answered four different ways: when a statement reaches the
database layer, what is it, and what will the layer do to it on the way through?

**#133: a write that returns rows was treated as a read.** `fetch_one()` is the
natural way to run `INSERT ... RETURNING id`, because you want the id back. The
read path didn't know it had been handed a write. On PostgreSQL it closed the
implicit transaction with a ROLLBACK, so the caller got an id for a row that
had just been thrown away. On SQL Server, Firebird and ODBC nothing committed it
at all. On some engines `fetch()` wrapped the statement in a `COUNT(*)` probe
and appended `LIMIT` / `OFFSET` (or `ROWS` / `TOP`), so the write either failed
with a syntax error or ran twice. With the query cache switched on, a repeated
`fetch_one()` of the same `INSERT` could be answered from the cache, so the
second row was never written. Four frameworks, four sets of symptoms, all
silent.

`execute()` had the mirror problem. A `SELECT`, a `WITH ... SELECT` or a
`RETURNING` run through it came back as a bare `true` on some adapters, so the
rows the statement produced were dropped on the floor.

**#138: `?` was translated with a text replace.** The translator turned every
`?` into the driver's marker, wherever it sat. `SELECT 'why?', ?` gained a second
placeholder and failed with an index error. A `?` in a comment or a quoted
identifier shifted every later parameter by one. And because PostgreSQL's jsonb
key operators are spelled `?`, `?|` and `?&`, a query using them could never
run, even with no parameters to bind. psycopg2 made it worse in Python: with
parameters it reads every `%`, so `LIKE 'abc%'` crashed too.

## Decision

The rules below hold in all four frameworks. `statement_semantics_contract.json`
carries them as data: its vectors are copied byte for byte into each framework's
test fixtures and walked through that framework's own functions.

### 1. What a write is

A statement is traced like this. String literals, quoted identifiers and
comments will be scrubbed out first, so `WHERE note = 'DELETE'` can't pass for
a write. Leading whitespace and opening brackets will be dropped. If the first
word is then `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `UPSERT` or `REPLACE`, it's
a write. If the first word is `WITH` and the scrubbed body holds `INSERT`,
`UPDATE`, `DELETE` or `MERGE` anywhere, it's a write too: a data-modifying
`WITH` usually ends in a `SELECT`, and the verb that matters sits inside it.
Anything else is a read.

When the detector is unsure it leans towards "write". That's the safe direction:
a read taken for a write only loses its pagination and its cache slot for that
one call, while a write taken for a read loses data.

| Framework | Detector (the one `fetch()` and the query cache consult) |
| --- | --- |
| Python | `DatabaseAdapter._is_write_statement(sql)` |
| PHP | `Tina4\Database\SqlStatement::isWrite($sql)` |
| Ruby | `Tina4::Database.write_statement?(sql)` |
| Node | `SQLTranslator.isWriteStatement(sql)` |

The ceiling is stated plainly in the fixture: only the SQL text is read, never
a function body. `SELECT create_user('a')` is a read even when the function
inserts a row. Run such a call inside `start_transaction()` / `commit()`.

### 2. fetch() and fetch_one() of a write

If the detector says "write", `fetch()` and `fetch_one()` will run the
statement exactly once, as written: no `COUNT(*)` probe, no `LIMIT` / `OFFSET` /
`ROWS` / `TOP` appended. The query cache will never answer it and never store
it; it will flush the cache instead, exactly as `execute()` of a write does.
Outside an explicit transaction the write is committed the way `execute()`
commits it. Inside one, the caller's own `commit()` or `rollback()` still owns
the boundary.

### 3. execute() returns the rows of a statement that produces them

`execute()` of a `SELECT`, a `WITH ... SELECT`, a write with `RETURNING`, SQL
Server's `OUTPUT inserted.*` / `deleted.*`, or a `CALL` / `EXEC` that produces a
result set will return those rows in the same result type `fetch()` returns.
The statement runs once, with no probe and no pagination. A plain write that
produces no rows keeps the return value it always had (`true`). A SQL error
still raises, as before.

### 4. Only a ? in SQL code is a placeholder

The translator will walk the statement and skip, untouched:

- string literals `'...'` (with `''` escapes) and PostgreSQL's `E'...'`, where a
  backslash escapes the next character;
- dollar-quoted strings `$$...$$` and `$tag$...$tag$` (`$1` is a parameter, not
  a tag);
- quoted identifiers `"..."` and `` `...` ``;
- comments, `-- ...` to the end of the line and `/* ... */`.

Every `?` left over is a placeholder and is numbered in order. A literal `%` is
never touched by the numbered form.

### 5. SQL with no parameters is sent exactly as written

If no parameters were passed, nothing is rewritten: no `?` translation and no
`%` doubling. The statement reaches the engine byte for byte, so
`'{"a":1}'::jsonb ? 'a'` works on PostgreSQL. With parameters, every `?` in
code is a placeholder, so the jsonb operators must be written as the functions
`jsonb_exists()`, `jsonb_exists_any()` and `jsonb_exists_all()`. A literal `%`
is doubled only for psycopg2 (Python), and only when parameters are passed,
because that's the only driver that reads every `%` in that case.

## Consequences

- **Behaviour change, Ruby on Firebird, needs maintainer sign-off.**
  `execute("INSERT INTO t ... VALUES (...) RETURNING id")` now raises
  `Tina4::Drivers::FirebirdDriver::ReturningNotSupported`. It used to commit the
  row and hand back nothing useful. The `fb` gem never opens a cursor for a
  singleton `RETURNING` result (measured on fb 0.10.0 against Firebird 5), so
  the value can't be read, and the old path also left the automatic transaction
  open on the connection. The statement is now rolled back and the error names
  the ways out: run the write without `RETURNING` and read the row back, use
  `db.insert(...)`, or write it as `INSERT ... SELECT ... RETURNING`, which
  Firebird returns as a real cursor.
- `execute()` of a row-producing statement no longer returns `true` on the
  adapters that used to. Code that tested `if db.execute(select_sql) is True`
  will see a result object instead; the result is always truthy.
- A write through `fetch()` that used to work only by accident of pagination
  (engines that ignored the appended clause) behaves the same; one that used to
  fail with a syntax error now runs.
- The `?` inside a literal, identifier or comment is no longer a placeholder.
  A query that relied on the old miscount to line its parameters up was already
  broken and will now fail loudly with a parameter-count error.

## Proof

`statement_semantics_contract.json` holds five invariants, all proven in all
four frameworks by one runner each, against real engines and no mocks: SQLite
for the fetch, cache and execute cases, a real SQL Server for `OUTPUT` and
`EXEC`, a real PostgreSQL for rule 5. Durability is always read back on a second,
fresh connection.

| Framework | Runner |
| --- | --- |
| Python | `tests/test_statement_semantics_contract.py` |
| PHP | `tests/StatementSemanticsContractTest.php` |
| Ruby | `spec/statement_semantics_contract_spec.rb` |
| Node | `test/statementSemanticsContract.test.ts` |

The runners were proved by mutation: dropping `INSERT` from the write verbs,
translating a `?` inside a literal, skipping the cache flush and classing
`SELECT` as rowless each turned the matching case red. The per-engine suites
that carried the original fixes (every adapter, including MySQL, Firebird and
ODBC) stay in place alongside them.
