# ADR-0059: Graph databases are one URL-selected data layer, shaped exactly like Database

- **Status:** Accepted
- **Date:** 2026-08-20
- **Scope:** Feature 139, Graph databases (Ultipa, Neo4j, Memgraph, ArangoDB)
- **Decision owner:** Andre van Zuydam

## Context

Some Tina4 projects use the Ultipa graph database, and graph engines more broadly
(Neo4j, Memgraph, ArangoDB) are a natural fit for relationship-heavy work Tina4's
audience does - knowledge graphs, fraud rings, recommendations, lineage. Today
graph access is hand-rolled per app: a bespoke client, a bespoke connection
story, a bespoke test setup. That is the same DRY failure the relational
`Database` layer already solved once, and it means every project pays the
integration cost again.

Tina4 already has a proven answer for "one uniform surface over many engines":
the `Database` layer selects a SQL adapter by URL scheme, exposes one method set,
reads `TINA4_DATABASE_URL` via `fromEnv()`, and treats each engine's native
client as an OPTIONAL dependency loaded only when that engine is used - so the
core stays zero-dependency. The owner's direction is explicit: graph should work
"exactly like how databases work."

Graph engines disagree on query language (Ultipa GQL/UQL, Neo4j/Memgraph Cypher,
ArangoDB AQL) and on protocol (Ultipa server, Bolt, HTTP). A single universal
graph query language on top would be a large, lossy abstraction. And Ultipa lacks
maintained community drivers across all four languages (notably PHP and Ruby),
while Neo4j/Memgraph/ArangoDB have usable ones.

## Decision

Tina4 ships ONE graph data layer in all four backend frameworks, modelled on
`Database` precisely.

1. **URL-selected factory.** `GraphDatabase.create(url)` (idiomatic spelling per
   language, mirroring `Database.create` / `initDatabase` / `Database.new`) parses
   the scheme, picks the adapter and connects lazily. `GraphDatabase.fromEnv()`
   reads `TINA4_GRAPH_URL` (+ `TINA4_GRAPH_USERNAME`/`_PASSWORD`,
   `TINA4_GRAPH_CONNECT_TIMEOUT`). Schemes: `ultipa://`, `neo4j://`/`bolt://`,
   `memgraph://`, `arango://`/`arangodb://`.

2. **One common adapter interface + raw escape hatch (unified + raw).** Every
   adapter implements a small PORTABLE core - `addNode`, `addEdge`, `getNode`,
   `updateNode`, `deleteNode`, `neighbors`, `traverse` - returning engine-neutral
   `GraphNode { id, labels, properties }` and `GraphEdge { id, type, from, to,
   properties }`. PLUS a raw pass-through: `query(text, params)` (read) and
   `execute(text, params)` (write) where `text` is the engine's NATIVE language,
   returning a `GraphResult` shaped like the relational `DatabaseResult`. We do
   NOT build a universal graph query language; engine-specific power goes through
   the raw hatch.

3. **Drivers are optional and loaded only when used.** The graph adapters import
   their engine driver lazily on first connect. A missing driver raises an
   actionable install error naming the package; the zero-dependency core imports
   and runs without any graph driver present. This is the exact rule the relational
   adapters follow for `pg`/`mysql2`/`ext-pdo`/etc.

4. **Memgraph reuses the Neo4j adapter.** Memgraph is Bolt/Cypher wire-compatible
   with Neo4j, so the single `bolt` adapter serves both; the scheme only sets
   engine-specific defaults. No separate Memgraph driver work.

5. **Ultipa gets bespoke standalone drivers under `tina4stack`.** Because Ultipa
   lacks cross-language community drivers, we own them as SEPARATE, reusable,
   independently-versioned packages - `tina4stack/ultipa-{node,python,ruby,php}`
   published to npm/PyPI/RubyGems/Packagist - each a thin client over Ultipa's
   wire protocol with the same shaped API in every language (see Amendment 1: the
   wire protocol is gRPC, so a driver may depend on the language's gRPC stack; the
   FRAMEWORK core stays zero-dependency by loading the driver only on use). The
   framework depends on them optionally, like any other engine driver. The other
   three engines reuse existing community drivers; no bespoke repos for them.

6. **Fail-loud + bounded connect, same as Database.** A bad raw statement RAISES
   (cause on `getError()`), never a falsy return. A connect is bounded by
   `TINA4_GRAPH_CONNECT_TIMEOUT` (seconds; default mirrors the relational
   contract) and the error names host, port and elapsed seconds.

7. **No mocks; real engines on the lab.** The contract suite
   (`fixtures/graph_contract.json`) runs against every provisioned engine
   (provider substitutability, exactly like the relational engine matrix). Ultipa
   community edition already runs on the lab; Neo4j, Memgraph and ArangoDB are
   provisioned (Docker) behind the require-services gate with per-engine
   `TINA4_TEST_<ENGINE>_URL`.

## Consequences

- Graph feels identical to SQL in Tina4: learn `Database`, you already know
  `GraphDatabase`. Switching engine is a URL change.
- The zero-dependency core is preserved; a project pays for a graph driver only
  when it opens a graph connection.
- We take on maintenance of four standalone Ultipa driver packages. That cost is
  deliberate: it is the only way to give Ruby and PHP first-class Ultipa access,
  and the packages are useful outside Tina4.
- The portable core is intentionally small; anything engine-specific rides the raw
  pass-through, so we never owe a universal graph language.

## Amendment 1 (2026-08-20): the Ultipa driver may use the language's gRPC stack

Point 5 originally said "thin zero-dependency client." Grounding the community
`ultipa-gqldb` server proved the wire protocol is **gRPC** (protobuf package
`gqldb`, default port 60061; `SessionService.Login` returns a `session_id` passed
as the `session-id` metadata header, then `QueryService.Gql` runs the query). A
production-grade pure-stdlib gRPC + HTTP/2 client is not "thin" in any language,
so a hand-rolled zero-dependency driver would be the wrong engineering call.

Decision (owner-approved): the standalone Ultipa driver in each language **may
depend on that language's standard gRPC + protobuf stack** (Python `grpcio` +
`protobuf`, Node `@grpc/grpc-js` + `@grpc/proto-loader`, Ruby `grpc` +
`google-protobuf`, PHP `ext-grpc` + `google/protobuf`). What must stay
zero-dependency is the **framework core** (point 3): the graph adapter imports the
driver lazily on first `ultipa://` connect, exactly as the relational adapters do
for `pg`/`mysql2`/`ext-pdo`. So "the core pays nothing until you open a graph
connection" holds; "the driver package itself has no dependencies" does not, and
was never the property that mattered. The Python reference driver (`tina4-ultipa`)
ships this way and is verified live against the community edition.

## Out of scope (deferred)

A graph ORM / active-graph model, graph AutoCrud, a graph dev-admin visualiser,
GraphQL-to-graph resolvers, cross-engine query translation, and graph schema
migrations. Revisit each on real demand.
