# ADR-0061: The tool loop closes - tools sent, tool_result returned

- **Status:** Accepted
- **Date:** 2026-08-22
- **Scope:** Feature 141, agent tool loop send + return path
- **Decision owner:** Andre van Zuydam
- **Extends:** ADR-0060 (the receive half)

## Context

ADR-0060 shipped typed streaming events in 3.13.113: `Ai.chat(stream=True)`
yields `text_delta` / `tool_call` / `done` / `error`. The receive side works.
The send side does not: `AiChatOptions` has no `tools` or `tool_choice`, so
the model is never told about any tool, so the `tool_call` event fires only in
theory. `_validate_messages` also rejects `role: 'tool'` (OpenAI) and content
parts of `type: 'tool_result'` (Anthropic), so even if a caller could get a
tool call back, they could not send the result back on the next turn.

The agent loop needs a full round trip:

1. Caller sends `messages` PLUS `tools: [ ... ]`.
2. Model streams back a `tool_call` event with the function name + parsed args.
3. Caller executes the tool.
4. Caller sends a new `Ai.chat` call with the tool result appended to the
   previous conversation.
5. Model streams back a `text_delta` (or another `tool_call`) and eventually
   `done`.

Step 1 and step 4 are missing across all four frameworks. This ADR closes them.

## Decision

Tina4 3.13.114 ships three additions in all four backend frameworks:

1. `Ai.chat(...)` accepts an optional `tools` argument: a list of
   `{name, description, parameters}` where `parameters` is a JSON-Schema object.
   Names follow each language (`tools=` in Python, `tools:` in Ruby, `tools`
   key in the PHP options array, `tools` field on the Node `AiChatOptions`).
2. `Ai.chat(...)` accepts an optional `tool_choice` argument:
   `'auto' | 'none' | 'required' | {name: string}`. Meaning matches OpenAI's
   contract; the client translates each value to the provider's shape below.
3. `Ai.chat(...)` accepts messages carrying tool results:
   * OpenAI-style: `{role: 'tool', tool_call_id: string, content: string}`
   * Anthropic-style (returned as a user turn): `{role: 'user', content:
     [{type: 'tool_result', tool_use_id: string, content: string}]}`

   Both forms validate. The provider translation layer maps whichever the
   caller sent to the shape the current provider expects, so an agent loop
   written against the Tina4 surface never has to fork on `TINA4_AI_PROVIDER`.

## Wire translation

### Outbound `tools`

| Provider | Body key | Element shape |
| --- | --- | --- |
| OpenAI, local | `tools` | `{type: "function", function: {name, description, parameters}}` |
| Anthropic | `tools` | `{name, description, input_schema}` (`parameters` renamed) |

### Outbound `tool_choice`

| Tina4 value | OpenAI body | Anthropic body |
| --- | --- | --- |
| `'auto'` | `{tool_choice: "auto"}` | `{tool_choice: {type: "auto"}}` |
| `'none'` | `{tool_choice: "none"}` | omit `tools` (Anthropic has no "none") |
| `'required'` | `{tool_choice: "required"}` | `{tool_choice: {type: "any"}}` |
| `{name: "x"}` | `{tool_choice: {type: "function", function: {name: "x"}}}` | `{tool_choice: {type: "tool", name: "x"}}` |

### Return path (tool_result -> provider body)

When the caller sends the tool result on the next turn:

* OpenAI-style input `{role: "tool", tool_call_id, content}` -> passthrough on
  OpenAI/local; translated to Anthropic as the user-turn form below.
* Anthropic-style input `{role: "user", content: [{type: "tool_result",
  tool_use_id, content}]}` -> translated to OpenAI as `{role: "tool",
  tool_call_id: tool_use_id, content}`.

Either input form works on either provider. The client normalises.

## Public surface

| Concept | Python | PHP | Ruby | Node.js |
| --- | --- | --- | --- | --- |
| Declare tools | `Ai.chat(msgs, tools=[...])` | `AI::chat($msgs, ['tools' => [...]])` | `AiClient.chat(msgs, tools: [...])` | `Ai.chat(msgs, {tools: [...]})` |
| Choose tool | `tool_choice="auto"` etc. | `'tool_choice' => 'auto'` | `tool_choice: 'auto'` | `toolChoice: 'auto'` |
| Return result (OpenAI form) | `{"role": "tool", "tool_call_id": id, "content": ...}` | array with same keys | Hash with same keys | Object with same keys |
| Return result (Anthropic form) | user message with `tool_result` part | same | same | same |

`toolChoice` in Node follows JS camelCase; every other language uses its native
casing. Wire bytes, tool shape, and translation are identical across languages
and provider-neutral.

## Non-goals

Client-side tool execution stays outside Tina4. The framework does not run the
tool for you, does not maintain a tool registry, and does not schema-validate
the arguments the model returned - the caller's tool implementation owns those.
A future ADR may add an opt-in `Ai.agent(...)` helper that runs the loop end
to end; this ADR gives that helper everything it needs, without foreclosing
its shape.

Streaming the tool result back mid-tool-execution (partial `tool_result`
chunks) is not in this ADR. The tool ran; you send its full result on the
next turn.

Provider-specific tool_choice values that do not map cleanly to the four Tina4
values (e.g. Anthropic's `disable_parallel_tool_use`) are not exposed; caller
who needs them constructs the raw request themselves via `Api.stream_sse`.

## Consequences

An application written against `Ai.chat` can now run a full agent loop:

```
tools = [{"name": "weather", "description": "Get the weather",
          "parameters": {"type": "object",
                         "properties": {"city": {"type": "string"}},
                         "required": ["city"]}}]

for event in Ai.chat(messages, tools=tools, stream=True):
    if event.type == "text_delta":
        print(event.text, end="")
    elif event.type == "tool_call":
        result = run_local_tool(event.name, event.args)
        messages.append({"role": "assistant", "tool_calls": [{
            "id": event.id, "type": "function",
            "function": {"name": event.name, "arguments": json.dumps(event.args)}}]})
        messages.append({"role": "tool", "tool_call_id": event.id, "content": result})
        # continue the loop with a fresh Ai.chat call
```

Identical shape in PHP, Ruby, and Node. No provider-specific plumbing in the
caller. No hand-rolled SSE. No raw HTTP in the app.

The 3.13.113 typed streaming events stop being theoretical - a real agent
loop can consume them today, provider-neutrally.

The shared `ai_client_contract.json` fixture grows by four cases: tool
declaration wire-shape, tool_choice mode translation, tool_result message
shape (both OpenAI and Anthropic input forms), and a full agent-loop
round-trip against the fixture server. All four proven live in every
framework, no test doubles.

## Deferred / not decided

- `Ai.agent(...)` helper that runs the loop end to end. This ADR gives the
  primitives; the helper is a future ADR when a caller pain-point justifies
  it. Today the loop is ~15 lines in the caller.
- Structured JSON output mode (OpenAI's `response_format: json_schema`,
  Anthropic's structured output beta). Adjacent but independent; own ADR.
- Streaming tool_result submission. Rare; not in current provider surfaces.
- Parallel tool_call handling in a single turn (OpenAI can emit N tool_calls
  at once). Already supported by the aggregator - each closes independently
  as its args JSON parses - but the ADR-0060 event stream just fires N
  `tool_call` events in order. The caller handles the parallelism.
