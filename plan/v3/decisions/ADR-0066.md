# ADR-0066: Security headers on every response and every entry point; CORS same-origin clarification

Status: Accepted
Date: 2026-09-24
Ships in: the next 3.13.x release
Issues: tina4-python #134, #135, #136, #137, #139 (fixed at parity in all four frameworks)
Clarifies: ADR-0048 (it does not supersede any clause of it)
Fixtures: `fixtures/securityheaders_contract.json` (three new invariants), `fixtures/cors_contract.json` (new)

## Context

SECHDR-DEC-01 made the security headers secure by default: the middleware is
registered at boot and a routed response carries the canonical set. Three gaps
sat underneath that promise.

**Some responses never met the middleware (#137).** Static files, the single
page front door at `/`, the 404 and 405 fallbacks and the framework's own
refusals (a Cross-Site Request Forgery (CSRF) 403, an auth 401, a rate-limit
429) were written by code paths that ran before the middleware, or skipped it
when an earlier hook refused. The one response most worth protecting, the
site's own HTML and scripts, went out with no `X-Frame-Options`, no `nosniff`
and no Content Security Policy (CSP).

**Some entry points never attached it (#134).** Python's `asgi()`, the
documented way to run under uvicorn, built the app by hand and left out the
security headers, CSRF and the configured Single Sign-On (SSO) route mount that
`run()` attached. The same app lost all three the moment it changed server.

**The CORS warning fired on the app's own page (#139).** A browser sends
`Origin` on every same-origin `POST`, `PUT`, `PATCH` and `DELETE`, and the
Cross-Origin Resource Sharing (CORS) layer read "Origin is present" as
"cross-origin". An app's own form save logged "refused cross-origin request"
and advised adding `'*'`, advice that would open the API to every website to
silence a warning about itself. ADR-0048 had already said the warnings must be
bounded, and that the behaviour would be gated by `cors_contract.json` and four
runners. That fixture was never written.

## Decision

### 1. Every response the framework writes carries the security headers

Static files, the `/` front door, the 404 and 405 fallbacks and every refusal
the framework writes itself will carry the canonical set from SECHDR-DEC-01. If
a route has already set one of those headers, its value is kept: only headers
that aren't there yet are filled in. A page that needs a relaxed CSP sets it on
its own response and the framework leaves it alone.

### 2. Every entry point builds the application the same way

Every supported way to serve a Tina4 app will attach the same middleware
(security headers and CSRF) and mount the configured SSO routes, because each
one goes through the same bootstrap rather than a hand-maintained copy of it:

| Framework | Entry points proven |
| --- | --- |
| Python | `run()` and `asgi()`, both through `_bootstrap_application()` |
| PHP | `App::run()` in the CLI (Tina4's own socket server), `App::run()` / `handle()` under a web SAPI (`php -S`, PHP-FPM, Apache), `App::__invoke()` (Swoole, RoadRunner, PSR-7) |
| Ruby | `app.rb` (`Tina4.initialize!` + `Tina4::WebServer`), `Tina4.run!` (Puma), `config.ru` under the `puma` executable, `tina4ruby serve` |
| Node | the `startServer()` listener, and `handle()` embedded in the caller's own `node:http` server |

The same pass fixed two neighbours the bootstrap owns: a first-visit SSO login
now gets its session cookie even when the session holds only SSO state (#135),
and the MongoDB session handler shares one client per URI instead of building a
new one for every handler (#136).

### 3. A same-origin request is not a CORS event

A request is same-origin when its `Origin` header, normalised to
`scheme://host[:port]` with the default port dropped (80 for http, 443 for
https), equals the request's own origin: its scheme, read through the same
`X-Forwarded-Proto`-aware detector the session cookie trusts, and its `Host`.
Such a request will produce no CORS warning and no `Access-Control-*` header,
with or without a policy. Being same-origin only silences the warning. It never
grants anything a cross-origin caller wouldn't get, so a spoofed `Host` gains
nothing. An `Origin` that differs only by port or scheme is cross-origin.

### 4. A CORS warning never advises '*'

The warning for a refused cross-origin request names the refused origin and
tells the operator how to add that one origin to `TINA4_CORS_ORIGINS`. It never
contains `*`.

### 5. Diagnostics are bounded by reason (ADR-0048, now proven)

Warnings are remembered by reason (unconfigured, denied, wildcard with
credentials), never by origin. A scripted probe sending a thousand invented
`Origin` headers will log one line per reason and grow no ledger. The first
line still names the origin that triggered it. PHP and Ruby gained a public
reader for the ledger (`CorsMiddleware::warnedReasons()`,
`Tina4::CorsMiddleware.warned_reasons`) to match Node's `corsWarningReasons()`,
so the runners read it through the framework rather than its internals.

## Consequences

- Responses that used to go out bare now carry six more headers. The default
  CSP `default-src 'self'` will now also apply to static HTML, so a static page
  that loads a script from a CDN needs `TINA4_CSP` set, exactly as a routed
  page already did.
- An app that served itself under `asgi()` now enforces `TINA4_CSRF=true`. A
  form that posted without a token worked there before and is refused now.
- PHP's `denied` warning was still keyed by origin on this branch; it's keyed
  by reason now.
- `cors_contract.json` records five ADR-0048 and ADR-0066 clauses as owed
  rather than dropping them: wildcard with credentials failing startup, an
  `Access-Control-Expose-Headers` default, one validated immutable policy, PHP
  applying CORS without an explicit `Router::use(CorsMiddleware::class)`, and
  PHP keeping its one-warning-per-reason promise across forked request children.
  Tina4's PHP socket server forks a child per request by default, and a child
  starts with an empty ledger, so in that mode each refused request logs its
  line. The ledger itself still can't grow; it dies with the child. PHP proves
  the bound in one serving process (`TINA4_SERVE_FORK=false`), the model a pool
  worker or PHP-FPM worker follows.

## Proof

| Invariants | Python | PHP | Ruby | Node |
| --- | --- | --- | --- | --- |
| security headers (3 new) | `tests/test_security_headers_every_response_contract.py` | `tests/SecurityHeadersEveryResponseContractTest.php` | `spec/security_headers_every_response_contract_spec.rb` | `test/securityHeadersEveryResponseContract.test.ts` |
| CORS (4 proven, 5 owed) | `tests/test_cors_contract.py` | `tests/CorsContractTest.php` | `spec/cors_contract_spec.rb` | `test/corsContract.test.ts` |

Every case runs through the real pipeline with no mocks: each entry point is a
real server on a real port (a real child process where the entry point is one),
the SSO mount discovers a real OpenID provider over HTTP, and CORS warnings are
read from the server's real log. The runners were proved by mutation: a no-op
header stage, a header that always overwrites, `asgi()` skipping the shared
bootstrap, a missing same-origin check and an origin-keyed ledger each turned
their cases red.
