THE CONTRACT TO ADOPT\n\nUnder ADR-0012 (standard > mainstream frameworks > libraries > internal precedent).\n\n### 3.1 What a missing or zero expiry stamp means: **NEVER EXPIRES.** Tier: mainstream frameworks. Unanimous, therefore binding.\n\nThis is settled and it is not close. Five mainstream implementations were measured, and none of them deletes:\n\n- **connect-mongo 6.0.0** matches missing expiry as valid *on purpose*: the read query is literally `$or: [{expires: {$exists: false}}, {expires: {$gt: new Date()}}]`. Measured against real MongoDB 7.0.39: doc with `expires` FIELD ABSENT -> `SESSION RETURNED`, stale doc -> null, and the cleanup query's deletion candidates were `[\"STALE\"]` only. Someone wrote that `$exists: false` clause deliberately.\n- **Laravel illuminate/session v13.23.0**: `return isset($session->last_activity) && ...`. Measured on real SQLite: `last_activity=NULL` -> `read()` returned the payload; `gc(7200)` deleted 1 row and left `A,C` - the NULL row survived.\n- **express-session 1.19.0 MemoryStore**: `if (expires && expires <= Date.now())`. Measured: NOEXP and NOCOOKIE both returned the session, only PAST was destroyed.\n- **Django 6.0.7**: `if not expiry: return self.get_session_cookie_age()` with the comment \"Checks both None and 0 cases\". Measured file backend: `'_session_expiry' present? False`, `get_expiry_age() -> 1209600`, loads, survives `clear_expired()`.\n- **connect-redis 10.0.0**: `else ttl = this.ttl` (default 86400). Measured against real Redis 7.4.10: no-expires session stored with real TTL 86400 and returned by `get()`.\n- **PHP native 8.5.7 files handler** - the thing tina4-php is reimplementing - never puts expiry in the payload at all. Measured 2x2 with `gc_maxlifetime=100` and explicit `session_gc()` returning 2: payload+stale DELETED, payload+fresh KEPT, **zero-byte+stale DELETED, zero-byte+fresh KEPT**. The decision tracked the file timestamp and was completely independent of the payload. Reading the zero-byte record - a record carrying no expiry information whatsoever - gave `session_status ACTIVE? yes`, `$_SESSION = []`, and it was writable.\n\nDjango is the strictest posture available and it still does not delete: `expire_date` is `NOT NULL` so the state is unrepresentable (measured: NULL insert -> `IntegrityError NOT NULL constraint failed`), and on a forced-NULL clone **both** of Django's real predicates matched 0 rows - the load predicate (not loadable) and the GC predicate (not deleted).\n\nSo the current tina4-php behaviour - missing stamp means epoch 0 means infinitely old means unlink the file - is not a defensible reading of any mainstream implementation. It is not a majority-vs-minority call; it is 0 for 5, plus the PHP standard library, plus 3 of the 4 Tina4 frameworks already doing the opposite.\n\n**Adopt:** absent or zero stamp means the record is valid and is returned. It is not deleted, and it is not a GC candidate. If a defensive posture is wanted later, Django's is the ceiling: decline to load, never destroy.\n\n### 3.2 Absolute vs relative: **ABSOLUTE.** Tier: internal precedent, because the tiers above it do not decide.\n\n- Standard tier: **no hit.** There is no cross-language standard for server-side session storage shape. PHP's `SessionHandlerInterface::gc(int $max_lifetime)` is a language-standard interface and it is relative, but it binds only tina4-php and only at the gc boundary.\n- Mainstream tier: **split 3-2 and therefore does not bind.** Relative: PHP native (file timestamp vs `gc_maxlifetime`), Laravel (`last_activity` integer, and mtime on the file driver), Rails (`updated_at`, with `add_index :sessions, :updated_at` so an external cron can sweep by age; there is no expiry column and no GC in the gem at all - measured, a 10-year-backdated session loaded fine with its row intact). Absolute: Django (`expire_date` datetime), connect-mongo (`expires` Date). Hybrids in both directions: connect-redis derives a relative Redis TTL from an absolute `cookie.expires`; Django's cache backend derives a relative TTL from an absolute stamp.\n- Libraries tier: connect-redis and connect-mongo are the library-tier entries and they are themselves split.\n- **Internal precedent decides, and it points at absolute.** Python file and database, Node file and database, Ruby database, PHP database are all already absolute. The only relative sites in the entire codebase are the four places that are broken or latently broken: tina4-php's file backend (fatal), tina4-python's mongo handler (latent, proved), tina4-nodejs `Session.start()`'s `_accessed` check (defused by a short-circuit), and tina4-ruby's file mtime (safe, but for the different reason that the OS owns the stamp).\n\nI am recording that this **diverges from the mainstream-authority agent's recommendation**, which was relative, on the grounds that relative degrades safely. The measured evidence inside Tina4 says the opposite about *this* codebase. Relative needs arithmetic (`now - stamp > ttl`), and a poisoned zero passes straight through arithmetic into a true result. Absolute needs a comparison (`now > stamp`), where a zero is naturally caught by the `> 0` guard the code already wants to write. Every Tina4 failure and near-failure measured here is in relative code; no absolute site failed for a stamp reason. Tiebreak under the maintainability principle also favours absolute: `write()` does one addition, `read()` does one comparison, and there is no ttl in scope at read time to get wrong.\n\n**Adopt:** an absolute epoch expiry, computed by the persistence layer at write time from the ttl, compared at read time, with `0` and absent both meaning \"no expiry\". Explicitly: **the ttl must not be in scope at read time.** Python's file handler already enforces this structurally (no `_ttl` attribute on the handler), and that is the property to replicate. Delete the `_ttl`-at-read-time member from every handler that has one.\n\n### 3.3 The stamp is owned by the persistence layer, never by the caller's payload. Tier: mainstream frameworks, unanimous.\n\nEvery one of the five mainstream implementations writes the stamp itself: Django's `create_model_instance` sets `expire_date=self.get_expiry_date()` on every save; connect-mongo recomputes `expires` on every set and on touch; Laravel's `getDefaultPayload()` sets `last_activity` on every write; PHP native gets it from the filesystem. Node and Python already do this. tina4-php is the only implementation in this survey where the stamp can be absent, and that is exactly because it delegates to the caller. Additionally, the stamp must live in an **envelope beside** the payload (Node's `{_data, _expires}`), never inside it, so a caller cannot omit or clobber it and so a user key named `_expires` cannot collide.\n\n### 3.4 Sliding: **slide on WRITE, not on read.** Tier: internal precedent plus maintainability.\n\nThis is a genuine semantic decision that has been made by accident so far and must be made explicitly. Measured: a Ruby file read leaves mtime untouched (`read refreshed the stamp? false`), so a session actively read but never written expires ttl seconds after its last **write**. Redis/Valkey `SETEX` and memcached's exptime behave identically - they re-arm only on write. PHP's field is named `last_accessed`, implying slide-on-read, and PHP native ships `SessionUpdateTimestampHandlerInterface::updateTimestamp()` precisely to refresh a stamp without rewriting the payload (observed live under `lazy_write=1`: `open / read / updateTimestamp / close` with no `write()` on an unchanged second request).\n\nSlide-on-read cannot be implemented uniformly without adding a write to every request on the native-TTL backends, which is a real cost for a session store. Slide-on-write costs zero code and is what four of the six backends already do natively. Adopt slide-on-write and **document it**: \"the session expires ttl seconds after it was last saved\". Rename `last_accessed` to something that does not lie.\n\n### 3.5 The consequential fixes that fall out of the contract\n\n1. **`write(id, data, ttl)` must accept and honour ttl on every handler in every framework.** Currently: PHP passes it only to the file backend, Ruby's 5 non-memcached handlers raise `ArgumentError` on it, Python's mongo discards it, Node's mongo discards it. Either honour it everywhere or remove it from the facade in all four; do not leave it half-wired.\n2. **`expires_at REAL` must become `DOUBLE PRECISION` (or BIGINT epoch seconds).** Python and Ruby both emit `REAL`, which is float4 on PostgreSQL with a 128-second ULP at the current epoch. This is a schema migration on a shipping branch, so it needs a migration note per the contract-change changelog rule.\n3. **MongoDB must move off the relative shape in Python** and onto either the absolute stamp or a real Mongo TTL index (Ruby already uses a TTL index and is the reference here: `{name: \"updated_at_1\", key: {\"updated_at\" => 1}, expireAfterSeconds: 3600}`). **Node's mongo must gain expiry at all.**\n4. **PHP `DatabaseSessionHandler` must call `execute()`, not `exec()`**, or the adapter surface must gain `exec()`. This is a one-word fix for an outage.\n5. **Node's `resolveDbPath()` must not silently fall back to a local file.** The precedent is already in the same file: `resolveBackend()` at `session.ts:100-129` rejects unknown backend names rather than falling through to disk, with a comment naming silent-demotion-to-disk as the exact failure it prevents. Apply the same rule one layer down.\n6. **Remove Node's duplicated relative check** at `session.ts:461-463`. Two expiry mechanisms in series on the same data, one of which is the broken shape, is a landmine.\n7. **PHP's meta-only collapse heuristic** (`Session.php:371-381`) must go. A live cleared session must read as an empty session, not as null.\n\n---\n\n## 4.
